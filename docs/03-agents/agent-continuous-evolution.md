# Agent 的持续进化:从运行轨迹中获得学习信号

> **一句话摘要**:今天的 Agent 能零样本解决新任务,却可能处理了一万次相似任务后仍犯同样的错误。持续进化 = 在模型外围建立**可验证的学习系统**:记录运行证据 → 三层验证 → 提取共性 → 更新知识/指令/程序/参数 → 回归后发布。本文基于《深入理解 AI Agent》第 8 章。
>
> **来源**:《深入理解 AI Agent:设计原理与工程实践》第 8 章(李博杰,https://github.com/bojieli/ai-agent-book),全文存档于 `references/ai-agent-book/book/chapter8.md`

## 概念:能力悖论与"保存 ≠ 学习"

!!! warning "核心悖论"
    Agent 可以零样本解决从未见过的复杂任务,却可能在处理了一万次相似任务之后,第二天仍然犯下第一天的错误。**能否自主从经验中学习**,是 Agent 从"会完成任务"走向"能够可靠工作"的关键。

**为什么模型自己学不动**:

- 部署后的模型不会因一次推理自动改变参数;上下文学习只让 Agent 在**当前任务内**适应;
- 把对话存进记忆 ≠ 学会新行为——原始轨迹里既有有效策略,也有偶然成功、错误归因和不可信输入;
- 生产环境很少提供干净学习信号:用户满意不代表合规,测试通过也可能源于删除了失败用例;未经验证的在线参数更新会**放大噪声、攻击与能力漂移**(错误经验被固化并在后续任务持续放大)。

!!! tip "保存经历 ≠ 从经历中学习"
    把一百条轨迹放进向量库,能找回案例,却不会自动完成**跨案例比较**(哪些步骤反复出现、某次成功来自策略还是偶然)。学习发生在系统主动完成"评价、对照、归纳、验证"之后,而不是日志写入磁盘那一刻。

**可行路径**:在模型外围建立**自主的学习系统**——记录运行证据、验证结果与过程、从多条轨迹提取共性,再决定更新哪个载体;所有修改先形成候选版本,回归测试与安全检查通过后才改变下一轮运行。前几章部件齐备后,把它们组织成"持续进化闭环"(第二章管任务内状态、第三章管知识、第五章管工具与元能力、第六章管评估、第七章管参数)。

## 原理 1:从运行轨迹中获得学习信号(起点是评价,不是总结)

持续进化的起点不是"总结"而是"**评价**"——系统不知道任务是否完成、哪一步造成成败,反思就只是猜测;错误评价一旦进入长期知识/提示词/训练数据,影响会跨任务放大。

### 三层验证结构(可靠性从底到顶递减)

| 层 | 验证器 | 回答的问题 | 依赖 |
| --- | --- | --- | --- |
| 底层 | 结果验证器 | 事情是否**真的办成** | 测试结果、数据库状态、工具返回(代码+环境真值) |
| 中层 | 过程验证器 | 是否以**允许的方式**办成 | 业务规则、权限、动作序列 |
| 上层 | 质量验证器 | 是否**办得合适** | Rubric 评价语言与策略(LLM) |

越靠下越应依赖代码和环境真值,只有难以形式化的部分才交给语言模型。

### 轨迹评价:结构化诊断,而非一个总分

以客服 Agent 为例,Rubric 至少覆盖七维:任务结果、规则遵从、隐私边界、事实可靠性、**承诺—行动一致性**、表达质量、合规变通。其中:

- **承诺—行动一致性**尤其适合 Agent:只读最终回复会以为"我已经为您提交退款"是良好服务;轨迹评价会检查是否真的调用了退款工具、调用是否成功、订单状态是否改变;
- 验证结果不压缩成标量,而是保留"任务部分成功、规则遵从通过、但出现一处无证据陈述"这类**维度化诊断**——后续模块才能判断该改知识、提示词还是 Harness;
- **LLM 验证器需要校准**:用专家标注的少量轨迹检查一致性;高风险/低置信度案例交给第二个模型或人工复核;模型版本变更后重跑校准集;
- 裁判与选手分离:**验证器只负责评价与证据,不应同时直接改写规则**。

## 原理 2:持续进化的四种方法(选载体看"能力能否被自然表达")

| 更新方式 | 适合承载 | 主要优势 | 主要局限 |
| --- | --- | --- | --- |
| **知识** | 事实、经验(文档) | 可解释、可审计、可回滚 | 需要检索设施(第三章) |
| **指令(Prompt/Skill)** | 可清楚语言化的策略 | 成本低、见效快 | 复杂策略难表达,易被忽略 |
| **程序** | 可精确执行的流程与约束 | 确定性最强 | 写代码有成本,需测试 |
| **模型参数** | 感知、语言风格、隐式策略 | 承载高维能力 | 成本高、不可解释、需训练数据 |

四种方式**不互斥**:医疗影像 Agent 靠参数识别病灶、知识库提供最新指南、代码计算风险指标;客服模型的自然语气来自后训练、企业政策由知识与 Skill 提供、关键合规则由服务端代码兜底。

!!! tip "选择的首要依据"
    不是"经验出现了多久",而是**目标能力能否被某种载体自然表达**。遇到问题先判断:适合外部规则、程序流程、Skill 还是模型参数?

## 原理 3:可长期运行的持续进化闭环

**在线执行与离线学习分离**(闭环设计核心):

```
在线:记录运行证据(轨迹、结果、评价)
  ↓
离线:从多条轨迹提取共性 → 生成候选更新(知识/Prompt/Skill/程序/参数)
  ↓
验证:独立边界任务 + 原有任务回归,检查是否真正有效
  ↓
发布:逐步发布、整理或回滚(可归因、可验证、可回滚的局部修改优先)
```

- 优先采用**可归因、可验证、可回滚的局部修改**;
- 系统也可以优化"管理和生成这些产物"的方法本身,但先做好局部修改;
- 闭环在**结果可自动验证的任务**上最可靠;目标模糊、反馈延迟的开放任务,人仍需参与问题定义与评价标准制定。

## 代码 / 实现:一个概念性的持续进化循环

原文为方法论章节。下面用纯 Python 演示"在线记录 → 离线验证 → 候选更新 → 回归发布"的核心流程(示意):

```python
class EvolvingAgent:
    """概念演示:三层验证 + 候选更新 + 回归门禁"""
    def __init__(self):
        self.knowledge = {}          # 更新载体:知识库
        self.rules = []              # 更新载体:程序/规则
        self.trajectories = []       # 在线记录的证据

    def record(self, trajectory, result_check, process_check):
        """在线:记录轨迹 + 底层/中层验证"""
        ok = result_check and process_check           # 结果 + 过程都通过?
        self.trajectories.append({"traj": trajectory, "ok": ok})
        return ok

    def offline_learn(self, extractor):
        """离线:从多条轨迹提取共性,生成候选更新"""
        # 只看成功轨迹中反复出现的做法(跨案例比较,而非单条总结)
        common = extractor([t["traj"] for t in self.trajectories if t["ok"]])
        return {"candidate": common, "source": len(self.trajectories)}

    def regression_gate(self, candidate, boundary_tasks):
        """回归门禁:候选更新必须通过边界任务 + 原有任务才能发布"""
        return all(boundary_tasks(candidate))         # 独立边界任务检查

# 演示:运行 100 次任务,成功轨迹中"先查订单状态"成为候选规则
agent = EvolvingAgent()
for i in range(100):
    traj = f"step{i}: 查询订单 -> {'先查状态' if i % 3 else '直接改单'}"
    agent.record(traj, result_check=(i % 3 != 0), process_check=True)

def extractor(trajs):
    return "先查订单状态再操作" if any("先查状态" in t for t in trajs) else None

candidate = agent.offline_learn(extractor)
print("候选更新:", candidate["candidate"], f"(来自 {candidate['source']} 条轨迹)")
print("回归门禁:", "通过,发布" if agent.regression_gate(candidate["candidate"], lambda c: [True]*3) else "拦截")
```

**运行结果**:系统从 100 条运行轨迹中提取出共性做法作为候选更新,并通过回归门禁后发布——这就是"保存经历 → 评价 → 归纳 → 验证 → 发布"的持续进化最小循环。

## 实践 / 应用:落地要点

1. **评价先行**:先搭三层验证器(结果/过程/质量),别急着"总结";
2. **选对载体**:知识→文档、策略→Prompt/Skill、流程→代码、高维能力→参数;从便宜的开始(知识/Prompt 优先于参数);
3. **裁判分离**:验证器与进化决策模块分开,避免"既当裁判又改规则";
4. **在线/离线分离**:在线只记录,离线才生成与验证候选更新;逐步发布、可回滚;
5. **与 Loop 配合**:持续进化是跨任务的"慢学习",Loop Engineering 是任务内的"快迭代"——两者互补(见 [Loop Engineering](../07-agent-coding/experience/loop-engineering.md))。

## 总结

- 能力悖论:Agent 强在零样本,弱在不能从经验中学习;"保存经历 ≠ 从经历中学习";
- 学习起点是**评价**:三层验证器(结果/过程/质量)+ 维度化轨迹诊断 + 验证器校准;
- 四种更新方式:**知识、指令、程序、参数**,按"能力能否被自然表达"选择,可组合使用;
- 闭环核心:**在线记录证据、离线生成并验证候选、逐步发布或回滚**;结果可自动验证的任务最可靠。
