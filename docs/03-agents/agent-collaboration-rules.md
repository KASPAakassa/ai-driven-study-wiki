# AI 协作规则设计:让 Agent 第一次进项目就知道怎么干活

> **一句话摘要**:AI 换一个对话就忘掉你的要求,每个项目都要重新调教——这不是模型的问题,是**规则没有固化**。本文把"协作规则文件(AGENTS.md)"提炼成一套设计方法:六个维度(开发基础/工作方式/开发边界/代码规范/自检验证/安全检查)怎么设计、规则怎么从对话记录里挖掘、边界怎么写才不会被 AI 钻空子。
>
> **来源**:微信公众号「Blinkoo毕林庫」《我在 GitHub 开源了一份 AI 开发协作规则》,https://mp.weixin.qq.com/s/q-3R3tyF37w8GWCeICudXQ;模板:https://github.com/Nicotine00/Blinkoo-Vibe-Daily;原始资料存档于 `docs/inbox/ai-collaboration-rules-source.md`

## 概念:为什么需要"协作规则"文件

半年跑多个项目的真实痛点:**共性问题反复出现,每个项目都要重新提相同的要求,换个对话 AI 就忘,还需要反复强调**。典型翻车:擅自硬编码、不确认直接大改项目、整个程序代码崩溃乱码、所有功能写在一个文件直逼千行无法修改。

!!! tip "解法:把规则固化成文件"
    把之前所有项目的 AI 对话记录跑一遍,把**反复强调的指令全部摘出来**,去掉项目特有配置、保留通用部分,整理成一份 `AGENTS.md`。放进项目根目录,让 AI 先读文件再干活——一次固化,所有项目复用。

## 原理:六个维度怎么设计

### 1. 开发基础(让 AI 第一次进项目就知道技术选型)

技术栈声明、项目结构约定、依赖管理规则——AI 不会自作主张引入你没用过的框架,不会凭空猜目录结构。

### 2. 工作方式(先方案后代码)

先 plan 后动手、增量修改、最小输出、多文件改动先列计划再执行。**核心原则:不要一次性给代码,先给方案。** 这防止"AI 直接大改项目"——改之前它必须先把计划摆出来给你看。

### 3. 开发边界(最重要的维度)

AI 需要知道**什么该做、什么不该做**,以及四个关键场景怎么办:

| 场景 | 规则设计 |
| --- | --- |
| 需求超出能力范围 | 明确要求 AI 停下来提问,不要硬做 |
| 用户的做法效率低 | 先提出更优方案征求同意,而不是擅自更换实现 |
| 需求会引入过高复杂度 | 评估后说明取舍,请求确认,不默默加复杂度 |
| 与既有约定冲突 | 引用冲突点,让用户裁决,不自行决定 |

### 4. 代码规范(约束产出质量)

不硬编码、留扩展口、函数粒度控制、不搞过度设计——AI 最常犯的"堆在一个文件里"就是函数粒度失控的结果。

### 5. 自检验证(写完先自测)

写完先自测、核心逻辑必须有测试、改完做对比(改动前后行为对比)、外部依赖先做连通测试再集成。**一开始觉得麻烦,养成习惯后反而节省大量调试时间**——把验证写进规则,AI 的"完成"才有客观标准。

### 6. 安全检查(兜底)

Git 基线(没有 Git 就不要让 AI 大规模改项目)、对话长度控制、敏感信息保护。规则必须要求 AI 在动手前确认有可回滚的基线。

## 代码 / 实现:规则文件完整性检查器(纯 Python)

把"六个维度"落成可运行的检查器——读你的 AGENTS.md,检查六个维度是否覆盖,输出缺口与建议:

```python
DIMENSIONS = {
    "开发基础":   ["技术栈", "项目结构", "依赖"],
    "工作方式":   ["先 plan", "增量", "最小输出", "列计划"],
    "开发边界":   ["该做", "不该做", "超出能力", "复杂度"],
    "代码规范":   ["不硬编码", "扩展口", "函数粒度", "过度设计"],
    "自检验证":   ["自测", "测试", "对比", "连通测试"],
    "安全检查":   ["Git", "对话长度", "敏感信息"],
}

def audit_rules(doc: str) -> dict:
    gaps = {}
    for dim, keywords in DIMENSIONS.items():
        missing = [k for k in keywords if k not in doc]
        if missing:
            gaps[dim] = missing
    return {"status": "PASS" if not gaps else "GAPS", "gaps": gaps}

# 演示:一份不完整的规则(缺"开发边界"与"安全检查")
partial = """
技术栈:Python + FastAPI
工作方式:先 plan 再动手,最小输出
代码规范:不硬编码,函数粒度适中
自检验证:写完先自测,核心逻辑加测试
"""
r = audit_rules(partial)
print(f"检查结果: {r['status']}")
for dim, missing in r["gaps"].items():
    print(f"  - {dim} 缺少: {', '.join(missing)}")
```

## 实践 / 应用:设计原则与使用流程

!!! tip "规则设计五原则"
    1. **从对话记录挖掘,不凭空写**:跑一遍历史对话,摘出你反复强调的指令——那些才是真正的痛点;
    2. **去掉项目特有配置,保留通用部分**:规则要能跨项目复用,项目差异放开头(项目目标/技术栈)由使用者填;
    3. **边界要写"怎么办",不只写"不许"**:"不要硬编码"不如"不允许硬编码;若必须写死,注释标注并说明原因";
    4. **按项目裁剪**:小项目只需要前面几条;项目越大,规则越全的优势越明显;
    5. **改规则前先备份**:尤其是有一定进度的项目,或新项目使用前。

**使用流程**(三步):复制 `AGENTS.md` 到项目根目录 → 修改开头项目目标和技术栈(或让 AI 填、你检查)→ 告诉 AI"先读它再干活"。

## 总结

- **六维度**:开发基础(技术选型)、工作方式(先方案后代码)、开发边界(该做/不该做/怎么办)、代码规范(质量约束)、自检验证(完成的标准)、安全检查(可回滚基线);
- **核心原则**:不要一次性给代码,先给方案;边界要写"怎么办";验证写进规则,"完成"才有客观标准;
- **价值**:把"反复调教 AI"的一次性劳动,变成一次固化、全项目复用的规则资产——AI 第一次进项目就知道边界在哪、怎么干活、什么时候该停下来问。
