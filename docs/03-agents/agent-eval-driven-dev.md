# 评估驱动开发(EDD):把评估变成 Agent 开发流程的一部分

> **一句话摘要**:Agent 开发最痛苦的事不是调 prompt、选模型,而是**评估**——改了提示词、换了模型、加了工具,到底变好还是变坏?本文提炼"评估驱动开发(EDD)"的基础方法论:评估与真实使用的鸿沟、生产 traces 是金矿、验证器要防作弊、以及"评估 = 训练目标 + 回归测试集"的持续学习闭环。
>
> **来源**:综合公开资料,基于《LangChain 刚开源了个 Eval Engineering Skill》(seebin,https://mp.weixin.qq.com/s/HpejKK3-rbYbqPmG3RuB-Q)提炼;配套 Skill 收录见 [Eval Engineering Skill](../07-agent-coding/skills/eval-engineering-skill.md)

## 概念:为什么评估是 Agent 开发的头号难题

!!! warning "核心痛点"
    改 prompt → 变好还是变坏?换模型 → 新版本更强?加工具 → 进步还是退步?**你心里没底。** 不是不想评估,是手写评估太累,而且写出来的东西经常和真实场景对不上。

Agent 开发者的三个典型痛点:

1. **评估与真实使用脱节**:精心设计的测试用例,生产环境里根本不会出现;真正出问题的场景,测试又没覆盖到;
2. **生产 traces 藏着金矿却难开采**:Agent 每次运行都留下轨迹(工具调用了什么、返回了什么、哪里出错),但很难把这些信息转成系统性测试;
3. **改完无法快速验证**:换模型/调 prompt/加工具后,靠感觉不行、手动测试太慢。

## 原理 1:评估的"鸿沟"——测试为什么对不上生产

手工设计测试的假设是"我了解用户怎么用";但生产环境里用户的实际用法、Agent 翻车的位置,开发者并不真正知道。**测试与生产之间的鸿沟,是评估失真的根源。**

!!! tip "解法方向"
    让评估**从真实数据出发**而不是从猜测出发:读代码仓库搞清 Agent 结构 + 分析生产 traces 还原真实行为——用"真实发生的事"替代"我猜会发生的事"。

## 原理 2:生产 traces 是评估的金矿

Agent 的每次运行轨迹(工具调用参数、返回结果、错误信息)是**最真实的训练与测试素材**:

- traces 记录了 Agent 在真实环境中的行为(哪些工具被调用、参数是什么、哪里失败);
- 从中提取**真实场景的输入-输出对**,生成与生产一致的测试用例;
- 这比手工编写更贴近真实——**"用户怎么用、Agent 在哪翻车",都在 traces 里**。

## 原理 3:验证器(Verifier)要防作弊

评估的核心组件是**验证器**——判断任务是否真正完成。团队发现反直觉的事实:**最好的评估几乎都经过多轮反馈**;验证器第一版特别容易被 Agent 钻空子:

| 典型作弊方式 | 说明 |
| --- | --- |
| **过度引用无关文档刷分** | 检索型任务里引用大量无关资料,靠"有引用"得分 |
| **假装完成动作** | 声称做了某操作,实际没有执行 |
| **利用暴露的答案走捷径** | 评估把答案泄露在上下文里,Agent 直接抄 |

**修复方法**:同时看 **Agent 的运行轨迹**和**验证器的运行轨迹**,快速定位"验证器被钻空子的点",然后修正——评估本身需要迭代打磨。

## 原理 4:持续学习闭环——评估成为开发流程的一部分

!!! tip "核心闭环"
    ```
    生产 traces(真实问题)
      → 转化成评估测试
      → 测试驱动 Agent 改进
      → 再跑评估验证
      → (回到 traces)
    ```
    评估不再是上线前的临时检查,而是**开发流程的一部分**——每次迭代都从真实数据里挖出问题,用标准化评估锚定改进方向。**闭环的两个支撑设计**:

1. **评估 = 训练目标 + 回归测试集**:改进的方向由评估锚定,历史评估集防止"修 A 坏 B";
2. **环境容器化**:模型、提示词、工具版本可随意替换对比——信号更干净、迭代更快。

## 原理 5:Trace 诊断——诊断 Agent 的最低技能

!!! tip "来自产品实战的判断"
    对 Agent 表现不满意时,第一个动作是**进 Trace 看每个选择**,然后问自己:**"这个玩意儿给我这些信息,我能不能判定明白?你判定不明白,它就也判定不明白。"**

- **Trace 是 Agent 的 X 光片**:完整记录每一步的模型输入/输出、工具调用与结果、上下文变化——不看 Trace 的"优化"都是猜;
- **诊断的两个追问**:①哪些信息已经给了它但没说清(我判定不明白 → 它更不明白);②有哪些信息**隐含在业务里但没显式给它**——"其中的哪些信息、如何给 AI",是产品/工程师长期奋斗的工作;
- **需要的最低技能**:能看懂 Trace 日志、理解上下文是怎么被压缩的、看工具调用为什么失败——**不是写算法,而是诊断 Agent 行为**;
- **收敛路径**:观测 Trace → 分析每个选择的效果 → 收集 **Bad Case** → 收敛成可优化的**黄金链路**(与 [数据飞轮](agent-evaluation.md) 和上文闭环完全一致)。

!!! note "与相关概念的边界"
    - **评估驱动开发(本文)**讲"把评估嵌入开发循环"的实践方法论;
    - [Agent 评测](agent-evaluation.md)(美团方法论)讲"评测体系怎么设计"(Rubric/人机一致/数据飞轮)——两者互补:方法论给原则,EDD 给开发流程;
    - [WorkBuddy Bench](workbuddy-bench.md) 讲"完成度怎么验收"——EDD 是它的开发期落地形态;
    - [Agent 持续进化](agent-continuous-evolution.md) 讲"从轨迹学习"——traces → 评估 → 改进正是持续进化的第一步。

## 实践 / 应用:落地 checklist

1. **先采 traces 再写测试**:评估用例优先从生产 traces 提取,而不是凭经验编写;
2. **验证器要防作弊**:测试你的验证器——故意用三种作弊方式跑一遍,看它能不能识破;
3. **评估要迭代**:第一版评估必然有漏洞,把它当代码一样 review 与打磨;
4. **容器化环境**:Dockerfile 定义可复现环境,模型/提示词/工具可替换对比;
5. **评估进 CI/流程**:每次迭代(改 prompt/换模型/加工具)都必须跑评估,用"回归测试集"防退化;
6. **用数据说话**:记录每次迭代的评估指标变化(hill-climbing),而不是靠感觉。

!!! tip "工程收益的实证"
    LangChain 在 Terminal-Bench 2.0 上光靠调 harness(提示词/工具/编排策略)+ 评估驱动,拿到 **13.7% 提升**,没换模型、没做微调——**"更好的 harness engineering + 评估驱动"本身就是可观的性能杠杆**(呼应 [Harness 工程](ai-infra-layering.md) 的"模型商品化、Harness 是竞争力")。

## 总结

- **评估是 Agent 开发的头号难题**:测试与生产脱节、traces 难转化、改完难验证;
- **评估从真实数据出发**:读代码仓库 + 分析生产 traces,用真实行为替代猜测;
- **验证器要防作弊**:过度引用、假完成、走捷径是三种典型钻空子方式,评估需多轮迭代;
- **持续学习闭环**:traces → 评估 → 改进 → 再验证;评估 = 训练目标 + 回归测试集,环境容器化;
- **工程启示**:评估驱动 + Harness 优化是独立于模型/微调的性能杠杆。
