# 如何设计一个 Agent 系统:5 个决策与一套能跑的实现

> **一句话摘要**:市面上的 Agent 资料两极分化——不是"接 API 调个循环"的玩具教程,就是某个框架的使用文档,中间缺的是**设计决策层**。本文用 Coding Agent(工具链最重、反馈最直接、风险最典型的 Agent 类型)串起五个设计决策:模型路由、循环、工具、闭环、安全——每个决策先讲通用原则,再给落到代码和参数的实现,并原样记录四处"被实践修正"的弯路。
>
> **来源**:微信公众号「带你实践的」《如何设计一个 Agent 系统:5 个决策,一套能跑的实现》,https://mp.weixin.qq.com/s/gWgBZ5lxRe57TbpfOaO6sQ;原始资料存档于 `docs/inbox/agent-5-decisions-source.md`

## 概念:为什么自建 Agent,以及四层架构

### 企业自建的三个理由(通用工具的共性短板)

| 问题 | 表现 |
| --- | --- |
| **成本结构不可控** | 通用工具按 token 计费且模型不可选——简单任务和复杂任务打到同一个最贵的模型上("用大炮打蚊子") |
| **数据出不去** | 代码、客户对话、经营数据要发到第三方(往往海外)服务器,保密团队天然犹豫 |
| **闭环断在最后一步** | 通用工具只做到"生成结果":代码写完要你部署、草稿拟好要你发送、报表生成要你归档——Agent 和你的基础设施是两套 |

自建价值就落在这三点:**成本可路由、数据留在自己基础设施、闭环接到自己的系统**。

### 四层架构 + 贯穿安全 = 五个决策

```
大脑(模型层)    → 决策一:单一供应商还是多模型路由
循环(编排层)    → 决策二:回答一次还是迭代到验证通过
手脚(工具层)    → 决策三:能力边界和权限边界怎么一起画
闭环(落地层)    → 决策四:最后一公里怎么接进你的基础设施
安全(贯穿四层)  → 决策五:不是第五个决策,是前四个的约束条件
```

## 原理:五个设计决策

### 决策一:模型——单一供应商还是多模型路由

**通用原则**:不同任务对模型能力要求差别极大;生产级系统按任务特征路由到不同模型,**接入层要协议兼容,保证供应商可随时更换**(模型市场不断洗牌,锁死单一供应商的系统会跟着供应商一起过时——用 API 同时兼容 Anthropic 和 OpenAI 协议,换供应商不改一行接入代码)。

**三条路由路线的权衡**:

| 路线 | 结论 | 理由 |
| --- | --- | --- |
| 让模型给任务打分再路由 | ❌ 出局 | 多一次模型调用(延迟+成本);打分结果不稳定,无法复现调试 |
| 写死规则路由 | ✅ 采用 | 可预测、可调试、零开销——"笨"但可靠 |
| 完全用户手动选 | ✅ 兜底 | 逃生舱:任何自动规则都可能判断错,必须留手动覆盖口 |

**规则路由三条**(按顺序判断,命中即停):

```python
REASONING_KEYWORDS = ["架构", "重构", "设计方案", "性能优化", "排查"]

def route_model(task: str, file_count: int, plan_steps: int, override: str | None) -> str:
    if override:                                     # 规则 1:显式指定(逃生舱)
        return MODEL_MAP[override]
    hit = any(k in task for k in REASONING_KEYWORDS)
    if hit and (file_count > 5 or plan_steps > 8):   # 规则 2:关键词 + 规模(且,不是或)
        return "z-ai/glm-5.2"                        # 推理档
    return "deepseek/deepseek-v4-flash"              # 规则 3:默认日常档
```

!!! tip "避开'为了路由先问一次模型'的鸡生蛋问题"
    首轮计划生成之前拿不到 `plan_steps`——所以实际顺序是:首轮统一用日常档生成计划,计划出来后步骤数超阈值,从第二轮起升档。

### 决策二:循环——回答一次还是迭代到验证通过

**循环的第一性原理是可验证**:模型的每一步判断必须建立在**真实的执行反馈**上,而不是它自己的想象上("我觉得应该对了"是 Agent 翻车的第一大原因)。代码报没报错、订单查没查到,都要原样回传给模型。循环要回答三个问题:

**① 什么时候算完成(双保险终止)**:
- **成功终止 = 验证命令通过**:每个任务在计划阶段必须声明机器可判定的验证命令(`pytest tests/`、`npm run build`、`curl` 健康检查),返回 0 即结束;**不允许没有验证命令的任务进入执行阶段**(硬条件)——逼着 Agent 把"完成了"定义成机器可判定的东西;
- **强制终止(三道熔断)**:最大迭代 30 轮(完成率与成本平衡);连续 3 轮无进展熔断(同一文件反复改同一处/同一报错反复出现→原地打转);单任务 token 预算(超了直接停)。

**② 失败了怎么办(三类失败三种策略)**:

| 失败类型 | 例子 | 策略 |
| --- | --- | --- |
| 环境瞬时错误 | 网络闪断 | 直接重试 |
| 代码逻辑错误 | 测试失败 | 带**完整报错**重试——原样回传 traceback 不做摘要("测试失败,共 3 个用例未通过"剥夺了模型定位问题的全部原料,完整 traceback 才是让它一轮定位的东西) |
| 计划性错误 | 方案走不通 | 重新规划;同一步骤改代码重试 2 次仍失败 → 升级为计划性错误 |

**③ 长任务怎么不失忆(上下文三层压缩)**:
- **工具结果分级保留**:最近 3 轮全量;更早轮次成功调用压成一行、失败保留报错摘要——越近越完整,失败优先于成功;
- **计划置顶**:任务原始描述、当前计划、每步状态永远固定在上下文最前面不压缩——**Agent 最致命的失忆不是忘了细节,是忘了自己在干嘛**;
- **文件内容不进历史**:只留"读过 auth.py(412 行)"的记录,需要时再重读——文件是可随时再取的外部状态,这条省的 token 最多。

### 决策三:工具——能力边界和权限边界要一起画

!!! warning "两条铁律"
    1. **每接一个工具,同步回答它的权限问题**(自动执行/人工确认/直接禁止)。"先接工具再补权限,补权限的那天一般是出事的那天。"
    2. **工具保持愚蠢,智能留给模型**——工具层替模型摘要、替模型判断的每一处小聪明,都会变成模型判断失准的盲区。

工具层四类能力(文件系统/代码执行沙箱/Git/部署),权限细节:

| 工具 | 权限边界 |
| --- | --- |
| 文件系统 | 读写限定项目根目录内;`.env`、密钥文件、系统路径默认拒绝 |
| 代码执行沙箱 | Docker 隔离,一个任务一个容器,任务结束即销毁 |
| Git | 经沙箱执行,强制推送判为高危命令拦截 |
| 部署 | 见决策四 |

**沙箱完整规格**(Docker,默认断网是最大杀手锏——绝大多数跑代码/跑测试不需要网络,混入外传数据逻辑时断网是最后保险):

```bash
docker run --rm \
  --network none \          # 默认断网;装依赖走内部镜像源白名单网络
  --memory 2g --cpus 2 --pids-limit 256 \
  --read-only \             # 只读根文件系统
  --tmpfs /tmp:size=512m \
  -v /workspace/task-{id}:/workspace:rw \
  --user 1000:1000 --security-opt no-new-privileges \
  niuma-sandbox:latest \
  timeout 300 bash -c "{command}"   # 超时宁短勿长:超时痛苦显性,跑飞成本隐性
```

!!! warning "胖镜像不是可选项,是必选项"
    一次把常用运行时(Python/Node/Go/JDK)装够(约 2GB)。反面教材是按语言拆小镜像——任务常跨语言,切换复杂度大于省下的磁盘。实测撞坑:镜像缺 pytest,模型想 `pip install pytest`,但在 `--read-only + --network none` 容器里装依赖行不通,只能改用 unittest 重写测试——**沙箱越严,镜像越要一次装够**。

工具侧封装很轻量:沙箱只暴露一个 `run_command(command)`,返回 `{exit_code, stdout, stderr}` 三元组,零加工。

### 决策四:闭环——你的 Agent 的最后一公里

每个领域都有一条通用工具到不了的最后一公里(通用 Coding 工具停在"代码写完测试通过",部署人工;通用客服工具停在"回复拟好",发送和工单流转人工)。**自建 Agent 最大的价值,是把这最后一公里接进你自己的基础设施**。设计这一层要想三件事:**生效动作失败怎么回退、不同环境怎么隔离、Agent 在这一层该有多大权限**。

牛码的最后一公里是部署(Kodo 对象存储版本化上传 + 切 current 指针 + 刷新 CDN,用户拿到一个链接而不是一堆文件):

1. **回滚:版本化切指针,不做撤销**——上传不覆盖旧文件,按版本号写独立前缀(`releases/v20260715-1432/`),`current` 指针指向某个 release;上线 = 切指针 + 刷新,回滚 = 切回上一版 + 刷新,不需要重新构建;健康检查失败自动回滚,**但"回滚之后再试一次"必须由人决定**(否则出现"部署-失败-回滚-再部署"死循环);
2. **多环境:物理隔离,不靠参数**——测试和生产不共用 bucket/云主机/密钥;区分环境不依赖 `--env prod`(参数会写错、会被模型幻觉),靠**凭证本身的权限边界**:拿着测试环境的 key,物理上碰不到生产资源;
3. **权限:生产的钥匙从头到尾不在 Agent 手里**——部署工具默认配置只有测试环境凭证;生产发布走独立流程:Agent 完成测试环境部署验证后生成发布请求(版本号/变更摘要/验证结果)→ 人在控制台确认 → 平台侧持有生产凭证的独立服务执行同样的切换动作。**凭证隔离防的是模型被提示注入、被诱导之后的恶意操作**(二次确认只防误操作)——安全要按最坏情况设计:假设模型某一天会被外部输入操纵,你的架构还能不能兜住。

### 决策五:安全——不是第五个决策,是前四个的约束条件

上线后再补的安全都是筛子。五条不分领域的底线:

1. **密钥集中托管,不下发到终端**(API Key 散落在每个开发者本地,泄露只是时间问题);
2. **敏感资源默认拒绝**(黑名单保护密钥文件、生产配置、客户隐私数据);
3. **高危操作二次确认**(删除、外发、资金变动类,自动化止步);
4. **生产与测试物理隔离**(靠凭证权限边界,不靠参数);
5. **全量审计日志**——每条工具调用记一行 JSON,同时就是成本账本:

```json
{"ts": "2026-07-15T14:32:01+08:00", "task_id": "t-8891", "step": 7,
 "tool": "run_command", "args_digest": "pytest tests/ -x", "exit_code": 1,
 "duration_ms": 4210, "model": "deepseek/deepseek-v4-flash",
 "tokens": {"in": 8412, "out": 356}}
```

两个设计点:`args_digest` 对超长参数只存摘要/哈希(日志不能变成第二个代码副本);每条带 `model` 和 `tokens`——**审计日志同时是成本账本**,事后追溯"这个任务为什么花了这么多钱"不用查第二个系统。

## 代码 / 实现:路由 + 审计成本聚合(纯 Python)

原文的 `route_model` 与审计日志设计,落成可运行验证:

```python
REASONING_KEYWORDS = ["架构", "重构", "设计方案", "性能优化", "排查"]
MODEL_MAP = {"thinking": "z-ai/glm-5.2", "daily": "deepseek/deepseek-v4-flash"}

def route_model(task, file_count, plan_steps, override=None):
    if override:
        return MODEL_MAP[override]                                  # 逃生舱
    hit = any(k in task for k in REASONING_KEYWORDS)
    if hit and (file_count > 5 or plan_steps > 8):                  # 关键词 AND 规模
        return "z-ai/glm-5.2"
    return "deepseek/deepseek-v4-flash"

# 审计日志 = 成本账本:按任务聚合 token 与耗时
def aggregate_cost(logs: list[dict]) -> dict:
    total_in = sum(l["tokens"]["in"] for l in logs)
    total_out = sum(l["tokens"]["out"] for l in logs)
    return {"tasks": len(set(l["task_id"] for l in logs)),
            "calls": len(logs), "tokens_in": total_in,
            "tokens_out": total_out, "total_ms": sum(l["duration_ms"] for l in logs)}

log = [
    {"task_id": "t-8891", "tool": "run_command", "args_digest": "pytest -x",
     "exit_code": 1, "duration_ms": 4210, "tokens": {"in": 8412, "out": 356}},
    {"task_id": "t-8891", "tool": "run_command", "args_digest": "pytest -x",
     "exit_code": 0, "duration_ms": 3800, "tokens": {"in": 9012, "out": 402}},
]
print(route_model("重构登录模块", 8, 3))        # 关键词命中 + 文件数>5 → 推理档
print(route_model("加个按钮", 1, 2))             # 无关键词 → 日常档
print(route_model("加个按钮", 1, 2, override="thinking"))  # 逃生舱
print("任务 t-8891 成本:", aggregate_cost(log))
```

## 实践 / 应用:被实践修正的四件事(最值钱的弯路)

!!! tip "设计方案在纸上永远是完美的,价值在于它被现实修正的那些地方"
    1. **三档路由简化为两档**(设计阶段自我否决):简单快速任务用小模型——但补全/格式化这类任务在 Agent 循环里占比极低(被 IDE 处理了),单独维护一档的复杂度和收益不成正比;
    2. **复杂度打分出局**(设计阶段自我否决):看似更智能,推演到调试(不可复现)和成本(额外调用)层面就站不住;
    3. **连续 3 轮无进展熔断一次都没触发过**(实践打脸):判定逻辑是"工具调用与结果签名完全相同",但模型每轮都换个小花样(加 `-v`、加 `echo`、换目录),签名轮轮不同,检测器眼睁睁看它转圈,最后靠最大轮数兜底——**相似度判定过严等同于形同虚设**;
    4. **"运行时装依赖"在断网只读沙箱里彻底行不通**(实践打脸):胖镜像不是可选项,是必选项。

**留下来的部分**(被实测反复验证):循环吃真实反馈、工具保持愚蠢;生产凭证不进 Agent 仍属设计原则(本次无生产环境可验)。

## 总结

- **五个决策**:模型路由(规则先行+手动兜底,协议兼容不锁死)、循环(可验证第一性原理+双保险终止+三类失败+三层压缩)、工具(权限同步+愚蠢工具+默认断网沙箱)、闭环(版本化切指针+凭证隔离+生产钥匙不在 Agent 手里)、安全(五条底线+审计日志即成本账本);
- **三条铁律**:验证命令是硬条件(不允许无验证任务进入执行)、工具保持愚蠢智能留给模型、安全按最坏情况设计(假设模型会被外部输入操纵);
- **最值钱的是被修正的地方**:两个设计阶段自我否决、两个被实践打脸——这些弯路可以直接跳过;
- **一句话**:Agent 系统的设计决策层,决定了它是在"能干活"和"能出事"之间走哪边。
