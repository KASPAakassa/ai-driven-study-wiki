# WorkBuddy Bench:Agent 的"完成"该由什么来证明?

> **一句话摘要**:腾讯 WorkBuddy 团队论文提出的 Agent 评测协议——不满足于"修 Bug 通过测试",而是检验 Agent 是否真正**完成一项工作**:在完整工作区里留下可用的交付物、让相关状态一致、并给出可复核的证据。本文提炼其四层完成度、任务设计、四个赛道与"五份合同"方法。
>
> **来源**:微信公众号「架构师 JiaGouX」《腾讯 WorkBuddy 团队论文:如何从"修 Bug"走向"完成工作"》(若飞),https://mp.weixin.qq.com/s/BqRjAd27bT17pMUbAGtmsg;官方仓库 https://github.com/Tencent/workbuddy-bench

## 概念:什么是"假完成"

研发里常见的"假完成":

> Agent 找到一条失败测试,改了几行代码,目标用例也绿了。第二天联调才发现,跨时区订单还没覆盖;接口少了一个兼容字段;发布说明引用的还是旧配置。**它确实修了一个 Bug,却没有把这项工作交到下一个人手里。**

这种错位不只发生在代码里:月度分析写完了但工作簿没更新;架构方案讲得很顺但迁移顺序和回滚条件没落下来;行程看起来很完整但时间冲突、预订状态和预算仍散在聊天记录里。

!!! note "定位:补上"验收端""
    Prompt、Context、Harness、Loop、Graph 管的是 **Agent 怎样运行**;WorkBuddy Bench 追问的是:**运行结束以后,留下的东西够不够支持"完成"这个结论**——它补的是验收端。

## 原理:四层完成度与评测协议

### 四层完成度:回答 ≠ 完成

| 层次 | 看到了什么 | 还缺什么 |
| --- | --- | --- |
| **回答** | 一段解释、方案或代码片段 | 没有进入真实工作区 |
| **动作** | 改了文件、调用了工具 | 不确定结果是否完整 |
| **交付** | 留下补丁、网页、报表或 PoC | 还要核对状态与约束 |
| **完成** | 交付物可用、相关状态一致、证据可复核 | 可以进入交接、发布或下一步 |

**代码写完只说明实现动作结束**;能不能进入下一阶段,还要看 CI、接口兼容、数据迁移和发布检查。Agent 有没有完成,最后要看**工作区里留下了什么变化**。

### 任务设计:题目要像工作

- 不直接复用公开 Issue 标题/描述,而是从**历史 commit、PR、真实 CVE 或业务场景**反向还原任务,改写成同事间的短请求;
- Code 任务会换成**开发、算法、产品、QA、运维五种角色**提需求;请求保留目标与约束,但省略目标文件、根因、参考 diff、字段结构和部分边界条件;
- 原则:**请求可以留白,工作区不能没有线索**——缺少的信息如果既不在请求里,也不在代码/数据/文档/接口中,Agent 只能猜,评测就失去稳定依据;
- 隐私:**借的是任务分布,不是生产会话本身**(原始 Prompt 与用户数据不进入公开任务)。

### 任务封装:现场要能回放

每项任务按统一目录封装:

```
task/
├── instruction.md   # 自然语言请求
├── task.toml        # 类别、难度、资源与超时
├── environment/     # Docker 与 Agent 可见的工作区
├── tests/           # 任务结束后执行的评测资产
└── gold.patch       # Code 任务可选的诊断参考
```

固定了关键边界:起点(从哪个版本/文件/状态开始)、可见范围(哪些评测资产求解期间不可见)、工具与资源、结果写入位置、验收程序。与研发流程的对应:instruction.md = 需求卡,task.toml = 执行策略与资源限制,environment/ = 固定版本环境,tests/ = CI/验收规则,results/ = 构建产物与发布证据。

## 四个赛道:Code / Web / Office / Security

| 赛道 | 规模 | 工作现场 | 如何验收 |
| --- | --- | --- | --- |
| **Code** | 80 任务 / 18 细类 | 代码仓库,5 种角色提需求(34 个真实 commit 快照 + 24 个 clean-room + 22 个合成) | 契约测试等确定性检查;任务进公开集前先跑两次验证(基线 ≤0.3、"什么都不做也能过";gold patch 后必须 1.0) |
| **Web** | 70 任务 | 声明路径下留下**可运行前端工件** | 三类评分:规则检查(文件/格式/可执行测试)、LLM/VLM 判断(文本/结构/视觉语义)、Agent Judge 实际操作(流程/状态变化/持久化) |
| **Office** | 50 任务 | xlsx/csv/pdf/文档/JSON/Markdown 混合办公文件 | 验收**最终工作区一致性**:确定性规则(0.70~0.95 权重)检查文件/字段/数值/跨文件关系 + LLM Judge 评估语义条件 |
| **Security** | 60 任务(38 红队 + 22 蓝队) | binutils/curl/nginx/vim 等真实历史 CVE | 发现线索→定位原因→安全复现→**留下 PoC 证据**;全确定性程序评分,无 LLM Judge,五层反作弊检查 |

!!! warning "典型失败模式(来自 Code 赛道)"
    - Agent 一直修改测试文件直到超时;
    - Agent 在大仓库里迷路,改了无关模块;
    - 语义大体正确但遗漏必需字段/参数形状/输出格式——`bug_fix` 和 `api_contract` 平均分仅 0.47,而 `feature_pipeline` 0.94、`testing` 0.88。**"卡住的往往不是那几行代码,而是没找到负责该行为的模块、没读懂现有接口契约。"**

### 与其他 Benchmark 的边界

| 项目 | 主要工作现场 | 判断完成的方式 |
| --- | --- | --- |
| SWE-bench | 代码仓库与 GitHub Issue | 补丁通过相关测试 |
| BrowserGym 生态 | 标准化浏览器观察与动作空间 | 各 Web Benchmark 任务指标 |
| OSWorld | 真实桌面、网页与跨应用流程 | 初始状态 + 执行式评测脚本 |
| τ-bench | 用户对话、业务 API 与策略规则 | 最终数据库状态 + 多轮稳定性 |
| **WorkBuddy Bench** | Code / Web / Office / Security 工作区 | 各赛道的**工件、状态与证据** |

作者强调这些项目测的是不同边界,放一张"谁更先进"榜单意义不大;WorkBuddy Bench 的 Code 主要是 Python,Office 是文本/文件优先(不覆盖 OCR、像素级版式或原生桌面 GUI),结论不能直接外推。

## 实践 / 应用:把"完成"的验收带回日常

### 四个日常场景的"假完成 vs 可交付"

| 场景 | 容易出现的假完成 | 更接近可交付的结果 |
| --- | --- | --- |
| 研发 | 目标测试绿了 | 补丁、回归测试、接口兼容、变更说明、未验证边界一致 |
| 架构 | 方案文档写完了 | ADR、依赖、接口、迁移顺序、故障处理和回滚条件能对应 |
| 工作 | 报表和总结生成了 | 原始数据、工作簿、报告、指标口径和状态文件是同一版 |
| 生活 | 行程建议看起来完整 | 日期、路线、预算、预订状态和提醒进入可用的日历/文件 |

### 团队自建 Agent 评测:先写五份小合同

1. **任务合同**:目标、约束和停止点是什么(例:延迟购买不计入本次实验转化);
2. **现场合同**:基线、版本、数据和可见范围是什么(固定 commit、工作簿版本或数据库快照);
3. **动作合同**:能用哪些工具、哪些动作需要审批(可以改分支,不能直接改生产库);
4. **交付合同**:结果落在哪里、格式和状态怎样变化(PR、报表、工作簿、页面入口或安全报告);
5. **验收合同**:用什么规则和证据判断完成(测试、字段检查、跨文件一致性、运行状态)。

### 失败复盘的五类归档(决定下一轮改什么)

- **找错对象**:改了无关文件,或在测试文件里打转 → 补工作区信息;
- **契约遗漏**:行为大体正确,字段/参数/输出格式不完整 → 补接口事实;
- **业务口径错**:代码能跑,时间窗口/状态/归因关系错了 → 补领域事实;
- **交付没落地**:聊天里说完成,约定路径没有成品 → 补交付合同;
- **证据不完整**:发现问题但复现/边界/交接材料不足 → 补验收合同。

### 评测记录要保留的条件

只记录模型名,会把 Harness 差异藏起来——**同一个模型换 Harness,分数会变**(如 GPT-5.5 在 Security 从 cbc 第六升到 cc 第二;HY-3 打开 reasoning passback 后 Code 分数变化)。建议记录:模型 + Harness 版本 + 数据集版本 + 工具权限 + 指令与运行协议。复现流程见官方仓库(`uv sync` → 拉数据集 → 配置 model/job → `uv run ./scripts/run.sh`),结果保存在 `results/`。

## 总结

- **"完成"四层**:回答 → 动作 → 交付 → 完成;完成 = 交付物可用 + 状态一致 + 证据可复核;
- **WorkBuddy Bench** 把"完成"做成可运行、可复现的评测协议:任务像工作(请求留白、工作区给线索)、现场可回放(task 目录封装)、四个赛道按交付物分别验收;
- **与运行侧互补**:Prompt/Context/Harness/Loop/Graph 管运行,WorkBuddy Bench 管验收;"一个管开工前(授权治理),一个管交付后(验收)"——见 [Agent 评测](agent-evaluation.md) 的评测基建思路;
- 日常可复制的最小实践:**五份合同**(任务/现场/动作/交付/验收)+ 五类失败归档。
