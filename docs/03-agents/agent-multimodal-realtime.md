# 多模态与实时交互:语音、Computer Use 与机器人

> **一句话摘要**:Agent 从纯文本走向真实世界,需要三类能力——理解、生成、交互;交互把前两者放进有时间约束、会产生反馈、还会改变环境的闭环。本文基于《深入理解 AI Agent》第 9 章,拆解语音三范式、Computer Use 的截图-动作循环、以及机器人的闭环对照实验法。
>
> **来源**:《深入理解 AI Agent:设计原理与工程实践》第 9 章(李博杰,https://github.com/bojieli/ai-agent-book),全文存档于 `references/ai-agent-book/book/chapter9.md`

## 概念:理解、生成、交互——三类能力的分工

| 能力 | 回答的问题 | 作用 |
| --- | --- | --- |
| **理解** | 能否看懂并想明白(文字/语音/图像/视频 + 推理规划) | 决定"会什么"与智能上限 |
| **生成** | 能否把想法表达出来(文本/代码/图像/视频/语音/动作) | 决定"会什么"与智能上限 |
| **交互** | 能否在持续变化的环境中,在合适时机接收信息、行动、根据反馈调整 | 决定能否把智能转化为**任务结果** |

!!! note "关键认知"
    交互能力与智能上限并不直接相关,但它决定模型能否在真实环境中把已有的智能**稳定转化为任务结果**。一个数学/代码很强的模型,可能无法把实际任务做好——正如人的聪明程度与岗位表现之间的关系。

## 原理 1:语音——最自然的人机接口

语音是带宽最高、最自然的交互方式(说话速度约为打字的 4 倍,不占双手与视线)。两类产品:语音输入法(口述转文字,替代键盘)与语音 Agent(语音即交互本身);进阶用法是 **whisper coding**——口述指挥编程/研究 Agent。

### 语音架构三种范式(OpenAI GPT-Live 给出的三分法)

| 范式 | 结构 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **级联(Cascaded)** | ASR + LLM + TTS 串成流水线 | 简单、首代 ChatGPT Voice | 信息在模型间传递丢失,回应缓慢生硬 |
| **端到端全模态(Omni)** | 单一模型"听-想-说" | 延迟更低,保留韵律与情感 | 仍是"轮流说话",靠静音判断轮次,停顿/噪音易误判 |
| **全双工(Full-Duplex)** | 边听边说,同时处理 | 自然打断、实时对话 | 架构复杂 |

### 语音的实时性挑战:延迟瀑布与排队论

- **串行延迟累积**:VAD(500-800ms)+ ASR(50-200ms)+ LLM TTFT(100-500ms)+ 生成短句(100-300ms)+ TTS(200-500ms)≈ **0.95-2.3 秒**;开启 reasoning 时首 token 等待可能 5-10 秒;
- **排队延迟**:总延迟 ≈ 空载延迟 × 1/(1-利用率)——利用率 50% 延迟 2 倍,80% 延迟 5 倍;服务器不能长期高负载运行;
- 优化方向:流水线并行(VAD/ASR 期间 LLM 提前思考)、后台深度思考与前台实时交互分工。

## 原理 2:Computer Use——GUI 自动化 Agent

把交互闭环具体化为 **"截图 → 动作 → 新截图"**:

```
持续感知(截图/可访问性树)
  → 判断当前状态与时机
  → 选择动作(点击/输入/滚动)
  → 执行并观察新截图
  → 继续、修正、重试、停止或重新规划
```

**关键变化**:瓶颈已从"能否完成任务"扩展到**操作效率、连续视觉理解、状态确认**——一次点错、界面变化未察觉、异步加载未等待,都会让 Agent 迷路。可访问性树(Accessibility Tree)与截图互补:前者给精确控件信息,后者给视觉上下文。

## 原理 3:机器人操作——以 XLeRobot 整理桌面为例

把同一闭环放进物理世界,用**五个连续实验**建立可比较的方法论:

1. 真机遥操作:建立"人类执行"上限;
2. 模拟理想控制:建立"理想闭环"上限;
3. 真机自主控制:测量 Agent 实际表现;
4. 模拟策略对照:隔离"模型策略"与"物理执行"的差距;
5. (对照)归因:区分瓶颈在感知、策略还是执行。

!!! tip "方法论价值"
    先建立人类与理想闭环的上限,再测量 Agent 与上限的差距——这套"对照实验"思路适用于任何多模态/物理交互 Agent 的评估。

## 代码 / 实现:交互闭环与延迟计算

原文为方法论章节。下面用纯 Python 演示"交互闭环的延迟瀑布估算"(判断实时语音系统是否达标):

```python
def pipeline_latency(vad=0.65, asr=0.15, ttft=0.25, gen=0.2, tts=0.3, parallel=False):
    """语音串行 vs 并行流水线的总延迟(秒)
    parallel=True: VAD/ASR 期间 LLM 提前开始思考,部分重叠
    """
    if not parallel:
        return vad + asr + ttft + gen + tts
    # 并行:LLM 的 TTFT 与 ASR 重叠,只计一次最长的链
    return max(vad + asr, ttft) + gen + tts

def queued_latency(idle_latency, utilization):
    """排队论:总延迟 ≈ 空载延迟 / (1 - 利用率)"""
    return idle_latency / (1 - utilization)

serial = pipeline_latency(parallel=False)
overlap = pipeline_latency(parallel=True)
print(f"串行流水线: {serial*1000:.0f} ms")
print(f"流水线并行: {overlap*1000:.0f} ms (节省 {serial-overlap:.2f}s)")
for u in (0.5, 0.8, 0.95):
    print(f"利用率 {u:.0%}: 延迟变为 {queued_latency(serial, u)/serial:.1f} 倍")
```

**运行结果**:串行约 1.55s,流水线并行约 1.0s;利用率 80% 时延迟 5 倍、95% 时 20 倍——解释了为什么实时语音系统既要并行化流水线,又不能让服务器长期高负载。

## 实践 / 应用:落地要点

1. **先分清瓶颈在"理解/生成"还是"交互"**:交互能力与智能上限正交,别用更强的模型掩盖交互架构缺陷;
2. **语音选型**:延迟敏感用 Omni/全双工,简单场景级联即可;优化流水线并行 + 控制利用率;
3. **Computer Use 注意状态确认**:等待异步加载、检查动作是否生效、用可访问性树 + 截图双通道;
4. **物理/多模态评估用对照法**:先建上限(遥操作/理想模拟),再测差距(自主/策略对照);
5. **与多 Agent 结合**:多模态交互闭环可作为子 Agent 的专业能力(视觉 Agent、语音 Agent)。

## 总结

- 三类能力:**理解/生成决定智能上限,交互决定能否转化为任务结果**;
- 语音三范式:级联 → Omni(轮流)→ 全双工(边听边说);实时性受延迟瀑布与排队论约束;
- Computer Use = "截图-动作-新截图"闭环,瓶颈在操作效率、连续视觉与状态确认;
- 机器人/物理交互用"对照实验"方法:先定上限,再量差距;
- 共同主线:**持续感知 → 判断时机 → 选择动作 → 进入环境 → 观察反馈 → 修正/重试/重规划**。
