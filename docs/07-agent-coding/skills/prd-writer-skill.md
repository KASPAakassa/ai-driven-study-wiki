# prd-writer:用 AI 写 PRD 需求文档——全栈工作者的"人人都是产品经理"抓手

> **一句话摘要**:人人都是产品经理——全栈工作者自己写需求,是把 Agent Coding 做好的关键前置。prd-writer 是 VibePM 工作流里开源的 AI PRD 写作技能(MIT 协议):把产品经理的分阶段思维变成 **AI 必须遵守的门禁**——不是一次性输出长文,而是按步骤交付、逐步确认:先验证方向 → 概念版对齐 → 落地版展开 → 写后自检。核心能力:三视角诊断、分两版交付、MVP 闸门、补全盲区、先读再写。
>
> **来源**:微信公众号「VibePM」《用 AI 写 PRD 需求文档,别再「一稿到底」:prd-writer 技能开源分享》,https://mp.weixin.qq.com/s/N97KwQ9QxFoqX1ihqL5BGw;GitHub https://github.com/vibepm666/prd-writer;原始资料存档于 `docs/inbox/prd-writer-source.md`

## 概念:为什么全栈工作者需要自己写需求

**AI 写 PRD 的最大坑**:不是写不出来,而是**写得太快、太满、方向未对齐细节已固化**——方向没对齐就堆细节,写完才发现走不通;文档很长但研发和设计仍反复追问。

**prd-writer 的定位**:专为产品经理、创业者及技术负责人设计的 AI PRD 写作助手,也是 VibePM 工作流里的"PRD 撰写与迭代"技能。适用场景:从零写 PRD、评审已有需求稿、在现有 PRD 里追加模块而不改乱原文。它**不替代人的思考**,而是作为"副驾驶"——通过引导式交互和结构化扩展,把模糊想法快速转化为逻辑严密、格式规范的高质量 PRD 草案。

!!! tip "对全栈工作者的意义"
    本质上**人人都可以是产品经理**——需求自己也可以写。对全栈工作者来说,自己写 PRD 是 Agent Coding 的**有效抓手**:需求文档是 AI 编码的"上游契约",需求清晰度直接决定 Agent 产出质量。prd-writer 让"写需求"这件事从"只有 PM 会"变成"任何人可上手"。

**核心理念**:把 PM 的分阶段思维变成 **AI 必须遵守的门禁**——不是一次性输出长文,而是按步骤交付、逐步确认:先验证方向 → 概念版对齐 → 落地版展开 → 写后自检。

## 原理:五种核心能力与三种工作模式

### 五种核心能力

1. **三视角诊断** — 动笔前对齐:用户(痛点真实吗)、商业(值得做吗)、技术(做得出来吗),并推荐产品形态(Web/小程序/App)及理由;
2. **分两版交付** — 标准模式(默认)下**概念版只对齐方向,不展开实现细节**;落地版含动线、§5、状态机、文案、线框图;严格模式下概念版未明确确认不写落地细节("差不多"不算确认);说"快速模式"可合并为单文件;
3. **MVP 闸门** — 落地版默认只展开 🔴 核心功能的 §5;🟡⚪ 仅在清单留名。示例:生鲜超市 App 的 7 个 🔴 模块写全(首页至订单),领券/邀请仅列项,鲜友圈标"不做";
4. **补全盲区** — 交互反馈、空状态、状态机、数据校验、双受众文案(开发规格 vs 用户文案)、关键页线框图,以及按产品类型补充非功能需求;
5. **先读再写** — @ 已有文档或 docs/ 里的 PRD/调研稿会先读、摘录真源,只补缺口,不从零重写。

### 三种工作模式(交付节奏)

| 模式 | 触发 | 行为 |
| --- | --- | --- |
| 标准模式(默认) | 未特别声明 | 概念版对齐方向后写落地 PRD |
| 快速模式 | 说"快速模式"或"直接写 PRD/跳过概念版" | 合并为单文件,方向摘要写文首 |
| 严格模式 | 说"严格模式"或"正式交付" | 须概念版明确确认后再写落地 §5 |

### 产出物

文档写入项目 `docs/` 目录,落地版文首链回概念版;可选:Markdown 落盘后说"PRD 导出 Word",在同目录生成 `.docx` 文件。

## 代码 / 实现:安装与使用

### 安装(最简单方式)

```bash
# 方式一:把链接发给智能体,让它帮你安装
# 在 Cursor 等 Agent 对话里复制:
#   请帮我安装这个技能:https://github.com/vibepm666/prd-writer

# 方式二:手动克隆到技能目录
git clone https://github.com/vibepm666/prd-writer   # 放入个人/项目技能目录
# 个人技能(所有项目可用)vs 项目技能(仅当前项目可用),以 Cursor 为例
```

网络无法访问 GitHub 时用备用下载解压,将整个 `prd-writer` 文件夹放入技能目录即可。

### 三种使用模式

**模式 A · 从零写**:
> 我想做一个城市家庭用的生鲜即时零售 App,强调鲜活品质承诺和极速达配送,请按 prd-writer 流程帮我写 PRD。

Agent 三视角诊断后输出概念版(对齐定位与"不做什么"),确认后再写落地版——含动线、交互状态表、线框图与字段规范。

**模式 B · 评审**:
> 帮我检查一下这份生鲜超市 App 需求文档有没有问题 @docs/2026-06-25-生鲜超市APP-PRD.md

按清单评审动线、状态与验收标准,产出 `PRD-评审.md`,再问直接补全还是自行修改。

**模式 C · 增量**:
> 帮我在现有生鲜超市 PRD 里补充「黄金会员」权益与升级规则 @docs/2026-06-25-生鲜超市APP-PRD.md

定位相关章节融合更新,用 `【本次更新】` 标注,**不覆盖原文**。

**自动触发**:提到"PRD""写需求""审查需求""我想做个 App"等词,Agent 会自动加载本技能;也可手动指定 SKILL.md。

## 实践 / 应用:工作流衔接与站内关系

### prd-writer 工作流门禁

> 读稿 → 模式 A/B/C → 三视角诊断 → 概念对齐(或概念版确认)→ 落地版(MVP 闸门)→ 自检

它是 VibePM 工作流"**文档 → 结构 → 原型 → 测试/手册**"链中的**需求中枢**——产出在 `docs/`,下游读取上一阶段文件衔接。

## 总结

- **定位**:AI PRD 写作助手(副驾驶,不替代思考),把 PM 分阶段思维变成 AI 必须遵守的门禁;
- **核心能力**:三视角诊断(用户/商业/技术)、分两版交付(概念版对齐方向→落地版展开细节)、MVP 闸门(🔴 核心全写、🟡⚪ 留名)、补全盲区(空状态/状态机/双受众文案)、先读再写(增量不覆盖);
- **三模式**:标准(两版)/ 快速(单文件)/ 严格(概念版明确确认);
- **三种用法**:从零写 / 评审 / 增量追加(【本次更新】标注不覆盖原文);
- **对全栈工作者**:人人都是产品经理——自己写需求是 Agent Coding 的有效抓手,需求文档是 AI 编码的上游契约;
- **下一步**:PRD 产出后接 [Spec-First](spec-first-skill.md)(scope 锁定)或 [SDD](sdd-openspec-superpowers.md)(规格驱动),形成完整闭环。
