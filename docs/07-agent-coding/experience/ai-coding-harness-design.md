# AI Coding Harness 设计经验:护栏怎么长出来

> **一句话摘要**:Vibe Flowing(腾讯 AI 原生研发团队实践)最值得复用的不是它的功能,而是**护栏怎么设计、怎么生长**。团队里每个人不需要一上来就理解 Prompt Engineering、Harness、Agent Loop 这些概念——**真正 ROI 最高、见效最快的方式,是先让 AI Coding 运转起来,再让护栏随着实际需求逐步生长出来**。本文把案例里的 Harness 工程实践提炼成可复用的设计模式。
>
> **来源**:微信公众号「腾讯程序员」《从 Vibe Coding 到 AI 原生研发团队:一套能落地的工程实践》(作者:masoncai),https://mp.weixin.qq.com/s/DrIpzHm777Zd8klcyAICBA;完整案例见站内 [腾讯 Vibe Flowing:AI 原生研发团队落地](../../04-practice/ai-native-dev-team-vibeflowing.md);原始资料存档于 `docs/inbox/vibeflowing-source.md`

## 概念:护栏的哲学——先跑起来,再长护栏

!!! tip "核心理念"
    **代码本身就是描述业务逻辑最精确、最高效的语言。** 对大多数人来说,更实际的起点是先学会高质量地使用 AI 完成编码任务,而不是一上来理解所有概念。**让 AI Coding 先运转起来,护栏随实际需求逐步生长**——"让 AI 连续跑一整天"是能力上限,但日常开发是加功能、修 Bug,要守住的是**质量下限 + Token 效率**。

本文聚焦五个可复用的护栏设计模式(全部提炼自 Vibe Flowing 实战)。

## 原理:五个护栏设计模式

### 模式一:Rules 三层护栏(规则集中、分场景加载、不重复)

!!! tip "设计原则一条:规则集中、分场景加载、不重复"
    AI 上下文有限,规则散乱或重复既费 token 又容易让 AI 混淆。三层各管一段:

| 层 | 载体 | 管什么 | 何时加载 |
| --- | --- | --- | --- |
| 工程规范层 | 根目录 `AGENTS.md` | 文件红线、分层规范、前端约定、DB 变更流程、图表配色 | 每次会话(随身"项目规范手册") |
| 流程护栏层 | `.vscode/anydev_rule.md` | 三阶段流程不可绕过、用户非专业开发、分支透明、Git 护栏 | 每次进研发容器自动加载 |
| 记忆层 | 插件 Memory | 高频项目约定("时间字段统一 DATETIME"等) | 相关场景自动触发 |

**关键设计点**:三阶段流程不可绕过(需求讨论→开发实现→确认提交,每阶段需用户确认)——**禁止 AI 自行判断"小改动可以跳过讨论"**;用户非专业开发时"出现技术名词必须白话解释、方案先讲再动手、不让用户做选择题、拿不准就停下来问"。

!!! warning "护栏要防的不是 AI 不聪明,而是 AI 太自信"
    最典型的:用户说"把数据清掉",AI 要主动提醒"该账号没有 DELETE 权限,建议改用软删除"——护栏把**产品误区**也写进去了,而不只是技术红线。

### 模式二:Skills 双角色(保底线 vs 提效率)

**Rules 管的是"规矩",Skills 管的是"能力"**——光有 Rules,AI 不犯错但每次得摸索怎么干;光有 Skills,AI 干得快但可能不合规范。两者结合,AI 既守规矩又高效,人的介入成本降到最低。

Skills 的两个关键设计:

1. **按场景自动触发**(Agent 创建/工作流创建/Changelog/前端设计/Vue 开发/工蜂/iWiki/技能创建):用户说"新增一个专线质量分析 Agent",Agent 创建 Skill 自动激活,AI 按 Skill 定义的工作流一步步执行(探索代码→写提示词→建工具→注册→验证);
2. **代码去腐化的职责分离**(最值得抄):创建 2 个职责分离的技能——"扫描代码问题、创建 issue" vs "认领 issue、修复代码问题",**避免既当裁判又当运动员**;让 Agent 高频小批量定期运行,保障 AI 原生研发下仓库代码质量(代码演进快,腐化也快)。

### 模式三:CLI 安全工具(高频操作封装成"安全、留痕、可重复")

AI 常需要做"运营性"操作(执行 DDL、回填数据、管理配置)——让 AI 自己写临时脚本 `import db` 跑,**既不安全也不留痕**。封装 CLI 后:

| 工具 | 把什么封起来 | 护栏 |
| --- | --- | --- |
| `flow-db-exec` | DB 变更唯一入口 | 高危关键字硬拦截 + 账号权限双保险;强制先写 changelog.sql 再执行;结果可读 |
| `flow-config` | 业务配置 | 配置与代码同仓库,AI 直接读写改完即生效;Key 分层命名 |
| `run-cron` | 定时任务入口 | 独立进程,避免重任务阻塞线上接口 |

!!! tip "模式本质"
    **AI 不用理解底层连接、事务这些细节,调一个命令就行。** 命令输出本身是精简的——比 AI 写 50 行 Python 脚本(import db、建连接、执行 SQL、格式化输出)既安全又省 token。这是"工具保持愚蠢,智能留给模型"在运维操作上的体现。

### 模式四:让 AI 看见问题(质量保障的"看见"四层)

AI 编码最大的风险不是写得慢,而是**写错了不知道**。四层叠加,大部分问题 AI 会话内就能发现修复:

```
① 静态检查即反馈    ruff / ty / oxlint / vue-tsc 输出 AI 直接读到,自写自修
② AGENTS.md 汇总   规则越集中,AI 遵守得越好
③ 开发服务自主管理  dev.sh 统一启动,AI 自己看日志查进程
④ Playwright 验证   headless 截图/检查 API/验证交互——AI 自己做 QA
```

!!! warning "TDD 在 AI 场景的微妙问题"
    AI 写测试很快,但容易写出"自欺欺人"的测试(只覆盖 happy path、断言太弱)——用规则约束兜底,而非追求严格的"先写测试"。且**更看重"验收"而非"测试"**:AI 开发完用 Playwright headless 截图验证,再交提需求的人确认,形成闭环。

### 模式五:Everything as Code(能力全部代码化)

传统的 Agent 平台是"平台 + 后台配置"——AI 看不到全貌,每接新能力都要人手动"告诉"平台。AI 原生设计相反:**不把能力藏在管理后台或外部系统里,全部以代码形式存在,让 AI 能直接探索、理解、复用**:

| 传统模式 | AI 原生模式 |
| --- | --- |
| 提示词在管理后台维护 | 提示词是代码文件 |
| 工具在后台注册 | 工具是代码函数 |
| 配置靠人填表 | 注册是代码装饰器 |
| AI 看不到全貌 | AI 需要什么能力,直接在仓库里找,找到就能用 |

配套支撑:ReactAgent 基类(模型配置/上下文注入/SSE 流式/会话持久化统一),新增 Agent 只关注三件事——名字、系统提示词、工具。两个细节:**工具返回值尽量 markdown 而非原始 JSON**(Agent 更好理解 + 大幅省 token + 人看着方便);SSE 流式支持断连重连(刷新页面不丢进度)。

!!! note "与站内其他护栏文章的呼应"
    [给 Coding Agent 立规矩](agent-rules-agents-md.md) 讲规则文件载体工程(AGENTS.md/CLAUDE.md 正交、一份源三消费);本文的"Rules 三层"是实战级落地(工程规范/流程护栏/记忆三层分场景加载)。[AI 协作规则设计](../../03-agents/agent-collaboration-rules.md) 讲六维度内容模板;本文补充"护栏怎么生长"(先跑起来再加)与"护栏怎么防太自信"。

## 代码 / 实现:护栏生长判断器(纯 Python)

把"先跑起来,再长护栏"与"护栏设计原则"落成可运行演示——评估一个项目当前该加什么护栏:

```python
def harness_growth_check(project: dict) -> list:
    """按"护栏随需求生长"原则,给出当前最该补的护栏"""
    advice = []
    if not project["has_rules_file"]:
        advice.append("第一优先:建 AGENTS.md,先集中工程规范(Rules 三层的第一层)")
    if project["committers"] > 3 and not project["has_flow_rules"]:
        advice.append("多人协作:补流程护栏层(anydev_rule:三阶段不可绕过/分支透明)")
    if project["db_ops"] and not project["has_cli"]:
        advice.append("涉及 DB 操作:封装 flow-db-exec 类 CLI(高危拦截+changelog 留痕)")
    if project["ai_writes_code"] and not project["has_verify"]:
        advice.append("AI 在写代码:补'让 AI 看见问题'四层(静态检查→AGENTS→dev 管理→Playwright)")
    if project["agent_count"] >= 3 and not project["has_memory"]:
        advice.append("Agent 变多:补 Memory 记忆层 + 代码去腐化技能(职责分离)")
    return advice if advice else ["护栏已够用:继续按实际需求生长,不提前过度设计"]

# 演练:一个刚跑起来的单人 AI 编码项目
newbie = {"has_rules_file": False, "committers": 1, "db_ops": False,
          "ai_writes_code": True, "has_verify": False, "agent_count": 0}
for a in harness_growth_check(newbie):
    print("  +", a)
```

## 团队框架:代码越便宜,约束越重要

!!! tip "一个反直觉但合理的判断"
    **代码越便宜,写好代码的约束反而越重要。** 当生产的门槛降到几乎为零,质量的差异就不再是"能不能做出来",而是"做出来的东西能不能长期待在一起"——**当代码不再稀缺,稀缺的是秩序**。

**团队框架**不是新名词,也不是再造一个全栈框架:它是一套**结构化的约定 + 一层薄技术胶水**,铺在通用框架之上,让团队知道"怎么干"而不是每次重新讨论。关键反转:AI 没有上下文记忆——每一次生成都像一个新来的外包,干活快,但从来不知道之前的人怎么干的。**你不告诉它规则,它就每次都发明新规则;AI 不负责一致性,一致性得由团队框架来保证。**

### 两个陷阱(不是只有一个)

| 陷阱 | 表现 | 来源 |
| --- | --- | --- |
| **被大框架绑死** | 便利的代价是控制权(Jack Franklin 的 Inversion of Control:组件何时渲染 React 说了算,99% 没事,剩下 1% 想伸手调伸不进去);想改时发现它是承重墙 | 全栈框架的"精装修公寓" |
| **无约束散架** | 五人团队五种风格(路由按功能/按页面,状态管理 Pinia/Zustand/Composition API,API 请求三种封装)——每个决策单看都对,合起来项目变成各自舒适区的拼盘,新人要看五种风格 | 架构碎片化:从来没人做过收敛 |

过去团队在两个陷阱间"忍"——自己造轮子成本太高(路由/渲染/构建/热更新/TS/测试/部署都要持续维护,业务团队养不起)。**现在两个条件同时变了**:框架生态把自己拆成可拼装的积木(Vite 框架无关构建层/Nitro 独立服务器运行时/Vike BYOF/Vinxi 可编程框架层——"把 Next.js 拆了"),AI 把维护约定的成本打下来了。

### 团队框架 = AI 的"工作说明书"

"接口文件的鉴权通过这个中间件走,不要自己写""错误返回用这个统一函数""这个目录下的工具函数不要用了,用新的那个替代"——这些东西写下来**不只是给人看的**,结构化之后就是 AI 的工作说明书:AI 在生成代码之前先读一遍团队约定,产出的代码自然更像你们团队写的,而不是像从 Stack Overflow 上随机挑的答案。

!!! tip "维护成本的反转"
    过去团队框架最大的成本是维护文档和保证一致性;现在 **AI 恰好擅长把约定执行到位**——你只要维护一套干净的规则描述,AI 帮你落地,相当于把维护成本里最繁琐的部分外包出去了。

### "铺一条路"七要素(不是精装修公寓,是柏油路)

```
1. 项目模板和模块边界    新项目从哪开始,模块怎么拆,不用每次讨论
2. 标准接入方式          鉴权、权限、日志、监控,不绑某个框架的插件
3. 数据访问和接口约定    API 怎么调、错误怎么返回,有固定写法
4. 部署和测试基线        CI 跑什么,CD 怎么配
5. 可替换的底层适配器    业务代码不直接 import 框架特定 API,经过团队薄封装;框架换了,换适配器就行
6. AI 可读取的架构说明   活文档,不是写好就过期的 Wiki
7. 默认路径 + 逃生舱      默认怎么做清楚,但你也知道怎么绕
```

这层薄封装定义的是"**我们怎么用**",不是"**我们用什么**";选择那些可以被轻易替换的依赖(如 lit-html 这种随时能换的小包)——不重、不绑死任何东西,存在的唯一理由是减少团队在"怎么做"上的重复决策,也让 AI 知道该怎么做。

## 实践 / 应用:省 Token 的七条清单(工程性强但重要)

AI 原生研发模式下 token 是实打实的成本,一次会话上下文太大既贵又慢:

1. **AGENTS.md 集中规则**:项目规范写在一个文件里,AI 读一次就够,不需要每个文件重复说明;
2. **工具返回 markdown 而非原始数据**:一个格式化表格约 200 token,原始未经整理的 JSON 可能 10 倍;
3. **CLI 工具替代临时脚本**:一行命令 vs 50 行 Python 脚本;
4. **大仓 + 语义搜索**:monorepo 让 AI 一次会话覆盖全栈,配合语义搜索快速定位,减少"到处找文件"的探索开销;
5. **SDD 文档驱动**:复杂需求写成文档,AI 读完就有完整上下文,文档比对话历史精练;
6. **组件化 + Storybook**:AI 先看 story 了解已有组件避免重复实现;组件拆得小,每次改动范围小,上下文不用加载整个大文件;
7. **探索要"验证过再信"**:RTK(Rust Token Killer)等工具验证后效果一般(偶尔压缩出 bug、语义混淆)就弃用——"省不了几块钱,还让 AI 依赖一个不稳定的命令行代理,得不偿失"。

## 总结

- **护栏哲学**:先让 AI Coding 运转起来,护栏随实际需求逐步生长——守住质量下限 + Token 效率,而不是追求能力上限;
- **五个模式**:Rules 三层护栏(集中/分场景/不重复)、Skills 双角色(保底线 vs 提效率,去腐化职责分离)、CLI 安全工具(安全/留痕/可重复)、让 AI 看见问题(四层质量保障)、Everything as Code(能力代码化);
- **两条铁律**:规则集中不重复;护栏要防 AI 太自信(三阶段不可绕过、产品误区主动提醒);
- **一条判断**:新项目先跑起来再补护栏,不提前过度设计。
