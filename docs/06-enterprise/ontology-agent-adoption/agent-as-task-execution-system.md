# Agent 是任务执行系统:十个工程要点

> **一句话摘要**:Agent 不是聊天机器人,而是围绕模型搭起来的任务执行系统。本文从控制循环、工具边界、记忆取舍、验证机制、多 Agent 成本、框架控制权、生产三关到场景成熟度,提炼十个工程要点,并给出"先确认三件事"的落地框架与一段验证驱动的纯 Python 循环。
>
> **来源**:微信公众号《企业 Agent 工程化手记》素材《Agent 不是聊天机器人,而是任务执行系统》(作者一线实践,原文链接见收件箱登记);原始资料存档于 `docs/inbox/enterprise-agent-engineering-src-b9.md`

## 概念

做 AI 应用这几年,越来越少把 Agent 当成新名词。它更像是 LLM 应用被真实任务逼出来之后,自然长出来的一套工程形态。**单次 LLM 调用适合回答问题;真实需求却更接近"把事情做完"**——查资料、判断可信度、读文件改代码跑测试、发消息等结果、按反馈继续下一步。

Agent 的核心定义:**Agent 是一个围绕模型搭起来的任务执行系统,能根据目标维护状态、选择动作、调用工具,并用反馈不断修正下一步。** 这里的重点是"系统"——模型负责理解、推理和生成,Agent 负责把这些能力放进一个可控的运行环境。

只记三句话:

1. Agent 解决的不是聊天问题,而是**任务闭环**问题;
2. Agent 的核心不是多接几个工具,而是**控制循环、状态管理和反馈验证**;
3. Agent 能力越强,越要重视**工具边界、权限、安全和可观测性**。

| 维度 | 聊天机器人 | 传统自动化程序 | Agent |
| --- | --- | --- | --- |
| 控制流 | 一次生成 | 预先写死 | 模型即时决策,按反馈修正 |
| 是否需外部反馈 | 否 | 否 | 是(观察结果驱动下一步) |
| 不确定性 | 低 | 低 | 高(输出不稳、工具选错、状态污染、成本失控、权限风险) |

## 原理

### 1. 任务闭环:目标清楚,过程不固定

用户说"帮我看看仓库为什么测试失败,修好之后提交一个 PR",不能靠一段回答结束。系统要经历:读取项目结构 → 找到测试命令 → 运行失败用例 → 定位错误 → 修改代码 → 再跑测试确认。**每一步都产生新信息,新信息又影响下一步决策。**

传统程序适合分支少、规则稳定的流程;Agent 适合**目标清楚但过程不完全固定**的任务。工程上不能只看到弹性——只要模型参与决策,就要面对输出不稳定、工具选错、状态污染、成本失控和权限风险。

### 2. 控制循环:状态、动作、观察

Agent 架构图是一张循环图:**状态进入模型 → 模型决定动作 → 动作调用工具 → 工具返回观察结果 → 系统更新状态 → 进入下一轮。**

```python
# 伪代码:说明 Agent 控制循环结构,不是可运行程序
state = load_initial_state(user_goal)
while not state.done:
    context = build_context(state)               # 感知:整理上下文
    action = model.decide_next_action(context)   # 规划:决定下一步
    if action.type == "final_answer":
        return action.content
    result = tools.run(action)                   # 执行:调用外部工具
    state = update_state(state, action, result)  # 记忆:更新状态
    if should_stop(state):
        return summarize_current_state(state)
```

最容易被低估的是**观察结果**——没有它,Agent 只是在连续生成文本;有了它,才有机会根据真实环境修正下一步。循环通常拆成四层,每层都是具体工程问题:

| 层 | 职责 | 工程问题 |
| --- | --- | --- |
| 感知层 | 把外部世界整理成上下文 | 上下文怎么裁剪、排序,关键信息不被淹没 |
| 规划层 | 决定下一步,并不断修正计划 | 计划怎么表示,前一步结果推翻判断怎么办 |
| 执行层 | 调用搜索/解释器/数据库/浏览器等 | 工具边界清不清楚、参数可否验证、失败有无反馈 |
| 记忆层 | 保存过程与可复用经验 | 状态怎么落盘,失败怎么恢复,哪些动作必须确认 |

### 3. 规划策略要跟任务形态匹配

工程选型先看任务形态,而不是从 CoT、ReAct、ToT、GoT 术语讲起:

| 任务形态 | 策略 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 只要推理、无外部反馈 | CoT(链式思考) | 中间步骤显式展开,适合数学/逻辑/规则推导 | 前面错一步,后面沿着错误继续 |
| 频繁调用工具 | ReAct | 先想一步、做一步、按观察继续,边做边调 | 不要求一开始规划完整路径 |
| 比较多个候选方案 | ToT(思维树) | 同时展开多条路径再评估 | 高价值、低频、可多花成本才值得 |
| 回溯/合并/复用 | GoT(思维图) | 推理做成图,支持回溯合并 | 实现成本高,多数业务系统不必先上 |

**经验**:先从 ReAct 这类简单循环做起,真遇到规划不足、需要回溯复用时再升级。最怕一开始把推理架构做得很复杂,而评估、工具和权限还很粗糙。

### 4. 工具定义了 Agent 的行动边界

工具调用决定 Agent 能做什么,也决定它能闯多大祸。常见误区是把所有工具说明都塞进上下文让模型自己选——工具少时还行,一多就选错、混参、在重叠工具间反复试探。更稳的做法是**先分层再选择**:

```python
tool_category = classify_capability(task)             # 先判断任务需要哪类能力
candidate_tools = registry.find_by_category(tool_category)  # 再在这一类里选
tool = model.choose_tool(task, candidate_tools)
arguments = model.fill_arguments(task, tool.schema)
validated_arguments = validate(arguments, tool.schema)     # 参数落地前校验
result = tool.run(validated_arguments)
```

**工具说明要写得像接口契约,不要写成产品介绍**,至少说清四件事:解决什么问题、什么时候不该用、参数结构是什么、成功和失败分别返回什么。只靠自然语言描述参数,模型常生成"看似合理但系统无法执行"的输入;结构化参数、枚举、必填字段、取值范围、返回格式校验,都能显著降低失败率。也不要给 Agent 两个功能高度重叠、名字又相似的工具。

权限更关键:**读文件、写文件、发邮件、下单、删数据、调用内部系统不能放在同一信任级别。**

| 动作风险 | 分级 | 工程要求 |
| --- | --- | --- |
| 只读操作 | 低 | 可直接执行 |
| 写入草稿 | 中 | 留痕 |
| 发送外部消息 | 高 | 人工确认 + 审计 |
| 修改生产数据 | 高 | 人工确认 + 审计 + 最小权限 |
| 执行 shell 命令 | 极高 | 确认、审计、隔离环境 |

### 5. 记忆系统的价值在于压缩和取舍

什么都记,最后等于什么都用不好。

| 层级 | 存什么 | 工程要点 |
| --- | --- | --- |
| 工作记忆 | 模型当前能看到的上下文窗口 | 放目标、当前状态、关键约束、最近观察;最直接也最贵,不放完整流水账 |
| 会话记忆 | 跨轮对话的结构化摘要 | 用户偏好、任务进度、未完成事项;不塞对话原文 |
| 长期记忆 | 可复用经验(偏好、领域知识、常见修复) | 常配向量检索;难点在什么值得存、何时取、取回是否可信 |

最易出问题的是**旧信息污染新判断**:上次任务的临时路径、过期结论、失败假设被检索回来混进当前上下文。工程上要给记忆加**来源、时间、置信度和适用范围**。

RAG 与 Agent 记忆常被混讲,但关注点不同:**RAG 是外部知识库检索,解决模型不知道的问题;Agent 记忆关注任务过程与行为经验,解决这次做过什么、下次怎么做得更好。**

### 6. 自我反思要落到验证机制上

自我反思工程上更像一种检查机制:执行完工具调用后,检查结果是否满足可验证条件——文件是否存在、测试是否通过、接口是否返回预期字段、邮件是否真的发送成功。**没有外部验证的反思,很容易变成模型自我安慰**:写一段看似合理的复盘,然后继续沿错误路径走。

有效反思绑定三样东西:**观察结果、验收标准、下一步动作**,并拆成三类检查:目标是否仍然清楚、当前证据是否支持继续、失败是否需要换路径。落到代码就是下节 `verify(result, acceptance_criteria)` 的伪代码——重点是**把复盘接到可执行的判断上**,而不是生成一段泛泛总结。代码类 Agent 尤其如此:模型说修好了没有意义,测试通过才有意义。

### 7. 多 Agent 协作要先算协调成本

多 Agent 落地先带来的是协调成本。生产里常见形态比自由对话更克制:有人拆任务,有人执行,有人汇总,有人检查——**少了任何一环,协作都容易失控。**

| 模式 | 适用 | 风险 |
| --- | --- | --- |
| 层级模式 | 边界清楚、可拆分的任务(调研、批量分析、分区修改) | Manager 单点瓶颈;拆错任务后执行越快偏差越大 |
| 并行模式 | 互相独立的任务(同时分析几个竞品/模块) | 必须有汇总与冲突处理,否则输出是一堆并列材料 |
| 评审模式 | 生产系统(一个生成、一个检查、必要时规则验证) | 生成与审查分开,降低一路错到底的概率 |
| 自由对话 | 最不稳定;无强约束时易重复、跑题、互相确认错误结论 | 除非有轮次限制、终止条件、评估标准,否则别当默认架构 |

判断要不要上多 Agent,看三个问题:**任务能不能被清楚拆分?拆分后的结果能不能被独立验证?末端有没有可靠的合并机制?** 三个问题回答不清,多 Agent 只会放大混乱。

### 8. 框架选型要看控制权

| 框架 | 定位 | 控制权特征 |
| --- | --- | --- |
| LangGraph | 复杂工作流 | 图表达状态与转换,支持分支/回退/人工接管/长任务恢复;学习成本高但控制力强 |
| AutoGen | 多 Agent 协作探索 | 对话与角色封装顺;深度控制每步状态和权限需额外设计边界 |
| CrewAI | 角色明确的任务编排 | 上手快,适合快速验证;生产落地要补工具治理、状态管理、评估 |
| SmolAgents 等轻量框架 | 小型原型 | 代码少、抽象薄,容易看清 Agent 在做什么;系统复杂后要自己补工程能力 |
| 自己写主循环 | 任务很特殊、对性能/权限/状态/成本敏感 | 省掉抽象约束,主循环完全可控 |

选型看三个问题:**状态能不能清楚表达?工具调用能不能受控?失败恢复和人工介入是否好做?** 建议:MVP 先选轻量方案验证任务是否真的适合 Agent;复杂生产流程优先状态表达强、可观测性好的框架;关键业务系统**不要把安全、评估和恢复能力完全交给框架默认值**。

### 9. 生产落地最难的是可靠性、成本和安全

Demo 很容易让人兴奋,因为它在开放环境里做出一串动作;生产系统关心的是**它失败时会发生什么**。

**可靠性**:模型输出不要直接相信,能用 schema 校验就校验,能用程序验证就验证。失败后可以重试,但**重试要有上限,也要记录失败原因**——无限重试只是在烧钱。长任务要有**状态快照**:每个关键步骤后保存状态,恢复时从最近的可信检查点继续,别让模型凭记忆猜刚才发生了什么。

**成本**:主要来自模型调用次数和上下文长度。Agent 循环越长,token 越容易失控。常见优化:模型分级(贵模型做判断、便宜模型做翻译)、上下文摘要、结果缓存、工具结果裁剪、批量调用合并。没有一招解决所有问题,只能把成本纳入架构设计。

**安全**:Agent 能调用工具,就可能被提示注入诱导做越权操作——外部网页、邮件、文档、聊天消息里都可能藏着恶意指令。系统要**区分用户指令、开发者指令、工具返回内容和不可信外部内容**,不能把所有文本都当成同一层级的命令。权限按动作分级(见第 4 节),高风险动作需要确认、审计和隔离环境;能跑 shell 的 Agent 尤其要小心。

**可观测性**:线上问题不能靠猜。需要知道 Agent 每一步看到了什么、决定了什么、调用了什么工具、工具返回了什么、为什么进入下一步。没有这些记录,线上问题只能靠猜。

### 10. 哪些场景会先成熟

| 场景 | 成熟度 | 原因 |
| --- | --- | --- |
| 软件开发 | 最快 | 代码天然有文件、测试、构建、类型检查、版本控制,**很多结果可以被验证**,软件工程本身给了 Agent 反馈闭环 |
| 企业流程自动化 | 快 | 文档处理、录入、报表、审批辅助、客服分流规则清楚、工具边界易定义;权限审计做好即见效 |
| 研究助理 | 较快 | 搜索、总结、交叉验证;难点是事实可靠性,不能只看写得顺不顺 |
| 个人助手 | 慢 | 日程/邮件/购物/财务容错率低、权限风险高;答错可以接受,发错邮件改错日程不能接受 |
| 具身智能 | 更远 | 物理环境、传感器噪声、安全责任;需要整套高可靠控制系统,光有会规划的模型不够 |

## 代码 / 实现

原文为方法论文章,无代码。下面用纯 Python 演示**验证驱动的 Agent 循环**:每个动作后做外部验证(跑测试),按 `verify → passed / retryable / help` 三个分支前进,并在关键步骤前打状态快照:

```python
# -*- coding: utf-8 -*-
"""验证驱动的 Agent 循环:verify -> passed / retryable / help(纯 Python)
场景:代码 Agent 修复一个测试失败,每步做外部验证(跑测试)再决定分支"""

def apply_patch(attempt):
    """执行工具:应用补丁。第 1 次修不好,第 2 次修好"""
    return "patch_%d" % attempt

def run_tests(patch_id):
    """外部验证:真实跑测试,返回 {passed, failed, output}"""
    if patch_id == "patch_1":
        return {"passed": 2, "failed": 1, "output": "test_calc FAILED"}
    if patch_id == "patch_2":
        return {"passed": 3, "failed": 0, "output": "3 tests passed"}
    return {"passed": 0, "failed": 3, "output": "3 tests FAILED"}

def verify(result, acceptance):
    """外部验证:逐条检查验收标准;返回 (verdict, evidence)"""
    evidence = {k: check(result) for k, check in acceptance.items()}
    return ("passed", evidence) if all(evidence.values()) else ("failed", evidence)

def diagnose_failure(state, evidence):
    """模型诊断:依据证据判断 retryable 还是 help"""
    if state["attempt"] == 1 and evidence.get("tests_green") is False:
        return "retryable"      # 测试没全绿,补丁可修正
    return "help"               # 证据表明方向错误,不再自动撞结果

def agent_loop(user_goal, max_attempts=3):
    state = {"attempt": 0, "goal": user_goal, "checkpoint": None, "log": []}
    acceptance = {"tests_green": lambda r: r["failed"] == 0}

    while state["attempt"] < max_attempts:
        state["attempt"] += 1
        state["checkpoint"] = dict(state)               # 状态快照:关键步骤前落盘
        state["log"].append("attempt %d: 模型决定 -> 应用补丁" % state["attempt"])

        patch = apply_patch(state["attempt"])           # 执行动作
        result = run_tests(patch)                       # 工具返回观察
        state["log"].append("  执行 %s -> 测试结果 %s" % (patch, result))

        verdict, evidence = verify(result, acceptance)  # 外部验证
        state["log"].append("  verify -> %s (evidence=%s)" % (verdict, evidence))

        if verdict == "passed":
            state["log"].append("  完成:验收标准全部满足,任务闭环")
            return {"status": "done", "log": state["log"]}

        branch = diagnose_failure(state, evidence)      # 反思=决策点
        state["log"].append("  diagnosis -> %s" % branch)
        if branch == "retryable":
            state["log"].append("  修正动作,进入下一轮")
            continue
        state["log"].append("  请求人工:放弃自动修正,转入 help")
        return {"status": "help", "log": state["log"]}

    state["log"].append("  超过重试上限,从最近 checkpoint 恢复并转人工")
    return {"status": "help", "log": state["log"]}

if __name__ == "__main__":
    outcome = agent_loop("修复仓库里失败的测试")
    print("最终状态:", outcome["status"])
    for line in outcome["log"]:
        print(line)
```

**运行方式**:`python3 文件名.py`(纯标准库)。关键点:

1. **验证是决策点,不是复盘**——`verify` 逐条检查验收标准(`tests_green`),产出结构化 evidence,`passed` 才标记完成;
2. **诊断决定分支**——`diagnose_failure` 依据证据判断:第 1 次失败是 `retryable`(方向可修正,修正动作后重试);证据表明方向错了或超过上限则 `help`(转人工,不靠反复重试撞结果);
3. **状态快照**——每个关键步骤前把 `state` 打 check point,恢复时从最近可信点继续;
4. **重试上限**——`max_attempts` 硬性封顶,超限从 checkpoint 恢复并转人工。

**运行结果**:attempt 1 补丁没修好(2 过 1 挂)→ `verify=failed` → `diagnosis=retryable` → 修正重试;attempt 2 测试全绿 → `passed` → 任务闭环,最终状态 `done`。若把 `apply_patch` 改成永远修不好,则走 `help` 分支——**两条路径都验证通过**。

## 实践 / 应用:先确认三件事

做 Agent 系统前,先确认三个问题,再谈框架、记忆、多 Agent 和复杂规划:

| 问题 | 检查点 | 不满足时的降级 |
| --- | --- | --- |
| 任务是否真的需要模型参与决策? | 目标清楚但过程不固定、需按反馈修正;若规则稳定,传统程序更可靠 | 用确定性规则,别硬上 Agent |
| 结果能否被验证? | 有可执行的验收标准(测试、schema、文件、接口),而不是"看起来像" | 先补验证机制,或限定到可验证子任务 |
| 失败是否可恢复? | 有状态快照、检查点、重试上限、明确的 help 分支 | 先做状态管理和恢复路径,再开放能力 |

三个问题都站得住,才把模型放进控制循环。对应到本文十个要点,落地顺序建议:

1. **先搭最小控制循环**(要点 2),用 ReAct 式简单循环(要点 3);
2. **定义工具边界**(要点 4):分层候选 + 接口契约 + 权限分级;
3. **给循环挂验证**(要点 6):`verify → passed / retryable / help`;
4. **再谈记忆**(要点 5)、多 Agent(要点 7)与框架(要点 8);
5. 上线前过一遍**可靠性、成本、安全、可观测**(要点 9),按场景成熟度(要点 10)排优先级。

!!! tip "三个问题的关系"
    三个问题互不独立:结果能被验证,才谈得上失败可恢复;失败可恢复,才敢让模型在不确定环境里做更多决策。**能留下来的系统,需要在不确定环境里保持可控、可查、可恢复。**

## 总结

- Agent 是**任务执行系统**,核心是控制循环、状态管理和反馈验证,不是多接几个工具。
- 规划策略跟任务形态匹配:推理用 CoT、频繁调工具用 ReAct,复杂方案才考虑多路径探索。
- 工具是行动边界:先分层再选择,说明写接口契约,权限按动作分级。
- 记忆在于压缩取舍,防旧信息污染;反思必须落到外部验证(`verify`),而不是自我安慰。
- 多 Agent 先算协调成本,框架选型看控制权,生产三关是可靠性、成本、安全。
- 落地前先确认三件事:**任务是否真的需要模型参与决策?结果能否被验证?失败是否可恢复?**
