# Palantir Ontology 的构建、案例与边界:从 5000 万决策到物理本体

> **一句话摘要**:Palantir Ontology 不是 AI 自动生成的知识图谱,而是"人工设计架构 + 机器辅助映射 + 人工审核确认"的可执行语义层。本文拆解构建方法论与治理体系,用 bp、通用磨坊、温蒂汉堡、空客、坦帕医院五案例提炼数字与经验,并用"决策本体 vs 物理本体"差异矩阵划清边界。
>
> **来源**:微信公众号"本体论/案例分析系列"整理提炼;Palantir 官方文档 / General Mills Impact Study(AIPCon 2024)。素材:`docs/inbox/palantir-ontology-src-o1.md`、`src-o4.md`~`src-o10.md`

## 概念

### 本体构建的真相:三段式,不是自动生成

这不就是知识图谱吗?AI 能不能自动从数据里"生"出一个本体?答案是**不能**——没有任何工具能自动"设计"出 Object Type、Link Type 和 Action Type 的结构。**本体不是数据仓库,而是需要被精心设计和持续维护的 API**。

| 环节 | 角色 | 自动化程度 | 是否涉及"设计本体结构" |
| --- | --- | --- | --- |
| 架构设计 | 人工主导(FDE + 业务专家) | 无自动化 | **是**——有哪些 Object Type、怎么连、挂什么 Action |
| 映射辅助 | 机器辅助 | Schema 推断、列到属性自动映射、转换代码生成 | 否——只在数据集/列/流水线层面 |
| 审核确认 | 人工把关 | 提案评审、合并审批 | 是——最终决策权在人 |

一句话概括:**人工设计架构 + 机器辅助映射 + 人工审核确认**。

## 原理

### 构建方法论:从数据到对象的四步

| 步骤 | 工具 | 关键设计 |
| --- | --- | --- |
| ① 数据接入 | Data Connection | **As-Is 接入**:数据原样同步,Foundry 成为"唯一变更来源";200+ 连接器 |
| ② 数据转换 | Pipeline Builder | 点选式(可视化描述,后端自动生成代码);**输出可直接是本体组件**。流式数据不能配置编辑功能和多对多链接 |
| ③ 本体定义 | Ontology Manager | 创建 Object Type(选底层数据集→自动映射列到属性)、Link Type、Action Type;7 步向导;**一个数据集只能支撑一个 Object Type**,MDO 支持一对象多数据集 |
| ④ 本体消费 | Applications + AIP | Workshop/Quiver/Object Explorer 直接消费;AIP 在 Ontology 之上构建——**消费已有本体,不负责生成本体** |

### AI 在构建中的四个角色

| 层级 | 能力 | 做什么 | 边界 |
| --- | --- | --- | --- |
| 数据层 | Schema 推断 | 按样本自动推断列类型 | 纯类型推断 |
| 映射层 | 列到属性自动填充 | 列名→属性 ID/类型 | 规则推断,无 NLP;可删多余映射 |
| 实例层 | AIP Logic 非结构化映射 | 把 PDF 等抽取填充到已有 Object Type | 实例填充,非 schema 设计——须先定义 property |
| 架构层 | AI FDE(AI 前驻工程师) | 对话操作 Foundry,可创建/更新对象、链接、操作 | **只创建提案**,人工审核后合并 |

!!! warning "AI FDE 的本质"
    AI 智能体**不直接修改本体,而是创建提案**,人工审核后才合并到主分支。AI 降低的是**操作成本**,不是**决策成本**。

### 实体解析:同一台设备、同一个人怎么对齐

- **独立产品**:专门的 Entity Resolution 产品,金融案例中 ML 解析十亿级记录;hashing + AI/ML 提速降本,fuzzy matching 提准。
- **人机协同**:**ML 推荐配对 + 人工审核确认 + 反馈学习**,准确率比客户自己做高 **40%**。
- **可逆合并与隔离写入**(Gotham API):合并保留子对象历史、可反合并;内部 **winner object** 隔离新写入(元数据:`canonicalObjectPrimaryKey`/`winnerObjectPrimaryKey`/`otherObjectPrimaryKeys`),与 Git 合并异曲同工。

### 成本与准确性的平衡术

- **General Mills**:ELF 推荐 **超 70% 被人工接受**,每天省 4 万美元、年化 1400 万美元(仅部分网络)——AI 做高频推荐(降本),人工把关 30% 高风险决策(保准确性)。
- **bp**:数字孪生规模效应——每天 10 亿数据点,24h→20min;新增用例边际成本递减。

人工审核是**架构设计**而非口号:① 决策支持(AI 增强而非替代人类判断);② 人类监督(Actions + 审批);③ 反馈循环(AI 提案→人工审核→agent 学习)。

### 治理:本体层面的安全与权限

| 机制 | 要点 |
| --- | --- |
| 权限模型演进 | 旧:Ontology viewer/editor/owner;新:统一到 **Compass 文件系统** |
| Backing Dataset 权限传递 | 底层数据权限传递上来——**本体权限不会比底层数据更宽松** |
| Markings / CBAC | 敏感标记 + 角色权限;基于分类的访问控制,需 Palantir 介入 |
| 分支提案 | 本体编辑在分支上进行(Global Branching),提案经 review + merge 进主分支 |

## 代码 / 实现

纯 Python 演示**六边界判定法**(Six-Gate Filtering):某项数据能否进入本体,须由决策目标自上而下驱动、依次通过六道硬性关卡,而不是"有什么表接什么表"。

```python
# 六边界判定法:数据/属性能否进入本体,由决策闭包自上而下审计
GATES = [
    ("goal_relevance",       "是否直接进入目标函数 J 的计算?"),
    ("causal_reachability",  "与目标结果之间是否有已知因果/机理可达路径?"),
    ("observability",        "物理上可否被传感器直接测量或由状态观测器估计?"),
    ("actionability",        "是否对应可调节的执行机构,能施加干预?"),
    ("verifiability",        "执行 Action 后,物理世界能否在确定时延内回传可测反馈?"),
    ("governance_economics", "采集/清洗/高频同步/长期存储总成本是否显著低于决策收益?"),
]


def audit(feature: str, evidence: dict) -> bool:
    """evidence: {gate_name: (passed: bool, reason: str)}
    任一 gate 不通过 => 该数据被拒入本体(或降级为背景参数)。"""
    print(f"\n=== 审计候选数据: {feature} ===")
    passed_all = True
    for name, question in GATES:
        passed, reason = evidence[name]
        mark = "PASS  " if passed else "REJECT"
        print(f"  [{mark}] {name:22} | {question}")
        print(f"          理由: {reason}")
        passed_all = passed_all and passed
    print(f"  => 结论: {'准入本体' if passed_all else '拒绝进入本体'}")
    return passed_all


if __name__ == "__main__":
    print("决策目标 G: 高炉炉壁烧穿风险预测(提前 24h 预警,降低非计划休风)")

    # 候选 1:与目标强相关的工艺量 —— 应全部 PASS
    audit("高炉冷却水流量(1Hz 实时)", {
        "goal_relevance":       (True,  "直接进入炉壁热平衡目标函数"),
        "causal_reachability":  (True,  "传热机理明确:流量→对流换热系数→炉壁温度"),
        "observability":        (True,  "电磁流量计可直接测量"),
        "actionability":        (True,  "对应执行机构:冷却泵变频器"),
        "verifiability":        (True,  "调节后数分钟内热电偶回传温度反馈"),
        "governance_economics": (True,  "1Hz 采集成本远低于一次烧穿事故损失"),
    })

    # 候选 2:看似能"顺便"接入的无关数据 —— 第一关即被剔除
    audit("全厂配电房电能计量表读数(15min 累计)", {
        "goal_relevance":       (False, "不进入炉壁热平衡目标函数 J"),
        "causal_reachability":  (False, "与炉壁温度无因果传导路径,仅间接相关"),
        "observability":        (True,  "电表可测"),
        "actionability":        (False, "无对应可调节机构,只能观测"),
        "verifiability":        (False, "无法验证其对炉壁状态的任何影响"),
        "governance_economics": (False, "为无关数据长期同步存储,治理成本无收益"),
    })
```

**运行**:`python3 six_gate.py`(Python 3.9+,无依赖)。任一 `False` 即整体拒绝;实测候选 1 全过、候选 2 首关被剔除。

!!! tip "代码与 Palantir 的关系"
    六边界判定法源自工业本体边界的批判,精神与 Palantir"从决策出发反推本体结构"同源;形式化模型是决策闭包六元组 `O_G = {E, R, S, C, A, V}`。

### bp:10 年合作背后的可靠性工程

**背景**:2010 年墨西哥湾漏油事故后,监管要求 bp 实时掌控全球资产;维修、传感、工程、地质、气象数据分散在数十个系统。

**本体建模**:四层数据组织——区域/资产/节流/系统,**同一套底层数据按不同维度切片**。对象:设备、传感器、故障模式、维修工单、备件;预测模型作为 Function 绑定设备对象,输出**可执行推荐**("设备 X 未来 7 天 85% 概率故障 Y,建议停机前更换备件 Z")而非"告警",经 Action 自动建工单、预约备件、调度人员。

**成果**:ROI 超 100%(数亿美元);每天 10 亿数据点,24h→20min。

**可迁移经验**:① **从资产级切入**(ROI 最直接、数据最可得、决策链最短);② 今天启动约 18-24 个月完成资产级整合,36 个月扩展;③ 选一体化平台因"数据到决策全流程一个环境"。

### 通用磨坊:5000 万项决策背后的 AI 供应链

**背景**:4000 家供应商、200+ 北美工厂、120 万订单/年、**5000 万项运营决策/年**(每天 13.7 万项),驱动 100 亿美元 COGS——1% 优化就是 1000 万美元。

**本体建模**:把 **200 张主数据和运营数据表**语义化映射:ERP"采购订单"、物流"运单"、生产"工单"统一为标准对象类型(订单/工厂/供应商/运输路线),统一属性(ERP"交货日期"=物流"预计到达时间")。MDO 权限隔离:质检评分仅授权人可见。

**成果**:

| 指标 | 数字 |
| --- | --- |
| AI 推荐采纳率 | 超 70% |
| 每日/年度节省 | 4 万美元 / 1400 万美元(仅部分网络) |
| 订单处理/碳排放/准确率 | 18h→30min / -15000 吨 / 96-97% |
| 战略底座 | 四年 30 亿美元战略 |

**可迁移经验**:① **先建语义层再上 AI**——**数据治理不是 AI 的前置条件,数据治理就是 AI 的一部分**;② 人在回路是过渡态不是终态(目标 "take them off the loop"),需三条件:标准化采纳指标、技能重塑(团队转向训练 AI)、变革冠军;③ **机会成本可视化**提升采纳率。

### 温蒂汉堡:6500 家餐厅,人脑算不过来交给 AI

**背景**:QSCC 合作社管理 6500 家餐厅供应链,近 **40 亿美元采购力**;生鲜保质期从几小时到几天,每批食材都有"隐形时钟"在倒计时。总裁:"**人脑无法穷尽所有场景,才能正确解决问题。**"

**本体建模**:代号"从农场到 Frosty"全链路——对象:原材料/半成品/成品/餐厅/配送中心/供应商/运输批次;关系:`原材料-加工为->半成品`、`半成品-组装为->成品`、`成品-配送至->餐厅`;Action:创建采购订单/调度运输/调整库存分配。这让 AI 在"理解供应链业务"而非"查询数据库"。

**动态库存管理**:短缺 2800 箱→立即下单 3500 箱,同时建模整条链路(订原料→投产→发货到 DC→发到餐厅),逐店判断"削减订单能否撑到下午 3-4 点送达",撑不过就自动补货;三层:**实时感知**→ **约束求解**→ **动作执行**。

**治理设计**:多方主体(供应商/配送中心/加盟商/管理层)通过对象级/属性级/动作级三级权限实现"共享但不泄密"。

**经验**:① 判断复杂度**看变量组合数而非规模**;② 全链路 vs 局部优化——局部优化有"水面效应",3 个以上环节且有交互效应时选全链路;③ 治理设计比技术重要——**先回答:各方愿共享什么、给谁、什么条件下?**

### 空客:500 万个零件,用数据造出来

**背景**:A350 含 500 万个零件,数百团队在 4 国 8 厂协作制造。2015 年底需紧急增产且不牺牲质量;但排期、轮班、零件、工单、质量问题散落各国,没人能看到全局。

**本体建模**:三阶段——2015 年 A350 生产线→ 2016 年扩展到排班/供应链/财务 → 2017 年至今 **Skywise 天空智慧平台**(连接整个航空业)。

**成果**:A350 产量 +33%;10,500+ 架飞机接入(49% 机队);月度用户 25,000;"**每天至少少停一架飞机**"。

**可迁移经验**:① 从紧急业务需求切入(A350 增产这个具体压力);② 分阶段扩展——一条产线→企业级→行业平台;③ 平台一开始就要具备多租户和安全隔离能力。

### 坦帕医院:一套 AI 系统,两年挽救 700 名患者

**背景**:TGH 是坦帕湾唯一学术医疗系统,利润率仅 1-1.5%。脓毒症是"隐形杀手":黄金窗口仅几小时,早期症状与普通感染几乎一样,医护人员无法 24h 盯每个病人。

**本体建模**:把护士排班、患者普查、手术排班整合进**统一医疗业务语义层**(定义"护士—排班—床位—患者"关联链)。三类能力:① 脓毒症预警;② 运营优化(排班提前数周规划);③ 行动中心应用(直接调床位、改排班)。

**成果**:

| 指标 | 数字 |
| --- | --- |
| 脓毒症 48h 死亡率 | -68% |
| 两年额外挽救患者 | 700 名 |
| 恢复室滞留 / 安置管理 | -28% / -83% |
| 护士配比 / 预测准确率 / 应急 | +30% / 95% / 飓风 24h 灾难应用 |

**可迁移经验**:① 从最高价值场景切入(脓毒症预警——"做成了能救命"的场景);② 本体论是关键——没有统一语义层,AI 无法理解"床位安排如何影响护士排班";③ 人在回路——AI 给推荐、人做决策,让医生更早更准;④ 敏捷是副产品,合作是长期的(2024 年扩展为护理协调核心)。

## 反思与边界

### Palantir 的四大局限

| 局限 | 具体表现 | 对采用者的含义 |
| --- | --- | --- |
| 闭源与 IaC 缺失 | Platform SDK 仅支持 schema 读操作,无创建 API;不支持 OWL/SHACL 导出 | 只能 Web UI 建模,无法 IaC/CI-CD |
| 供应商锁定 | 构建需数周数月并暴露敏感数据;切换成本"指数级恶化" | 深度锁定,迁移约等于推倒重来 |
| 缺乏推理 | 依赖 Interface + 显式 Link Type,无 OWL 自动推理 | 推理密集场景用 Functions 弥补 |
| 实时性代价 | 重度物化,索引传播(Funnel)有延迟 | 非硬实时方案,止步于运营层 |

### 决策本体 vs 物理本体:差异矩阵

| 比较维度 | Palantir 运营本体(决策本体) | 严格工业物理本体 |
| --- | --- | --- |
| 系统目标 | 组织运营决策与业务行动编排 | 物理-工程世界可解释、可预测、可验证的状态表示 |
| 核心建模对象 | 业务实体、组织角色、任务、运营资源 | 物理资产、连续介质、相变过程、热力学状态、设备能力边界 |
| 时间表达 | 离散事件流、静态时序点 | 连续微分/差分动力学、瞬态演化、确定性时延 |
| 约束本原强度 | 软性业务规则、审批阻断、ACID 校验(人为可改) | 硬性物理规律(守恒律)、材料极限、独立安全层 |
| Action 本质 | 事务性修改、数据库回写、API 编排(无瞬态时间) | 动力学控制输入、安全包络内参数干预 |
| 验证机制 | 业务日志审计、人工审批流 | 物理传感器闭环、数字孪生仿真、稳定性判定 |

!!! warning "为什么工业不能照搬"
    盲目照搬运营模型到工业物理世界,"无异于用治理公司的行政流程去试图控制一台高炉的非线性化学反应"。运营中规则逾越最多导致亏损;物理世界中守恒律违背带来灾难性毁灭——Palantir 关系网络无法自发推导"乙烯进料量 +5% 时反应釜热平衡如何变化"这类守恒律因果。

### 工业需要的:运营—物理双层本体架构

工业 AI 的解法不是二选一,而是**解耦与多层共生**——上层吸收 Palantir 思想,下层用物理工程、状态估计、动力学约束和确定性控制守住物理底线:

| 层级 | 职责 | 关键机制 |
| --- | --- | --- |
| ① 运营本体层 | ERP/SCADA 数据对象化 + 对象图谱 + 权限 | 业务对象 + Action |
| ② 物理工程本体层 | 资产拓扑(ISA-88/95)、材料物化属性、工艺逻辑;把"生产计划"译为"加热炉工况" | 资产拓扑 + 物化词表 |
| ③ 实时状态孪生层 | IIoT 高频流 + EKF/软传感器,对隐藏状态连续估计 | State Estimation |
| ④ 动力学约束内核 | ODE/PDE 机理 + 物理硬约束 + 安全包络;Action 经仿真判定,违背则**一票否决** | 安全包络 + 一票否决 |
| ⑤ 控制执行层 | DCS/PLC/SIS 只收低时延设定值,毫秒级闭合控制环 | 毫秒级控制环 |

### 十步迭代生长法:本体不是规划出来的

真实路径是**决策闭包驱动 + 从 MVP 子图生长**("先花五年建全厂通用本体"是死胡同),像晶体析出一样逐步融合:

1. 定义核心决策目标 G(如:反应釜不过热前提下产率+3%);
2. 梳理业务与控制决策;
3. 用六边界判定法划定实体集 E_G;
4. 定义实时状态空间 S_G + 估计模型;
5. 注入物理/工艺/安全约束 C_G;
6. 设计可行动作包络 A_G;
7. 建立传感器证据链验证 V_G;
8. 配置细粒度权限;
9. 场景本体独立投产(MVP 子图直接闭环);
10. 跨场景晶体化融合(O₂ 经共享语义骨架对齐,自发生长)。

!!! tip "给技术人的判断"
    评判 Palantir Ontology,要用 **agent runtime 标准**而非描述逻辑标准——不问"OWL 推理完备吗",而问"我的 agent 能在治理约束内安全读取、推理、行动、回写、接受审核吗"。70% 采纳率、ROI>100%、700 条生命都是成绩单——**本体不是对世界的复制,而是行动者进入世界的接口**。

## 总结

1. **构建真相**:三段式"人工设计架构 + 机器辅助映射 + 人工审核确认"——没有银弹,设计决策权在人。
2. **方法论**:四步流水线 + 实体解析"ML 粗筛+人工确认+反馈学习" + 治理体系(Actions 控制平面、Global Branching、Markings/CBAC/MDO)。
3. **案例证明**:五案例共享主线——先建语义层、从决策反推结构、人在回路是架构设计、治理先于技术,从年省 1400 万美元到 700 条生命。
4. **边界清晰**:Palantir 解决"组织如何认识并作用于世界";工业还需"运营—物理双层五层架构"补上"世界如何存在与约束行动"。
5. **最终判断**:本体是行动者进入世界的接口——评判它看 agent 能否在治理约束内闭环行动。
