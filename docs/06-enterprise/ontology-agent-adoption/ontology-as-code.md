# Ontology as Code:像代码一样管理本体

> **一句话摘要**:较真"像代码一样管理本体(Ontology as Code)"这个流行说法:如果它是实指而非修辞,就必须逐条兑现代码的继承、引用、版本、行为四项能力,并建设一条显式的对账管线——而真正的受益者,是进场后的 AI/Agent。
>
> **来源**:付小杭《Ontology as Code:像代码一样管理本体》(OntoEffect 系列之七),微信公众号 https://mp.weixin.qq.com/s/p9e6YM-gGrEWWENJajS5GQ

## 概念

"Ontology as Code"这个说法,多数时候是**修辞**——意思大概只是"我们把 schema 存成了 YAML,放进了 git 仓库"。文件确实在版本库里,但继承靠字段复制、引用靠口头约定、版本号靠手动自增、行为逻辑散落在本体之外的服务代码里。**定义存进了 git,本体本身并没有变得更像代码。**

如果"像代码"是**实指**,本体就该逐条兑现代码的四项基本能力:

| 代码能力 | 本体对应物 |
| --- | --- |
| 继承(inheritance) | is-a 对象类型体系:子类自动获得父类属性与约束 |
| 引用(reference) | 类型化引用 + **注册期解析**(悬空引用进不了系统) |
| 版本管理(versioning) | **内容寻址的版本锚点**(任何结果可追溯到唯一版本) |
| 定义行为(behavior) | Action / Function 定义在本体里,名词与动词同库同治 |

## 原理:四项能力的字面兑现

### 1. 继承:is-a 不是 copy-paste

代码世界里,子类继承父类,改一处、处处生效。本体世界的对应物:对象类型父子体系——`ManeuverableSatellite` 声明自己 is-a `Satellite`,自动获得全部属性与语义约束,再叠加自己的增量。

反面是**没有继承的本体**:一张平铺的名词表,每加一个相近概念就把二十个字段复制一遍——第一天两份定义还一致,第三个月一份改了单位、另一份没改,**漂移从复制那一刻就开始倒计时**。继承不是建模的说辞,而是把"这两个概念本质相同"从口头共识变成**机器可见的声明**。

### 2. 引用:注册期解析,而不是运行时才发现 undefined

代码有符号解析:import 一个不存在的模块,编译期就报错。本体的对应物是元素间的**类型化引用**——关系类型引用它两端的对象类型,函数签名引用它作用的对象类型,动作定义引用它调用的函数和提交条件。

关键不在"能引用",而在**注册期解析和校验**:

- 指向不存在的对象类型?**注册被拒绝**;
- 函数签名与挂载点类型不匹配?**注册被拒绝**;
- 悬空引用根本进不了系统,而不是等到某次运行时才抛出 undefined。

这相当于本体有了**编译期符号检查**——一整类错误从"生产事故"降级为"提交失败"。

### 3. 版本:每个运行结果都能回答"我是在哪个 commit 上算的"

代码有 git:任何构建产物都能追溯到唯一的 commit。本体的对应物是**内容寻址的版本锚点**:每次 schema 变更产生一个新的**不可变版本**,任何运行态数据、任何一次函数求值、任何一条告警,都携带它所依据的本体版本。

!!! warning "受监管领域的致命点"
    没有版本锚的系统答不出"三个月前那条告警是按哪一版规则判定的"。规则改过之后,旧告警的判定依据随之蒸发——**审计要求你重现历史,而你只有现在**。版本锚点让"重现任意时刻的本体状态"成为一个查询,而不是一次考古。

### 4. 行为:本体里不只有名词,还有动词

这是最能区分"本体"与"数据字典"的一项:数据字典管到名词为止(有哪些实体、什么字段、什么类型);而代码里的类从来不只有字段,还有方法。

本体的对应物:**动作(Action)和函数(Function)就定义在本体里**。"对一条告警能做什么"(确认、升级、关闭,各自的前置条件和权限)、"这个属性怎么算出来"(派生逻辑、输入依赖),都是本体元素,和对象类型进**同一个注册表、受同一套治理**。名词和动词同库同治——这条分水岭的另一侧,行为逻辑散落在各个服务代码里,本体退化为一份没人保证与现实一致的说明文档。

## 原理进阶:as code 的真正难点——对账管线

代码世界有一个基础到极少被意识到的前提:**运行的就是编译产出的那一份**。源码 → 构建 → 部署,三者一致性由工具链原生保证。

**本体世界没有这个前提**:定义写在代码仓里,运行态注册在系统的元数据表里——**两个真理源,天然会漂移**。漂移的形态很具体:

- 代码里改了签名,注册表没同步,调用方拿着旧契约撞上新实现;
- 有人图快在管理接口上直接改了注册表,代码仓不知道,下次同步把热修复静默冲掉;
- 版本号涨到了 7,却没人答得出版本 7 对应仓库里哪一次提交——**版本号在涨,版本却不存在**。

把定义写进 git 只完成了一半。另一半是**三件必须显式建设的东西**:

1. **对账脚本**:扫描代码侧的定义全集,与注册表逐项 diff、增量同步——它是两个真理源之间**唯一合法的桥**,桥之外的任何直接写入都是漂移源;
2. **漂移门禁**:对账不是定期打扫,是**准入条件**——代码与注册表不一致,CI 直接拦截,进不了主干;漂移被消灭在提交时刻,而不是积累到某次故障排查时才被发现;
3. **版本锚定**:注册表里的每个版本携带它源头的 **commit 与内容哈希**,能回指到唯一一份源码。

!!! tip "核心命题"
    **"as code"不是一种存储格式,是一条对账管线。** 没有漂移门禁的 ontology as code,只是 ontology as text——文件在 git 里躺着,真相在别处漂着。

## 原理进阶:递归——本体用自己治理自己

业务数据的变更走 **Action 信封**:有提交条件、进审计日志、可以回滚。那么**本体自身的变更**走什么?

schema 变更改的不是数据,而是"数据长什么样"的规定——改错一个属性的语义,下游所有过滤器、规则、派生计算一起失真。越危险的操作越需要治理,但大多数系统恰恰在 schema 变更处**断档**:数据变更有完整事务和审计,schema 变更却是运维终端里的一条 DDL,或管理界面的一次点击——**权力最大的操作,走的是治理最少的通道**。

作者的回答是把问题**递归掉**:schema 变更也走 Action——存在一类 **schema-level Action**,操作对象不是业务对象,而是本体元素本身。新增对象类型是一次受治理的提交,注册函数是一次受治理的提交:同样有提交条件(引用必须可解析、约束必须自洽),同样进审计日志(谁、何时、凭什么理由),同样产生一个新的版本锚点。

结构性含义:

- 数据库不治理 DDL 权限体系(靠 DBA 纪律);代码世界不治理代码(靠 git+CI 外挂工具链);
- **本体是这个系统里唯一用自己的机制治理自己演化的层**:Action 是本体元素,而 schema 变更是 Action 的一种——治理不是罩在本体外壳,是**本体咬住了自己的尾巴**。

递归成立后,前两节线索合流:**schema-level Action**(每次变更是受审提交)+ **内容寻址版本**(每次提交产生不可变锚点)= **一条不可变的提交链**:每个节点有作者、有理由、有前置校验、有指向上一个状态的引用。

!!! tip "一句话分水岭"
    定义存在 git 里,是 **ontology as text**;本体自身长出 git 的语义(commit、diff、blame、revert 都有本体层对应物),才是 **ontology as code**。

## 代码 / 实现

原文为方法论文章,无代码。下面用纯 Python 演示"对账管线"的核心逻辑:两个真理源(代码仓定义 vs 运行时注册表)之间的漂移检测与门禁,这正是文章第三节的核心机制:

```python
# 两个真理源:代码仓里的定义 vs 运行时注册表
repo_defs = {"Satellite": {"type": "object", "fields": ["id", "mass"]},
             "ManeuverableSatellite": {"type": "object", "is_a": "Satellite",
                                       "fields": ["thrust"]},
             "ThrustFn": {"type": "function", "signature": "(mass) -> float"}}
registry = {  # 运行态注册表:某次直接改注册表,代码仓不知道
    "Satellite": {"type": "object", "fields": ["id", "mass"]},
    "ManeuverableSatellite": {"type": "object", "is_a": "Satellite",
                              "fields": ["thrust", "max_duration"]},  # 漂移!
    "ThrustFn": {"type": "function", "signature": "(mass, duration) -> float"},  # 漂移!
}

def reconcile(repo, reg):
    """对账脚本:逐项 diff,输出漂移清单;漂移门禁据此拦截提交"""
    diffs = []
    for name in sorted(set(repo) | set(reg)):
        if name not in repo:
            diffs.append(f"注册表多了未入库元素: {name}")
        elif name not in reg:
            diffs.append(f"代码仓定义未注册: {name}")
        elif repo[name] != reg[name]:
            diffs.append(f"定义漂移: {name}\n  repo: {repo[name]}\n  reg : {reg[name]}")
    return diffs

diffs = reconcile(repo_defs, registry)
for d in diffs:
    print(d)
print("-" * 40)
print("漂移门禁:", "CI 拦截,进不了主干!" if diffs else "通过,允许提交")
```

**运行结果**:对账脚本精确列出两处漂移(`ManeuverableSatellite` 多了字段、`ThrustFn` 签名不一致),门禁据此拦截。真实工程中,对账脚本跑在 CI 里,`diffs` 非空即失败——**漂移被消灭在提交时刻**。

## 实践 / 应用:谁最需要 as code——不是人,是 AI

前四节所述能力,人类团队靠纪律都能近似模拟(继承靠建模规范、引用靠评审会、版本靠变更单、schema 治理靠审批制度)——成本高、漏洞多,但确实能运转。**真正让 as code 从"良好实践"变成"结构必需"的,是 agent 进场**,理由有两个:

### 其一:AI 缺的不是智力,是可编译的目标

- 让 agent 用自然语言描述意图,你得到的是需要人类翻译和把关的意图;
- 让 agent 面向一个 **as code 的本体**编程,你得到的是**能被注册期校验拒绝的代码**:引用不存在的对象类型?拒。签名类型不匹配?拒。想绕过治理信封直接落库?这样的调用在暴露给 agent 的接口面里**结构性不存在**——不是运行时鉴权拦住了它,是它根本无法被表达。

一门有类型检查、有"非法程序"概念的语言,把对 AI 产出的约束从**事后审查前移到表达层**。

### 其二:as code 给了 AI 的产出一个治理落点

- 图形界面里点出来的本体变更:没有 diff、没有 review 最小单元、没有回滚点——agent 通过界面自动化改了本体,你既看不清改了什么,也撤不回去;
- as code 形态下:**agent 的每一次本体修改天然是一个 commit**——可 diff、可审、可拒、可回滚。人审 agent 的产出,审的就是一个 **PR**,用的是软件工程打磨了几十年的协作与把关机制。

!!! tip "作者的核心判断"
    代码形态不是为了人类开发者的舒适,是为了**给 AI 的产出一个治理落点**。在 agent 时代之前,ontology as code 是提升工程质量的选择题;agent 进场之后,它是让 AI 参与本体演化的前提条件。**运营 AI 的问题,一半是本体问题;而本体问题,一半是 as code 问题。**

## 实践进阶:类比的边界——机器守结构,人守语义

类比在一个地方断裂:

- **编译器给出的是语义保证**(编译通过 = 类型安全,机器给的、可传递的);
- 本体的"编译"(注册期校验)保证的只是**结构一致**:引用可解析、约束自洽、签名匹配。它保证不了业务概念本身是对的——继承链搭得再干净,如果概念一开始就切错了位置,结构完美的本体照样系统性地错下去;
- **概念的演化**(语义漂移、继承关系重构)没有自动兼容检查器,是本体工程真正的手工活,只能靠人对领域的理解。

但这条边界不减损价值,反而澄清了分工:**机器守结构,人守语义**。as code 的全部建设——继承、引用、版本、行为、对账管线、自我治理的提交链——本质上是把一切可以机器化的守卫交给机器,好让人的注意力集中到唯一不可机器化的事情上:**概念一致**。

> 让本体像代码,不是为了写得快。是为了让每一次变更都**无处遁形**。

## 总结

- "Ontology as Code"要成为实指,必须兑现四项能力:**继承**(is-a 声明)、**引用**(注册期解析拒绝悬空)、**版本**(内容寻址锚点)、**行为**(Action/Function 入库)。
- 真正的难点不是存储格式,而是**对账管线**:对账脚本 + 漂移门禁 + 版本锚定,保证两个真理源(代码仓与注册表)不漂移。
- 最高形态是**递归治理**:schema 变更也走 Action,本体用自己治理自己,长出 git 的语义(不可变提交链)。
- 核心价值在 **agent 时代兑现**:as code 给 AI 一个"可编译的目标"和一个"治理落点"(修改 = PR,可 diff 可回滚)。
- 边界:**机器守结构,人守语义**——概念正确性永远需要人。
