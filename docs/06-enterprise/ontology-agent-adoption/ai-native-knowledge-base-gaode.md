# 高德广告工程的 AI Native 知识库体系:六域知识底座与检索闭环

> **一句话摘要**:AI Native 知识库不是再建设一个文档平台,也不只是给现有资料叠加一层 RAG——它的核心问题是如何把分散在代码、设计文档和研发经验中的知识,转化为**结构清晰、能够准确检索、可以持续更新的工程资产**。高德广告工程团队给出了一套完整落地:四层架构 + 六个知识域 + "意图识别→直达短路→并发召回"的检索链路 + 手工/SDD/多 Agent 三条生产路径 + 反馈闭环保鲜。
>
> **来源**:微信公众号「高德技术」《高德广告工程的AI Native知识库体系》(作者:信息业务中心),https://mp.weixin.qq.com/s/1d9LDoD2SOcEZ19mDwiE-Q;原始资料存档于 `docs/inbox/gaode-knowledge-base-source.md`

## 概念:AI Native 知识库要解决什么问题

!!! tip "不是文档平台,也不是 RAG"
    当需要了解"某业务能力如何实现"时,相关知识分散在 CodeWiki、设计文档、研发人员的经验里,跨多个平台才能找全,还要判断是否齐全、是否仍然有效。**人可以凭经验串联线索、辨别时效,Agent 却难以准确识别信息之间的关联与有效性**——这正是知识库要补齐的。

高德广告工程把研发流程推进为 AI Native 模式:一个需求周期拆成**六个阶段**(需求增强、需求拆解、方案设计、代码开发、测试闭环、线上运维),每个阶段都有 Agent 深度参与;但 Agent 在复杂任务中仍受上下文质量影响,缺三样东西——**对系统整体的认知、对历史经验的记忆、对实现细节的掌握**。过去的知识积累(CodeWiki/设计文档/需求复盘)彼此割裂,覆盖率、准确性、时效性都难保证,"知识虽多却无法有效驱动 Agent"。

## 原理:四层架构与六大机制

### 总体架构(四层)

| 层 | 职责 |
| --- | --- |
| **接入层** | 统一知识入口,集中管理检索/发布/审计/演进;当前以 **Skill 形态**嵌入各类研发 Agent,为独立部署留扩展空间 |
| **能力层** | Skill 内核:一次请求统一走"**意图识别 → 路由 → 执行 → 审计回执**";读侧(检索/重排/跨库探索/效果评测)+ 写侧(发布/更新/索引重对齐/SDD 归档/规约同步/案例沉淀) |
| **知识层** | 六个并列知识域(索引上的 L1),域间通过统一跨层映射相互引用 |
| **反馈层** | 让知识库在规则约束和人工审核下随研发过程持续演进:纠错、案例沉淀、规约同步、效果回归 |

规模:已沉淀 **6 个知识域、千余篇知识**,由数十个代码仓库、上千篇文档抽取而来。

### 六个知识域(按 Agent 提问的知识类型切分,不按团队/系统)

| 域 | 回答什么阶段的问题 | 组织设计 |
| --- | --- | --- |
| **语义域** | 需求阶段:"是什么、像不像" | **全局统一组织**,术语差异用"映射"维度表达 |
| **架构域** | 跨系统关系 | 全局统一组织,保证跨域引用一致性 |
| **服务域** | 开发阶段:"在哪、怎么实现" | **实例驱动不预先登记**;每服务固定六类 L3(框架/流程/接口/实现/最佳实践/规约,允许留空) |
| **项目域** | 一次研发全过程 | **扁平单篇**:需求/方案/反思整体归档一篇,保留上下文完整性 |
| **案例域** | 经验沉淀 | 流程沉淀与运维 Case |
| **规约域(SDD)** | 服务规约 | 人工审核落地,Agent 只出建议 |

**三条贯穿全域的约束**:①**跨层映射**——每篇文档底部预留其他五个域的映射项,有明确关系填链接、无关联显式标注;②**索引归纳纪律**——每级只归纳直接下级、严格不跨级,索引页正文写"下级一句话归纳 + 内联 URL"(这是检索"读正文直达"的前提);③**模板即契约**——普通知识文档统一四段式骨架(Preamble / Body / 跨层映射 / Metadata),发布前必须通过模板校验。

### 检索链路:从"翻三四个平台"到一次直达

一次"某业务能力如何实现"的查询:

```
意图识别 → 路由 → 直达短路(命中索引先读正文,正文给叶子链接且置信度高 → 直接返回,全程不发向量)
                     ↓ 未直达
          结构化检索 ∥ 向量检索 并发 → merge 重排(最贴意图的域提前,同名他域作"相关"列出)
                     ↓ 向量命中碎片
          回溯至完整权威文档 → 按任务选取章节/摘要交给调用方
```

**四个关键设计**:

1. **意图识别三件套(声明式 registry + LLM 判定 + 置信度兜底)**:不依赖硬编码 if-else,也不靠训练分类器——所有意图登记在一张表(动作必选 × 目标域可选 × 流程阶段可选,配触发关键词与典型句式);LLM 拿自然语言对着表打标(非精确匹配,"我在写代码,实现资料给我"也能判成 查询×服务域×代码开发);三维度均明确且无冲突=高置信,缺失/冲突=返回候选或澄清,连动作都认不出=低置信**强制反问一次,绝不硬猜**;
2. **索引正文优先**:节点名多是代码标识符,与自然语言对不上,命中索引后优先读正文做语义匹配;导航点查通常只读索引与目标文档,**不产生向量调用**;
3. **直达短路 + 并发召回**:高置信直达直接返回;否则结构化与向量并发,merge 守两条硬规则——以结构 canonical 为权威锚、向量补漏;向量命中先回溯完整权威文档再取相关章节(避免碎片脱离上下文);
4. **意图加权重排**:同一概念跨域同名,不固定某域优先,按"流程阶段 × 域"优先级矩阵重排、保留多域——**唯一硬约束:不能因向量分高,就拿"是什么"答"怎么做"**。

### 检索质量怎么看(recall-eval 的两条纪律)

- **召回率只是手段,不是目的**:召回高 ≠ 下游 Agent 任务准(塞一堆不相关内容进上下文反而是负担);它只作检索层的**回归哨兵**;
- **整体价值看两个代理信号**:①**采纳信号**——案例沉淀记录"用了哪些知识、哪些被采用/修改/未使用";②**消融对照**——关库 vs 接库各跑一遍真实查询,定性比对 Agent 输出差异。

### 与纯向量 RAG 的六项差异

| 场景问题 | 朴素向量 RAG 局限 | 高德处理 |
| --- | --- | --- |
| 节点名是代码标识符、查询是自然语言 | chunk 相似度对不上 | 索引正文语义匹配 + 向量补漏 |
| 调用方要完整上下文 | 抛 top-k 碎片 | 回溯完整权威文档,再按任务取 |
| 同名概念跨多个域 | top1 易落错域 | 阶段 × 域加权重排,消歧不删域 |
| 导航/点查不需要向量 | 每次查询都走向量 | 命中索引正文直达,不发向量 |
| 多域治理规则不同 | 统一切片难以表达 | 六域模型 + 统一映射补充治理语义 |
| 知识要能被人维护 | 碎片化索引不便人工维护 | 模板即契约,人能读能写能校验 |

!!! note "边界声明(原文)"
    与只索引代码的 codebase index 相比,本方案覆盖知识类型更广;与知识图谱/GraphRAG 相比,选择了相对轻量、便于人工共建的组织方式——三类方案各有适用边界,并非相互替代。

## 代码 / 实现:意图识别路由的最小演示(纯 Python)

把"声明式 registry + 置信度兜底(低置信强制反问)"落成可运行实现:

```python
# —— 声明式意图 registry:动作 × 目标域 × 流程阶段 ——
REGISTRY = [
    {"action": "query",  "domain": "service", "phase": "dev",
     "keywords": ["实现", "怎么实现", "代码", "在哪"]},
    {"action": "query",  "domain": "semantic", "phase": "req",
     "keywords": ["是什么", "概念", "含义", "术语"]},
    {"action": "query",  "domain": "service", "phase": "ops",
     "keywords": ["为什么", "排障", "故障", "原因"]},
]

def route_query(text: str) -> dict:
    hits = []
    for intent in REGISTRY:
        matched = [k for k in intent["keywords"] if k in text]
        if matched:
            hits.append((intent, matched))
    if not hits:
        return {"action": "clarify", "reason": "低置信:连动作都认不出,强制反问一次,绝不硬猜"}
    # 取匹配关键词最多的意图;若并列冲突 → 澄清
    best = max(hits, key=lambda h: len(h[1]))
    ties = [h for h in hits if len(h[1]) == len(best[1])]
    if len({(h[0]["domain"], h[0]["phase"]) for h in ties}) > 1:
        return {"action": "clarify", "reason": "意图冲突(多域命中),返回候选供用户澄清"}
    return {"action": best[0]["action"], "domain": best[0]["domain"],
            "phase": best[0]["phase"], "matched": best[1]}

for q in ["某业务能力的实现资料给我", "这个能力是什么概念", "线上怎么排障",
          "随便说点什么"]:
    print(f"  {q!r:22} → {route_query(q)}")
```

## 实践 / 应用:知识生产、闭环保鲜与可迁移要点

### 知识生产的三条路径(共享一套写入纪律)

**写入纪律**:URL 完整性(终态不留 TBD)、写后逐篇回读(不抽样)、Owner-only 索引更新(不级联改上级)、命名含中文描述。

1. **手工发布与更新**:`publish` 按模板创建、`update` 整体覆盖;服务规约走 `spec-sync` 特例——豁免四段式、只校验最简骨架(标题/Owner/最后更新),**规约由负责人提供并审核,不由 Agent 直接生成**;
2. **SDD 归档**(研发流程自然出口):做完一个项目把需求/方案/反思归档为一篇(解析校验→方向路由→落库登记);反思里的服务规约不自动写入,只生成"建议整理入 service_spec"提示,经人工审核后落地;
3. **多 Agent 批量抽取**(初始填充,数十仓库上千文档数十小时):`kb_multi_agent` 五个设计——①流水线:主对话作 orchestrator,triage→explore→review→publish 各有专职 worker,另配排障角色;②长时运行:`/goal` 绑 Stop hook,检查终止条件(完成/取消/失败/escalation 堆积/30 分钟未变),状态全落盘、**上下文可丢、进度不丢**;③抗遗漏:源树 BFS 全展开、按源型拆 batch、代码源三层防线(survey 标优先级/explorer 带 file:line 取证/reviewer 覆盖率审计);④多来源整合:同一 spec 多源逐段比对(去重/互补合并/矛盾升级/新主题追加),自动匹配 depends_on 与 exposes 反向补齐"被谁调用";⑤两段式发布:本地产中性数据半成品供人 review,确认后对齐远端模板逐篇推送——产出与格式解耦,远端模板变了只重跑发布。

### 闭环与保鲜(防腐层)

- **流程沉淀**:需求增强/架构拆解隐式沉淀案例(采集"用了哪些知识、哪些有用、交付物"——正是采纳信号的来源);SDD 产出一篇;线上问题归报警/排查 Case;
- **反哺各域**:运维 Case 反向沉淀 SOP(硬约束);SDD 反思经 spec-sync 反哺服务/架构域;案例 consolidate 周期提炼共性发布到上层;**使用即反馈**(找错/不全/过期即 feedback)是最轻量高频的纠错入口;
- **保鲜更新**:reindex 按四档严重度对齐(空页/轻修链接/补框架/重建漂移,默认最轻档);巡检 + 分层评测(定期全量回归/逻辑变更即时全量/大批量发布 smoke/高频 query 每周抽样);
- **已知局限(原文自陈)**:保鲜仍薄弱(源头变化未自动感知,变更到纠正有窗口)、跨服务调用关系可能不全(依赖代码证据)、检索对索引正文质量敏感("最快的直达路径,恰恰建立在最依赖人工维护的索引正文上")。

### 可迁移要点(给企业知识库建设)

1. **按"Agent 提问的知识类型"分域**,不按团队/系统——每类问题落一个域,域内再按最自然维度细分;
2. **模板即契约 + 跨层映射**:结构一致是"能被准确命中"的前提,映射显式标注避免无效关联;
3. **直达短路省成本**:能靠索引正文直达就不发向量——导航/点查是高频且零向量成本;
4. **消歧不删域**:同名概念用"阶段 × 域"加权重排,而不是砍掉其他域;
5. **召回率只当回归哨兵**,用采纳信号 + 消融对照衡量真实价值;
6. **保鲜是防腐层**:流程产生知识 → 沉淀提升质量 → 高质量更容易被采用 → 使用继续产生反馈;源头变化感知是下一阶段重点。

## 总结

- **定位**:AI Native 知识库 = 把分散知识转化为结构清晰、可准确检索、可持续更新的**工程资产**,让人与 Agent 基于同一套经过治理的知识源协作;
- **四层架构**:接入(Skill 形态)/ 能力(意图识别→路由→执行→审计)/ 知识(六域 + 跨层映射)/ 反馈(纠错/沉淀/规约/回归);
- **检索**:意图识别三件套、索引正文优先、直达短路 + 并发召回、阶段 × 域加权重排;
- **生产**:手工 / SDD 归档 / 多 Agent 抽取(上下文可丢、进度不丢);
- **价值判断**:知识库的价值不取决于文档数量,也不能只用一次召回衡量——关键是能否被找到、被采用、并在系统变化后及时修正。
