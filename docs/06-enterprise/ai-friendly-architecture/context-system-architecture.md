# Context System 架构:让 Agent 从"找到资料"走到"可靠行动"

> **一句话摘要**:资料都在,Agent 却不知道哪一份算数、此刻取哪几条、做到什么程度才算完成。Context System 不是一套新平台,而是把散在各处的**事实、权限和结果连进同一条任务**的跨系统运行约定,拆成四层——事实层(什么算数)、上下文层(此刻看什么)、执行层(能做什么)、反馈层(证据验收+经验回送)。本文总结其架构、五步落地链路与三件套资产,并把四层与站内已有专题( Ontology / Context Engineering / Loop-Graph / 记忆治理 )交叉汇总。
>
> **来源**:架构师(JiaGouX)《Context System 架构拆解:让 Agent 从"找到资料"走到"可靠行动"》(https://mp.weixin.qq.com/s/vh2SWPlZIATW2ubSNkpl1Q)

## 概念

### 问题:人和人之间的默认共识,到了系统里都要显式化

"把这个版本发到预发布环境"——人搭档会自动补齐:哪个提交、哪套环境、谁批准的、哪些检查不能省、出事去哪看。换 Agent 就没这么顺:人和人之间默认的共识,必须变成**可读取、可判断、可验证**的能力。

资料往往不缺(发布规范在文档、代码在 Git、制品在仓库、审批在工单、状态在监控),麻烦在于:**Agent 仍可能不知道哪一份算数、此刻该取哪几条、做到什么程度才算完成**。

### Context System 是什么:跨系统的运行约定

Context 在这里不只是一段提示词和记忆,而是**任务当下依赖的事实、规则、状态、工具和证据的总和**。Context System 是承载这组能力的工程系统:

- **不替代知识库**:知识库仍是事实的重要来源,Context System 接着往前多走几步——直到任务有结果、也有证据可查;
- **不推倒已有系统**:知识库、Git、工单、监控都不用重建,它更像一份**跨系统的运行约定**,把散落的事实、权限和结果连进同一条任务;
- **四层分工**:

| 层 | 回答的问题 | 一句话职责 |
| --- | --- | --- |
| 事实层 | 什么算数 | 确认哪份记录能拍板,对象有稳定标识、来源与生效域 |
| 上下文层 | 此刻看什么 | 只把眼前有用的"最小充分工作集"拿上桌,随任务持续更新 |
| 执行层 | 接下来能做什么 | 模型做判断,系统守边界(权限/回滚/幂等由系统兜) |
| 反馈层 | 做成没有 + 留下什么 | 用外部证据验收;新经验走"候选→核验→审核→发布→可撤回" |

## 原理(四层拆解)

### 事实层:先找到能拍板的事实

Agent 搜到一段内容,只说明它**和问题有关**,不代表它能影响当前动作——要看它从哪来、对应哪个版本、现在是否仍然有效。例子:去年的事故复盘和今天的环境配置都可能命中"预发布失败",前者帮找线索,后者才代表环境现状;"群里那句这次可以跳过"不能自动覆盖正式发布规则。

关键问题:**冲突时,哪一份记录能拍板?** 为此:

- 关键对象要有**稳定标识**,来源和维护人跟着记录;
- 生效的**项目、环境、过期时间**最好成为数据本身的一部分;
- 两份记录打架时,系统才有依据决定继续还是停下来找人确认;
- **Ontology 补上语义**:知识库/数据库保存记录,Ontology 说清记录表达什么,系统才分得清"候选版本 / 已批准版本 / 已部署版本";
- 起步不需要图数据库,关系表、几份 YAML 或已有 CMDB 都能先跑;**真正难改的是含糊的语义**——它会顺着自动化流程一路传下去。

### 上下文层:只把眼前有用的东西拿上桌

把上下文窗口理解成 Agent 眼前的工作台。Anthropic 对 Context Engineering 的描述里,最值得在意的是**"持续"**二字:上下文不是任务开始时装一次就结束,工具返回新结果、任务状态变化,下一轮工作集就该重新选。

放回预发布场景:刚接任务看目标环境/候选版本/当前授权 → 准备执行才拿工具参数/禁止项/停止条件 → 出异常再翻日志/变更记录/事故经验 → 验收时放下旧材料,注意力回到本轮证据和目标环境。

这就是**"最小充分工作集"**:眼前够用就好,用不到的留在窗口外,真需要还能找回来。佐证:OpenAI Codex 内部实践用较短的 `AGENTS.md` 当地图(约 100 行只是实践量级,不是通用上限),详细文档放更深目录,入口只负责指路、不复制整本说明书。

### 执行层:模型做判断,系统守边界

信息选对后才动手:看状态 → 选动作 → 调工具 → 根据结果继续或停下(Agent Loop)。短任务一个 Loop 就够;跨研发/测试/发布的 Graph 才有价值——**执行图**(任务怎么跑)与**事实图**(任务依据什么)要分开,可互相引用,不混成一种状态。

提示词只能管一小部分,系统要管的是:

- **输入说清**:项目、版本、环境在输入时说明白,不让默认值替 Agent 猜;
- **授权分离**:查看信息与执行变更分开授权,回滚入口在动作发生前就准备好;
- **边界兜底**:超时/重试交给工具,幂等/并发冲突交给状态机或底层系统;
- **结果留证据**:工具返回别只给"成功",要说明影响了什么、证据位置在哪;没做完的部分如实留下;
- **警惕"执行成功"**:退出码 0 只证明命令正常结束——制品对不对、服务健不健康、流量是否落到预期版本,都要另外查证;
- **权限靠系统执行**:提示词告诉边界,但越权调用光靠模型"自觉"不够,真正的拒绝与审批必须由工具/权限系统执行,状态与数据限制落到底层约束。

### 反馈层:结果先留证据,经验晚一点写

任务结束后,留下的东西分两摊:

| 类型 | 内容 | 门槛 |
| --- | --- | --- |
| **运行证据** | Agent 看过哪些来源、依据哪条规则、调用了什么工具、目标系统后来发生了什么 | 能沿任务一路查回;多证据互相印证,"已完成"才可信 |
| **可复用经验** | 影响以后怎么做(Skill / Runbook / Checklist / 过程资产) | 必须经复现、确认适用范围、审核后才写入 |

关键区分:**聊天记录留下的是这次发生的事,过程资产却会改变下次怎么做。后者写入前必须经过核验和发布。** 一次失败日志可以进任务记录,一条临时安排可以随任务归档;只有经过复现和审核的做法才进长期过程资产。

OWASP Agent Memory Guard 项目正关注这类风险:把跨会话、运行时**可写**的 Agent 记忆视为持久化攻击面,探索完整性检查、策略、快照、回滚(仍在演进,不宜当成熟标准;但错误内容一旦进入长期层,影响不会随当前任务结束)。

**写回路径(先朴素一点)**:

```
候选经验 → 复现与核验 → 责任人审核 → 发布 → 可撤回
```

Agent 可以整理候选、附证据、提示冲突,但**不要顺手把发布权交给它**;正式事实、长期规则、高风险动作归不同责任人,授权分开。

### 五步落地链路(以"发到预发布"为例)

1. **先把"这个版本"说清楚**:把"这个版本/预发布"换成稳定对象——哪个提交、哪份制品、目标环境、发布规则、审批是否仍有效;候选不唯一或授权失效,**停下来问人比自己补齐答案更可靠**;
2. **每往前一步,重新拿一次上下文**:预演/部署/验收需要的东西不一样;环境状态这类会变的事实带上版本或时间,免得下一步还在用旧结果;
3. **动手之前,先看边界**:先做变更预览确认影响范围,再调已授权工具;参数不合法/权限不够工具直接拒绝;重复调用与并发冲突别留给模型;必要检查没过就停下,视情况补偿或交人;
4. **让系统来证明结果**:验收不听 Agent 自述,去 Git/制品库/测试系统/部署平台/监控取证;几处证据对不上就留"待确认/失败",不必急着生成一份完整的成功报告;
5. **新经验先进候选区**:发布结果直接进任务记录(证据保留定位);新做法作为候选经验,带来源/适用版本/复现步骤,核验通过才更新发布清单或过程资产;不再适用时能撤回,且查得到影响过哪些任务。

任何一步断掉都会留下痕迹:开头没把对象说清,后面可能整条链发错版本;验收没外部证据,误判会被写成成功;误判再写回长期资产,还会影响下一次任务。

## 代码 / 实现(落地三件套)

不要从"先建一个平台"开始,先选一条**小链**(预发布核验 / 生产告警初查 / PR 合规检查都合适;第一阶段甚至只做只读核验),准备三份很薄的资产:

**① 来源地图**(一页纸):关键对象从哪里来、由谁维护、记录冲突时按什么规则处理;不必覆盖所有系统,能支撑这条任务即可。

**② 上下文配方**(YAML / JSON 或现有工作流配置即可,不必发明新 DSL):

```yaml
任务: 预发布核验

必须读取:
  - 当前发布规则
  - 候选版本清单
  - 目标环境状态
按需读取:
  - 对应事故复盘
  - 深层日志和历史变更
停止条件:
  - 授权缺失
  - 候选版本不唯一
  - 必要检查未通过
验收证据:
  - 提交与制品对应关系
  - 构建和测试结果
  - 目标环境版本与健康状态
```

**③ 工具合同**:输入 Schema 与权限明确,预演与真正执行分开;超时、错误码、回滚入口让调用方拿得到;"该由工具保证的事,就不要留给模型临场发挥"。

**失败样本先测**:不急着只测顺利发布——同时出现两个候选版本、审批刚好过期、部署回执成功但健康检查失败……跑这些样本,最容易看出系统**该停时能不能停,事后还能不能查到依据**。

**起步指标收敛**:先看来源有没有取错、验收证据是否完整;遇到冲突能否及时停下,甚至比速度更值得关注;只读链稳定后再开放范围小、可审核、可撤回的写操作。

**实践要点**:

- 团队不必一次做齐四层——先选一条高频任务跑起来,能回查来源、能在越界前停住;做过几轮,最缺哪一层会自己露出来;
- 收益不一定马上体现在速度上,但问题究竟出在**事实、上下文、工具还是治理规则**,通常会比以前清楚得多;
- 知识库当然还要继续做:没有稳定的文档、索引和版本管理,Context System 也找不到可靠的事实;
- 核心心法:**知识可以慢慢积累,更在意每一次行动能不能说清依据、经得起复查**。

## 总结

1. **Context System 是跨系统运行约定,不是新平台**:把散落的事实、权限、结果连进同一条任务,让 Agent 知道"下一步去哪查、做完去哪核验"。
2. **四层各管一件事**:事实层拍板(稳定标识/来源/生效域/Ontology 语义)、上下文层取最小充分工作集(持续更新)、执行层守边界(权限/回滚/幂等靠系统)、反馈层验证据(外部取证 + 经验分级写入)。
3. **五步链路防断点**:把对象说清 → 每步重取上下文 → 动手前看边界 → 系统证明结果 → 经验先进候选区;任何一步断掉都会在后续留下痕迹。
4. **落地从一条小链开始**:来源地图 + 上下文配方 + 工具合同三件套,先只读核验,失败样本优先测"该停时能不能停"。
5. **与站内资料是互补关系**:四层分别对应 Ontology 语义层、Context Engineering、Loop/Graph 执行、记忆与文档治理——本站四组专题在此被串成一条可运行的链。

**下一步学什么**:先读 [AI Friendly 后端架构](ai-friendly-backend.md)(六类事实与架构资产),再按表格进对应专题;想动手就选一条高频只读任务(如 PR 合规检查),按三件套落地。
