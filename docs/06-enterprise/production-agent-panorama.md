# 生产级 Agent 全景:从企业定位、架构工程到组织与人才

> **一句话摘要**:为什么企业里大量 Agent 停在 Demo、一上生产就崩?本文是作者为企业做的 6 场培训(框架/架构/Skill/Tool/AI 原生组织/人才)的理论部分全景整理,把"Agent 进入企业后应该做什么、如何做成长期运行的生产系统"串成一条完整链路:**三层定位 → 场景选型 → 产品形态 → 稳定性设计 → 8 层技术架构 → Harness 调试 → Tool/Skill/Pipeline 分工 → 六阶段成熟度 → AI 原生组织 → 人才标准**。每个环节都给出可复用的判断框架(如 Workflow vs Agent 二维矩阵、多 Agent 两问、Tool/Skill/Pipeline/Agent 四概念表),并交叉链接站内各专题文章。
>
> **来源**:微信公众号(6 场企业培训的理论部分,标题《生产级 Agent 全景:架构、Harness 工程、组织与人才》),https://mp.weixin.qq.com/s/rZEqIQR-RcNBWMH_9xq2bw;抓取日期 2026-08-10,原始资料存档于 `docs/inbox/production-agent-panorama-source.md`

## 概念

### Agent 在企业软件中的定位:三层架构

理解 Agent,先看它和现有软件系统的关系。传统企业软件的核心职责是 **System of Record(记录系统)**:CRM 记录客户/线索/订单/合同,ERP 记录库存/采购/销售/财务,项目管理系统记录需求/任务/进度——它们保证企业拥有一份相对可信的事实记录。

Agent 增加了一个新的软件层:**认知与行动层(Cognitive & Action Layer)**。用户直接提交任务("分析最近一个月销售线索,找出高价值客户,生成跟进建议并更新到 CRM"),Agent 负责:理解意图 → 组织上下文 → 判断可用工具 → 调用系统 → 检查结果 → 写回业务系统。原本用户需要跨软件查找、复制、操作的过程,由 Agent 完成中间环节。

由此企业软件分成三层:

```
┌─────────────────────────────┐
│  用户入口与交互层             │  Web / 桌面 / CLI / 工作区
├─────────────────────────────┤
│  认知与行动层(Cognitive)     │  Agent:理解、规划、调用、写回
├─────────────────────────────┤
│  业务记录层(System of Record)│  CRM / ERP / PM / 文档
└─────────────────────────────┘
```

**Agent 的价值只看两个指标**:完成了多少任务 × 任务有多大价值。企业最终关心交付结果;聊天次数、工具调用量、生成内容长度都只是过程指标。

### 为什么是 AI Coding:Agent 的天然验证场

早期 LLM 应用(聊天、RAG、Workflow)解决"生成信息/检索知识/跑固定流程",而 Agent 需要"在完整环境里持续行动"——率先验证这个能力的是 Coding Agent,它拥有四个天然条件:

1. **上下文相对清晰**:代码、依赖、配置、文档都在仓库里,可读可搜;大量训练数据来自 GitHub,模型熟悉代码世界;
2. **工具天然存在**:终端、文件系统、搜索、编译器、测试框架、Git 开箱即用,不必等业务系统开放接口;
3. **验证机制完整**:编译/测试/运行结果即反馈,写完代码可执行测试、发现问题再改,形成清晰反馈循环;
4. **恢复成本较低**:Git 可看 diff、可回滚;而线上业务的已发邮件、已提交付款、一次客户沟通都很难撤销。

Manus 早期用 CodeAct(把行动转成代码再执行)、Codex、Claude Code 扩大任务范围,都是同一思路。**Coding Agent 是观察通用 Agent 演化方向的重要窗口**。

## 原理

### Workflow 还是 Agent:二维选型矩阵

不是所有项目都该上 Agent。用两个维度判断:

- **横轴:业务知识的专业程度**(通用 → 专业)
- **纵轴:工具数量 / 行动次数 / 循环推理次数**(低 → 高)

| 象限 | 特征 | 重点 |
|---|---|---|
| 固定流程 → **Workflow** | 步骤清楚、规则稳定、异常少(表单通知、定时汇总、固定报表、审批流转) | 流程编排,结果稳定、成本可控 |
| 专业知识重、行动少 → **知识工程** | 知识库/Skill/本体/知识图谱 | 普通知识库解决"有哪些资料",Skill 补充"资料怎么用",本体定义业务对象/属性/关系/动作;图谱不必上图数据库,MySQL 存对象+关系即可,关键是知识结构化、模型能在合适阶段取到 |
| 通用复杂任务 → **通用 Agent** | Deep Research、Coding Agent、办公助手:任务拆解、工具选择、上下文管理、多轮执行 | 通用业务知识,挑战在 Loop 工程 |
| 专业 + 多轮行动 → **业务型 Agent** | 金融/法律/医疗/客服:每轮需注入业务规则、客户信息、历史记录、权限约束 | 知识工程、流程设计、工具体系、治理机制全部参与 |

### Agent 产品形态:垂直嵌入还是独立产品

- **垂直能力放进成熟产品**:服务已有业务(CRM 客户分析、项目需求拆解、客服回复建议),直接加入口——现有产品已有用户、数据、权限和流程,Agent 更容易接入真实场景;
- **通用能力做成独立产品**:服务多部门或做公司统一任务入口,独立产品便于连接多系统、建立统一任务中心,承载权限/日志/工作区/成果管理;
- **Web / 桌面 / CLI 各有位置**:Web 开箱即用、部署方便;桌面端能拿更多本地上下文(文件、应用、浏览器状态),Claude Code 让行业重新看到本地环境价值;CLI 适合开发者和专业用户,商业化用 API Key 做身份/计量/收费。
- **企业大概率是混合结构**:桌面端拿本地上下文和执行本地操作,云端连业务系统/存企业资产/管权限,SaaS 保存业务事实,Agent 负责理解任务和组织行动。

### 稳定性设计:让用户敢把重要任务交出去

Agent 承接的任务越重要,用户越关心执行过程。产品需回答:它准备做什么?正在调用哪些工具?访问了哪些数据?哪些已完成?哪些需人工确认?出错能否追踪恢复?对应四个能力:

1. **工具链路透明**:展示用了哪些工具、关键参数、得到什么结果(敏感信息可隐藏,但执行路径必须可解释);
2. **Human in the Loop**:高风险动作(对外发送、改关键数据、删文件、支付退款、发布、不可逆操作)必须人工确认,也可放在计划阶段、关键节点、最终提交;
3. **行为监测和回溯**:保存任务日志、工具调用、上下文版本、输出结果、异常信息,过程可追踪才有信任;
4. **清晰的成果区**:未来 Agent 产品同时提供对话视图、执行过程视图、项目/Workspace 视图、成果视图——用户关注从"每轮对话"转向"进度、异常和结果"。

### 多 Agent 的两问:产品形态 vs 运行架构

团队讨论多 Agent 时,PM 和工程师常说的是两件事:

- **产品侧**:用户是否需要认识多个**长期存在**的角色(人事 Agent / 财务 Agent / 写作 Agent / 客服 Agent)?每个有自己的身份、工作区、历史、权限、长期上下文,划分依据是**上下文和职责边界**——例如公众号/小红书/短视频文案共享背景资料,一个写作 Agent + 不同 Skill 就够,不必按渠道各配一个;
- **技术侧**:当前任务执行中是否需要 **Sub-agent / Agent Team**?主 Agent 临时创建子任务并行搜索/分析/执行再汇总,用于并行处理、隔离上下文、控制权限、划分复杂任务、结构化汇总。用户是否感知这些 Sub-agent 是另一个产品选择。

> **两问定乾坤**:问题一"用户是否需要长期认识多个角色"决定**产品形态**;问题二"当前任务是否需要多个执行单元协作"决定**运行架构**。

### Agent 的 8 层技术架构:基础 Loop 一上生产就完蛋

基础 Agent Loop 很简单(任务 → 模型判断 → 执行工具 → 结果回模型 → 循环),但生产系统必须补齐 8 层:

| # | 层 | 职责与要点 |
|---|---|---|
| 1 | **Agent Loop** | 用户任务 → Harness 组装上下文 → 模型判断 → 返回 Tool Call/结果 → Runtime 执行 → 结果回 Harness → 重组上下文;生产需支持多轮、终止、异常重试、状态保存 |
| 2 | **Tool 层** | 文件读写/搜索/浏览器/数据库/企业 API/本地命令/MCP 外部工具;提供可调用的行动能力 |
| 3 | **Context 层** | 每次模型调用能看到什么:System Prompt、任务、历史、身份、用户资料、计划、工具说明、Skill 描述、中间成果、业务知识、权限信息;**模型能力相同时,Context 质量直接决定表现** |
| 4 | **编排与会话管理** | 长任务状态(完成哪些步骤/处理哪个子任务/生成哪些文件/哪些等待确认/失败从哪继续)+ 历史压缩、窗口管理、任务恢复、多轮协作 |
| 5 | **Skill 与插件层** | Skill 沉淀任务方法、业务 Know-how、操作手册、脚本、模板;插件层让能力可安装/卸载/复用 |
| 6 | **观测与评估** | 记录每轮调用、Token、工具调用、执行时间、错误、用户反馈、成果、完成率;评估任务是否完成、结果是否正确、成本是否合理 |
| 7 | **任务与调度** | 定时任务、Heartbeat、后台队列、超时、失败重试、状态恢复、任务通知 |
| 8 | **治理层** | Agent 有持续身份和工作区,按组织成员管理:身份、权限、数据范围、审阅、行为日志、成本额度、风险策略、负责人——**这层决定 Agent 能否进入高价值业务** |

### Harness 究竟负责什么

Harness 是模型外围的一整套运行机制:最小 Harness 只有 ReAct Loop;生产环境再加 Context、Permission、Memory、Hook、Tool、Skill、状态管理和异常处理。核心任务:**在每次模型调用前组装合适的 Context,在模型返回后推动任务继续执行**。

实战调试发现,**大量问题出在 Harness 而不是模型**:Tool 描述不清晰、参数定义模糊、System Prompt 内部冲突、Skill 触发条件不准、历史消息污染判断、遗留 Hook 挡操作、工具结果过长挤占上下文、权限信息没及时更新。调试生产级 Agent 应先看完整 Trace:模型实际收到哪些消息?工具名称/描述是什么?为何选这个工具?Runtime 实际执行了什么?工具返回了什么?下一轮 Context 如何组装?哪条规则影响了最终判断?

### Tool / Skill / Pipeline / Agent:四个概念一张表

| 概念 | 解决的问题 |
|---|---|
| **Tool** | Agent 可以执行什么动作 |
| **Skill** | 某类任务应该怎样完成 |
| **Pipeline** | 谁在什么阶段使用什么能力完成交付 |
| **Agent** | 谁长期承担这类任务 |

以写公众号为例:Tool = 读文件/搜资料/生成图片/保存文档;Skill = 选题方法/文章结构/标题规则/排版规范;Pipeline = 选题→资料整理→初稿→审阅→配图→发布;Agent = 长期负责写作任务的写作助手。

**Skill 和 Pipeline 必须配合**:Skill 代表能力,Pipeline 代表交付过程。"会写标题"是 Skill,"每周完成三篇公众号文章"需要完整 Pipeline。Pipeline 需明确:当前阶段、谁负责、用哪些 Skill/Tool、输入输出、失败处理、哪些节点人工确认。**企业常花大量精力写 Prompt 却不定义交付管线,结果单次表现不错、长期交付不稳定。**

### 生产级 Agent 的六阶段成熟度

| 阶段 | 能力 | 说明 |
|---|---|---|
| 1 | 能够聊天 | 验证模型和基础交互 |
| 2 | 能够调用工具 | 读文件/查数据/连业务系统,形成最小 Agent Loop |
| 3 | 能够规划并产出成果 | 拆解任务、维护计划、生成文件、成果区展示 |
| 4 | 能够长时间运行 | 任务队列、Heartbeat、断点恢复、重试、通知 |
| 5 | 能够被治理 | 身份、权限、审阅、日志、成本控制、风险策略 |
| 6 | 能够沉淀能力 | 成功经验整理成 Skill/模板/工具/评测集,能力复用迭代 |

> Demo 通常只覆盖前两个阶段;生产系统的大部分工程工作集中在后四个阶段。

## 代码 / 实现

最小 Agent Loop 的骨架(示意,省略具体模型 SDK):

```python
def agent_loop(task, harness, tools, model, max_rounds=20):
    context = harness.assemble_context(task)   # Context 层:组装 system/历史/工具说明/Skill
    for _ in range(max_rounds):
        result = model.step(context)            # 模型判断:返回 Tool Call 或最终结果
        if result.is_final():
            harness.save_state(result)          # 编排:保存状态
            return result.answer
        tool_result = tools.execute(result.call)  # Tool 层:Runtime 执行
        context = harness.assemble_context(task, tool_result)  # 重组上下文
    raise TimeoutError("超过最大轮次")
```

生产版还要在循环外挂上:任务队列与 Heartbeat(第 7 层)、观测日志(第 6 层)、权限校验(第 8 层)、Skill 懒加载(第 5 层)。其中 Skill 通常只把 Name/Description 给模型,模型判断需要时才读取完整内容(如飞书多维表格 Skill 把大量 API 说明放 `references/`,按需读对应章节,减少每次注入的上下文)。

## 实践 / 应用

### AI 原生组织的四层

把视角从 Agent 放大到组织,AI 原生组织关注四层:

1. **Context Layer(上下文层)**:汇聚完成任务所需信息——数据、文档、历史决策、业务状态散落不同系统时,Agent 无法形成完整判断,人也付出大量内部交易成本;该层负责连接信息并按任务动态装配;
2. **Pipeline Layer(管线层)**:定义任务如何在组织流转——角色、阶段、输入、输出、状态、交付标准;很多传统 SOP 可在这一层重新整理;
3. **Skill Layer(技能层)**:保存组织做事方法——专业知识、操作手册、判断规则、分析框架、代码脚本、交付模板;员工经验整理后可转化为 Agent 可调用的能力;
4. **Agent Governance Layer(治理层)**:把 Agent 作为持续运行的执行单元管理,配置身份、权限、日志、审阅、责任边界。

操作系统作为组织总线,人持续提供 Context,Agent 按 Pipeline 调用 Skill 和 Tool,结果写回记录系统。形成的系统需具备三个特征:**可运行、可验证、可迭代**。

### 业务恢复能力决定控制机制

不同业务的容错要求差异很大:纯线上软件业务(日志/版本/数据库备份/Git)恢复能力强;线下业务、资金业务、医疗操作、对外沟通恢复成本高。恢复能力弱的业务要增加控制机制:执行前预览、分级授权、关键节点确认、沙箱环境、版本管理、操作留痕、人工接管、回滚方案。

> **渐进授权**:高风险场景先让 Agent 负责分析、建议、准备材料,由人完成最终提交;随评测数据积累,再逐步开放部分执行权限。

### 组织与人才:从架构到组织的闭环

- **组织变化是渐进的**:企业更可能先改变工作边界、再调整岗位名称——PM 承担更多原型和代码,工程师参与更多需求定义,业务人员构建简单自动化,测试人员建立 Agent 评测体系,PM 负责人与 Agent 的协作流程,FDE 承担场景理解、方案设计和落地交付;
- **招聘四维度**:
  1. **基础素质**:聪明(学习速度)、乐观(相信值得投入)、皮实(失败后继续探索)、自省(持续复盘成长);
  2. **专业能力**:级别对应负责范围(P5 功能 → P6 模块 → P7 产品 → P8 产品线 → P9 创造业务),高级别需"平地抠饼"能力——方向不清晰、资源不完整时定义目标并推动落地;
  3. **业务能力**:理解客户是谁、行业怎么运转、谁在赚钱、利益如何分配、需求共性与定制、产品如何商业化;
  4. **组织能力**:推动项目、处理冲突、获得资源、管理预期,同时避免成为团队高风险项。
- **Agent 领域无成熟范式**:大多数候选人缺完全匹配的项目经验,招聘时更看重学习能力、场景理解和动手能力;Agent PM 与 Agent 工程师的学习重点也因此不同(PM 重业务拆解与交付管线设计,工程师重 Context 装配与 Harness 工程)。

## 总结

全文围绕一件事:**企业怎样让 Agent 长期、稳定地完成有价值的任务**。三条线汇合:

- **架构线**:Agent Loop、Harness、Tool、Skill、Context、Memory、任务调度、治理机制共同支撑长期运行;
- **业务线**:围绕真实任务设计 Pipeline,明确输入、输出、责任人、交付标准和异常处理;
- **组织线**:重新划分人与 Agent 的职责,调整岗位边界、协作方式、评价体系和人才要求。

生产级 Agent 的完整闭环:**先找到值得解决的业务问题 → 搭建可持续交付的系统 → 把实践经验沉淀为 Tool/Skill/Pipeline/评测集 → 形成组织可反复使用的生产能力**。理论框架只能帮团队少走弯路,真正的坑点藏在真实故事里(为什么做 Agent、第一版架构、踩过哪些坑、方案迭代了几次、哪些能力最后被放弃)——这些真实经验才是生产级 Agent 最有价值的部分。
