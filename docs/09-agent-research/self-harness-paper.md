# Self-Harness 论文解析:让 Agent 学会改造自己的"操作系统"

> **一句话摘要**:Self-Harness(arXiv:2606.09498)把 Agent 的 **harness(系统提示/工具/运行时机制/验证规则/编排逻辑/权限策略/故障恢复)视为可迭代的外部状态**——不改模型权重、不换更强老师,让同一个固定模型**根据自己失败轨迹提出小步改动,再用回归测试决定是否升级**。核心循环:Weakness Mining(弱点挖掘)→ Harness Proposal(提议)→ Proposal Validation(回归验证)。在 Terminal-Bench-2.0 上三个模型全部提升,held-out 也涨(最大绝对增益 21.4 个百分点、最大相对提升 138%)。
>
> **来源**:论文《Self-Harness:让 Agent 学会改造自己的"操作系统"》,https://arxiv.org/abs/2606.09498;公众号解读「如果 AI 可以重来」,https://mp.weixin.qq.com/s/vp16cIvTY4G-syT2HApNbA;原始资料存档于 `docs/inbox/self-harness-source.md`

## 概念:为什么需要 Self-Harness

**Harness = Agent 的操作系统**:模型是内核能力,harness(系统提示、工具、运行时机制、验证规则、编排逻辑、权限策略、故障恢复)决定能力如何被调度、约束和修复——往往决定 Agent 的上限和稳定性。

**过去改进 harness 的两条路**:

1. **人类工程师手工调参**:有效,但模型发布越来越快,不同模型的工具习惯、错误模式、提示敏感性都不同——给每个模型手工定制最优 harness 成本越来越高;
2. **Meta-Harness 类方法**:用更强的外部 Agent/优化器改弱模型的 harness——仍依赖外部更强能力;若目标模型已是前沿模型,或外部模型不了解目标模型的具体失败模式,优化会变贵、变慢、变偏。

**Self-Harness 的核心转向**:

> 不是让人来改,也不是让另一个更强 Agent 来改,而是让**目标 Agent 在当前 harness 下观察自己的失败,用结构化证据提出候选修改,通过回归测试决定哪些修改真正进入下一版 harness。**

### 改的是什么:非参数化改进

- **不变的**:模型权重、解码配置、工具集、评估器;
- **被优化的**:模型外部那层**可声明、可审计、可回滚的执行协议**。

关键洞察:很多 Agent 失败不是"模型不知道答案",而是**执行协议(SOP)出了问题**——答案算出来了但忘了写入评分器要求的文件、工具报错后反复重试同一坏命令、长时间探索不进入实现验证、跨 shell 命令丢失环境变量/路径/安装状态、未检查产物就声称完成。**这些问题适合用可测试的 harness 迭代解决,不一定适合微调。**

## 原理:三步核心循环

### 第一步:Weakness Mining(弱点挖掘)

让固定模型在当前 harness 下跑一批 **held-in 任务**,收集执行轨迹和验证器结果。重点不是看几条失败案例,而是把失败记录按**验证器拒绝原因、Agent 侧因果行为、可复用行为机制**聚类——避免把表面症状当根因(两个任务都因缺文件失败,一个是忘了创建工件、另一个是工具错误后删了文件,所需修改不同)。

### 第二步:Harness Proposal(提议)

同一个固定模型在"提议者"角色下读取证据包,生成**多个彼此不同但尽量最小**的候选 harness 修改。每个候选必须说明:目标失败模式、修改的可编辑表面、预期行为效果、潜在回归风险。

两个实用约束:

- 不能**大规模重写整体架构**;
- 不能只写泛泛的"以后要更仔细"——必须把失败模式映射到具体 harness 表面(新增验证指导、限制工具循环、加入工件恢复策略、修改运行时策略)。

### 第三步:Proposal Validation(回归验证)

候选修改不会因为"听起来合理"就被接受。每个候选 harness 重新评估,并**同时检查 held-in 和 held-out 两个分割**。接受规则很保守:

!!! tip "接受门限"
    **held-in 不退步、held-out 不退步,且至少一个分割的通过数提升。** 只在一个分割上变好、另一个变差的候选,会被拒绝。

这让 Self-Harness 更像**经验性的状态转换**:每次升级留下证据——想改变什么行为、改了哪个表面、为什么改、评估结果是否支持升级。

## 代码 / 实现:实验设置

| 实验控制项 | 论文设置 |
| --- | --- |
| 基础模型 | MiniMax M2.5、Qwen3.5-35B-A3B、GLM-5 |
| 初始 harness | 基于 DeepAgent 的极简 harness(简短系统提示 + 默认文件/编辑/shell 工具) |
| 被固定的部分 | 模型、解码配置、工具集、预算、基准环境、评估器 |
| 被允许改变的部分 | 声明式 harness 配置界面(指令、验证指导、运行时策略) |
| 基准 | Terminal-Bench-2.0(容器化终端环境,确定性验证器判断最终容器状态) |
| 主要指标 | 通过率 Pass %,每个候选在两次重复尝试上计算 |

实验用固定的 64 个案例子集(排除依赖不稳定外部网络或多模态输入的任务,减少环境噪声)。

## 实践 / 应用:实验结果与工程启发

### 结果:三个模型都涨,held-out 也涨

| 模型 | held-in | held-out | overall |
| --- | --- | --- | --- |
| MiniMax M2.5 | 43.0 → 50.0(+16%) | 40.5 → 61.9(+53%) | 42.2 → 53.9(+28%) |
| Qwen3.5-35B-A3B | 15.1 → 36.0(+138%) | 23.8 → 38.1(+60%) | 18.0 → 36.7(+104%) |
| GLM-5 | 47.7 → 57.0(+20%) | 42.9 → 57.1(+33%) | 46.1 → 57.0(+24%) |

**最大绝对增益 21.4 个百分点,最大相对提升 138%**;held-out 提升说明修改不是只修补已见失败案例;接受门限阻止了"牺牲一个分割换另一个"的升级。

### 学到的不是通用鸡汤

不同模型保留的 harness 修改明显不同:

- **MiniMax M2.5**:主要问题是缺失必需工件、结构化工具内容格式错误、工具循环停滞 → 最终 harness 鼓励更早创建输出文件、更谨慎处理内容标签、工具交互过长时重定向执行;
- **Qwen3.5-35B-A3B**:主要收益来自依赖预检查、避免重复失败命令、打破探索循环、工具错误后工件恢复(extract-elf 案例:从反复覆盖/编辑失败拉回到"恢复缺失文件并验证 JSON 输出");
- **GLM-5**:集中在跨 shell 会话保持环境设置、从长时间探索转向实现和测试(解决"环境状态丢失"和"探索太久不落地")。

**同一初始 harness 暴露的失败模式随模型而变——有效的 harness 优化,应把模型特定弱点变成具体、可执行、可验证的运行规则。**

### 对 Agent 工程的四条原则

1. **把 harness 当成版本化资产**:好的 Agent 经验不应散落在聊天记录里,应沉淀为可编辑、可审计、可回滚的 harness 配置;
2. **用轨迹证据驱动修改**:不要因一条失败日志就改 prompt——先看失败是否重复、根因是否一致、能否映射到可改的执行表面;
3. **保持小步修改**:单次编辑越大,越难判断哪条规则产生效果,也越易破坏原本成功的行为;
4. **必须有回归门**:harness 改动不能只看"这次好了没",还要看其他任务有没有变坏——没有 held-out/回归测试,自我改进很容易变成自我过拟合。

### 局限性(论文自承)

- 研究的是**固定基准下的有界 harness 编辑**,不是开放域、自主长期运行的自我改进系统;
- 效果依赖三个前提:**验证器足够可靠、执行轨迹支持合理归因、任务分布与评估分割差异不大**;
- 接受规则基于通过率非回退——对操作真实账户/付费接口/生产资源的高风险 Agent,需要更强的安全门限、人工审计和对抗测试。

## 总结

- **定位**:Self-Harness 让固定模型根据自己失败轨迹改造自己的 harness——非参数化改进(权重/解码/工具集/评估器不变,只改可声明、可审计、可回滚的执行协议);
- **三步循环**:Weakness Mining(聚类失败根因)→ Harness Proposal(最小有界修改,映射具体表面)→ Proposal Validation(held-in + held-out 双分割回归门);
- **结果**:Terminal-Bench-2.0 三模型全涨(+16%~+138%),held-out 也涨,无单分割退步;
- **模型特定性**:同一初始 harness 暴露的失败模式随模型而变,有效优化是把模型弱点变成具体可验证的运行规则;
- **四原则**:harness 版本化资产、轨迹证据驱动、小步修改、回归门;
- **局限**:有界编辑非开放进化,依赖验证器可靠性与归因质量,高风险场景需更强安全门限;
