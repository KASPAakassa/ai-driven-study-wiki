企业Agent什么时候必须停下来等人？看后果，不看信心

企业 Agent 在高风险动作前进入等待人工确认状态《企业 Agent 工程化手记》第 5 篇。
前四篇我依次写了：怎么不让 Agent 走错（任务边界）、工具太多为什么会失控、它走错之后系统怎么收场（异常恢复）、以及怎么让系统记住自己做到了哪一步（状态机）。
这一篇补最后一块、也是最容易被自动化冲动盖掉的一块：什么时候，这一步必须停下来，交给人。
如果只记一句，就是：
Agent 可以自动生成建议，但不能自动替人承担业务后果。
很多企业 Agent 真正出问题，不是因为它不会做，而是因为它把"能做"误当成了"该做"。
我的结论先放前面：
不要用"模型有没有把握"来判断要不要接管。
要用"这个动作发生之后，后果会不会进入真实业务系统"来判断。
换句话说：
草稿可以自动，生效必须确认；内部分析可以自动，对外触达默认确认。
最危险的不是跑不动，而是跑得太顺
这半年重构 CRM Agent，我有个反直觉的体会：Agent 自动化做得越顺，我越紧张。
因为顺的意思是——它会把一个"本该有人看一眼"的动作，也一起顺手做了。给客户群发提醒、批量改客户阶段、删掉一批它判断为重复的记录，这些动作模型执行起来和"查一条数据"没区别，但后果完全不是一个量级。
上一篇说状态机让系统知道自己停在哪一步。这一篇的问题是：哪一步，本来就应该是"停下等人"？
最近一段业务系统开发记录里，我反复遇到同一个问题：业务规则看起来已经说清楚了，Agent 很容易把下一步也顺手做掉。
这一步是什么？
把规则写进账号开通和权益生效链路。
从模型视角看，它只是多处理几个账号名。从业务系统视角看，它是一个边界完全不同的动作。
比如有一条账号开通规则：某些系统账号不能按普通业务账号处理，其中一部分还要根据组织上下文派生出对应账号。
这条规则本身不复杂。
真正复杂的是：它到底只影响新开通账号，还是会碰到历史账号？它只是补一条识别规则，还是会顺手改相邻流程？它只是调整某个自动化入口，还是会把原本属于其他系统的主流程也接过来？
这些问题，不能交给模型自己猜。
所以后来我在这类需求上会先把接管点写清楚：Agent 可以只读确认账号开通链路，可以列出规则命中的脱敏样例，可以说明准备影响哪一段流程；但一旦准备把规则写入真实的开通 / 权益生效链路，就必须停下来等人确认影响范围。
这里面有三个真实细节。
第一，账号规则不是孤立字段。某个派生账号看起来只是字符串，但它落在开通链路里，影响的是系统账号能不能被正确识别、后续业务账号会不会被误处理。规则一旦写错，不是页面文案错了，而是开通结果错了。
第二，范围很容易被 Agent 自动扩大。用户要的是"账号开通时按某类规则识别系统账号"，但相邻链路上还有其他流程、历史数据和既有记录。任何一个被顺手改到，后果都不是同一类问题。
第三，业务归属不一定在当前系统里。有些主流程已经由外部系统负责，当前系统只做增强记录和执行跟踪。如果 Agent 没停下来确认归属边界，很容易从"补后续跟踪"扩成"接管主流程"。
所以这一篇虽然继续服务 CRM Agent 这个主线，但我不把这条素材包装成"某次 CRM 生产事故"。
更诚实的说法是：我在最近的业务系统开发里，已经把"写入账号开通规则"、"影响权益生效结果"、"改变后续跟踪触发线"都当成必须人工接管的动作来设计。它们和 CRM 里的批量改客户阶段、对外发提醒是同一种问题：动作一旦发生，影响会进入真实业务链路，不能只靠模型自信往前跑。
后来我给这类需求加了一条很朴素的判断线：
只要 Agent 准备从"解释规则"进入"让规则生效"，就不能继续自动跑。
解释规则，是只读的。
列影响范围，是只读的。
生成脱敏样例，也是只读的。
但把规则写进开通链路、让它影响后续权益、让它触发相邻流程，这些都已经是业务动作。
业务动作要停下来。

业务规则进入真实链路前先进入人工确认流程

接管不是信心问题，是后果问题
很多人设计人工接管，第一反应是"模型不确定的时候就问人"。
我试过，行不通。模型对很多危险动作恰恰很"确定"，而对一堆无关紧要的小事反复犹豫。用信心做触发，结果是人被一堆"确认吗"淹没，真正危险的动作反而被自信地放过了。
站在企业系统开发负责人的角度，我判断接管点时，不先问模型有没有把握，而先问三件事：这个动作可不可逆？代价超没超阈值？它有没有越权？
所以真正该停下等人的，是三类动作：
不可逆：发出去就收不回的。给客户发邮件、对外通知、删除数据、提交事务。

代价超阈值：金额、影响范围、记录条数超过你设的线。改 1 条客户阶段和批量改 500 条，不是一回事。

越权：它动了自己身份不该动的东西。这一条留到下一篇细讲。

判断接管点，判断的是动作的后果，不是模型的信心。
拿账号开通这个例子看，规则能跑通只能说明"当前样例没有发现问题"。它不能说明相邻流程和历史数据都不受影响，也不能说明业务归属方已经接受这次边界变化，更不能说明这条规则应该直接进入真实开通链路。
所以它命中的不是"模型不确定"。
它命中的是"后果进入业务系统"。
我现在会把接管点分成四档。
第一档，只读分析。比如查当前规则、解释字段含义、列可能影响的业务对象。可以自动做。
第二档，可撤销草案。比如生成待确认的开通规则、生成待审批的话术、生成待执行的客户跟进建议。可以自动生成，但不能自动生效。
第三档，真实写入。比如修改客户阶段、改开通规则、写入业务状态、创建任务。必须看影响范围，满足条件才允许继续。
第四档，不可逆外发。比如对客户发送消息、提交审批、触发外部系统后续动作。默认停下来等人，除非这条动作已经被系统规则明确证明可以自动执行。
这四档的关键区别不是技术难度，而是后果半径。
后果只停留在草稿里，可以自动。
后果进入业务系统，要接管。
后果发给外部对象，默认接管。
这也是我现在设计企业 Agent 时最常用的一条传播给团队的规则：
不要问模型有多自信，先问后果会走到哪里。

function should_handoff(action):
  if action.kind == "read_only":
    return false

  if action.kind == "draft":
    return false

  if action.effect == "write_business_state":
    return true

  if action.effect == "send_to_external_party":
    return true

  if action.impact_count > policy.max_auto_items:
    return true

  if action.owner_boundary == "unclear":
    return true

  return false
这段伪代码故意没有写"模型置信度"。
因为我不希望系统问的是：
模型有多确定？

我希望系统问的是：
这个动作会不会写入业务状态、触达外部对象、超过影响范围，或者跨过业务归属边界？

把"人工接管"做成工程，而不是弹窗
确定了"哪些动作要停"，还要把它落成系统能力，而不是一个临时弹窗。四个设计点：
把"等人"做成一个合法状态。接上一篇——状态机里要有 等待人工确认 这个状态，Agent 进到这一步就停住、持久化、不往下走，等批准信号再续跑。它不是流程中断，是流程的一部分。

触发条件写成显式规则。不可逆 / 超阈值 / 越权，写成代码能判断的条件，不靠模型自觉。模型负责执行，规则负责拦截。

接管要给人足够上下文。不是弹一个"确认吗"，而是告诉人：它想做什么、为什么这么判断、会影响哪些数据。人要能在三秒内看懂、做决定，否则审批会变成无脑点"同意"，等于没有。

接管动作要留痕。谁批的、什么时候批的、基于什么信息批的。这不是为了好看，是为了出事之后能追溯到人——企业系统里，"谁负责"必须有答案。

这四点放回最近的账号开通 / 权益生效链路里，也完全成立。
等待人工确认 不是一句提醒，而是一个状态。Agent 到了这个状态，只能报告规则命中的脱敏样例、影响的新开通范围、明确不碰相邻流程和历史数据，不能继续写入真实链路。
触发条件也不是"感觉危险"。它可以写得很明确：准备改变账号开通规则；准备影响权益生效结果；准备写入多个业务范围的系统账号；准备改变主流程归属。
上下文也不能只给一句"是否确认"。至少要给人看三样东西：它准备改哪类业务规则，已经用哪些脱敏样例验证过，还有哪些链路明确不在本次范围内。
留痕更重要。谁批准了这次规则生效，批准前看到的脱敏样例是什么，为什么确认不影响相邻流程和历史数据，这些信息以后都可能成为排查问题的入口。
如果要把它做得更像一个工程能力，我会要求接管请求里至少有六块信息：
第一，动作类型。它是只读、草案、真实写入，还是不可逆外发。
第二，业务对象。它会影响哪一类客户、账号、订单、审批或任务，不要只写"一批数据"。
第三，影响范围。影响多少条、哪些状态、是否跨组织或跨流程。
第四，触发理由。为什么系统判断这一步需要接管，是不可逆、超阈值、越权，还是业务归属不清。
第五，建议动作。人不是来读日志的，人要能直接选择：批准、驳回、缩小范围、改成草案、转给业务 owner。
第六，恢复路径。如果这一步批准后失败，系统下一步是重试、回滚、暂停，还是继续交给人。
少了这六块，人工接管很容易退化成一个按钮。
按钮看起来让人参与了，实际上只是把责任甩给人。
真正有价值的人工接管，是让人基于足够上下文做业务判断，并且让系统知道批准之后该怎么继续。
这套规则怎么拿去用
如果你正在把 Agent 接进业务系统，不需要一开始就设计很复杂的审批平台。
先把每个工具、每个动作、每条自动化链路过一遍这四个问题：
第一，它只是读数据，还是会写业务状态？
第二，它只是生成草案，还是会让规则真正生效？
第三，它只是影响当前对象，还是会扩大到一批客户、账号、订单、审批或任务？
第四，它只是内部处理，还是会触达客户、合作方或外部系统？
只要有一个答案进入后半句，就不要让 Agent 直接执行。
先让它生成接管请求，把动作、对象、范围、理由、建议和恢复路径说清楚，再交给人判断。
这一步做完，人工接管就不再是"怕出错所以加个弹窗"。
它会变成企业 Agent 的刹车系统：
平时不打扰。
真到业务后果要落地的时候，必须踩住。

function advance(task, action):
  if should_handoff(action):
    task.status = "waiting_for_human"
    task.pending_action = action.summary
    task.handoff_context = build_context(action)
    task.resume_policy = decide_resume_policy(action)
    save(task)
    notify_owner(task)
    return

  execute(action)
  task.status = next_status(task, action)
  save(task)

function resume_after_approval(task, approval):
  if task.status != "waiting_for_human":
    return

  if approval.decision == "reject":
    task.status = "stopped"
    save(task)
    return

  if approval.decision == "narrow_scope":
    task.pending_action = apply_scope_limit(task.pending_action, approval.scope)

  execute(task.pending_action)
  task.status = next_status(task, task.pending_action)
  task.approved_by = approval.owner
  save(task)
这里最重要的不是代码本身，而是两个设计选择。
第一，waiting_for_human 是一个正式状态，不是异常。
系统进入这个状态以后，不能继续偷偷往下跑。
第二，批准以后不是简单地"继续"。
人可能批准，也可能驳回，也可能要求缩小范围。状态机要能接住这三种结果。
