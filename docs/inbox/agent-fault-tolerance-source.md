# 原始资料:Agent 容错设计:不止于重试的完整思路

> 来源:用户提供(方法论文案);抓取日期:2026-08-09
> 状态:已整理为正式文章 docs/03-agents/agent-fault-tolerance-design.md

## 核心内容(原文)
面对工具调用失败,优秀的 Agent 容错设计远不止"重试"。核心在于建立系统性工程思维:将错误分类,针对不同类型故障采取精准策略,实现"失败得体面,恢复得优雅"。

### 第一步:错误分类定界(三层面)
- 调用前(歧义层):LLM 生成参数后执行前——参数名错误/类型错误/必填字段缺失(参数幻觉)
- 调用中(执行层):HTTP 超时/服务挂了/限流 429/5xx
- 调用后(语义层):结果为空/格式无法解析/数据内容错误

### 分层应对
- 调用前(预防参数幻觉):Schema 校验(Pydantic/Zod)+ 错误反馈修正(校验失败反馈 LLM 自我修正)+ 防函数签名漂移(定期对比期望 Schema 与 API 实际返回)
- 调用中(韧性三件套):指数退避重试(1s,2s,4s+随机抖动防惊群;只对暂时性错误重试)+ 超时控制(硬超时+超时信号交 Agent 决策)+ 断路器(连续失败达阈值熔断,冷却后半开试探恢复)
- 调用后(语义错误):区分"成功但无结果"与"执行失败";优雅降级(工具优先级列表,高级不可用降级备选,如语义搜索→关键词搜索)+ 人类兜底(所有降级失败后,携带完整错误上下文和已尝试恢复步骤,暂停请求人工介入,不静默失败)

### 完整架构与核心难点
- 可观测性层:架构基石(分布式追踪/错误分类/熔断指标/告警),否则生产"盲飞"
- LLM 非确定性是核心难点:结构化错误处理(Prompt 告知特定错误如 429 的具体操作流程)+ 状态机约束(关键路径限定行为)+ 幂等性(发邮件/下单等非幂等操作注意重试重复执行)

### 总结
健壮容错 = 预防 + 执行控制 + 降级 + 观测有机结合;不保证永不失败,但确保失败得体面,恢复得优雅。
