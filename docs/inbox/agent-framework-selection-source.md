上一篇，我们没用任何框架，手写了一个 196 行的 Agent。核心就是那个循环：模型决定调什么工具，你的代码执行，再把结果塞回去。
接下来很自然会遇到一个问题：既然循环不复杂，为什么还有这么多 Agent 框架？到底该学哪个？
我一开始也想找一张“功能对比表”，看谁支持工具、记忆、多 Agent、MCP，打勾最多就选谁。后来发现这条路基本没用——现在主流框架该有的能力大多都有，真正的区别不是“能不能做”，而是：
你准备把哪一层控制权交给框架？
有的框架只替你接管 while 循环；有的连状态、恢复和分支一起管；还有的直接让你用“研究员、审核员、经理”来描述系统。抽象越高，上手越快，但出问题时要穿透的层也越多。
这篇不评“谁最强”，只画一张后端能落地的选型地图。
本文技术资料核验于 2026 年 8 月 9 日。版本号和框架状态来自各项目官方文档、官方仓库及软件包发布页。
先看地图：框架其实在替你接管不同的层

Agent 框架地图
把一个 Agent 系统从下往上拆，大致有三层：
1.循环层：模型调用、工具执行、结果回填、停止条件
2.运行时层：状态、分支、持久化、中断恢复、人工审批
3.协作层：多个 Agent 的角色、委派、交接和团队流程
上一篇的 196 行代码，三层都由我们自己管。框架的价值，就是从这里面接走一部分。

OpenAI Agents SDK：最像“给上一篇代码装上工程配件”
如果把上一篇的 run_agent() 交给一个 SDK 管，OpenAI Agents SDK 是最顺手的理解方式。
它的核心抽象不多：Agent 定义指令和工具，Runner 负责循环；需要多个专家时，可以把 Agent 当工具调用，也可以用 Handoff 把会话控制权移交出去。除此之外，它内置了 Session、Tracing、Guardrail 和可暂停恢复的人工审批流程。
后端类比一下：它不是一个工作流平台，更像一个带中间件和链路追踪的 Agent Runtime SDK。
适合它的场景：
·需求还是“一个 Agent + 一组工具”为主
·想少写循环、重试、会话和 trace，但保留普通代码的可读性
·Python 或 TypeScript 项目，希望很快接进现有服务
·多 Agent 只是局部委派，不是整个系统的建模中心
它并不等于只能调用 OpenAI 模型，SDK 提供模型与 Provider 扩展入口；但它的接口演进、托管工具和观测体验天然围绕 OpenAI 生态展开。如果你的核心要求是彻底的厂商中立，要把模型适配和迁移成本单独评估，不能只看“接口兼容”。
我的判断：学完手写循环后，想最快进入框架世界，可以先从它开始。它增加的抽象最少，你还能看见上一篇里的每个零件。
LangGraph：不是 Agent 模板，而是“可恢复的状态机”
LangGraph 官方对自己的定位很克制：一个面向长时间运行、有状态 Agent 的低层编排框架和运行时。它甚至明确提醒，新手如果只想快速做一个 Agent，可以先用更高层的 LangChain Agents。
这句话很重要。LangGraph 的核心卖点不是“少写几行工具调用”，而是下面这些工程问题：
·一个任务跑到第 8 步服务重启了，能不能从断点继续？
·某一步要人工审批，能不能暂停几小时后恢复？
·哪些节点必须按固定逻辑执行，哪些节点允许模型自主决策？
·状态如何持久化，分支怎么回放，失败路径怎么定位？
你会定义 State，把模型调用、工具执行、审核等动作做成 Node，再用 Edge 描述流转。它很像我们熟悉的状态机 + 工作流引擎 + checkpoint，只不过节点里可以放 LLM。
适合它的场景：
·长任务、强状态、需要中断恢复
·固定流程和 Agent 决策混在一起
·人工审批、失败重跑、审计要求明确
·团队愿意为可控性接受更多图结构和状态设计
代价也很直接：简单问题会显得重。一个本来 40 行能讲清的循环，放进图里要多出 State、Node、Edge、Checkpoint 等概念。如果你的 Agent 还没遇到“恢复、分支、审批”这些痛点，提前上 LangGraph，可能只是把业务复杂度换成了框架复杂度。
我的判断：它不是默认起点，而是复杂度真的长出来之后的升级路线。
CrewAI：当“角色协作”本身就是业务模型
CrewAI 最有辨识度的抽象是 Crew：给 Agent 分角色、目标和工具，再把任务交给这支团队。当前官方架构同时强调两部分：
·Flow 管状态、事件和确定性的整体流程
·Crew 在某个步骤里组织多个 Agent 自主协作
官方甚至直接建议，生产应用从 Flow 开始，再在确实需要创造性协作的节点里调用 Crew。这个变化挺值得注意：多 Agent 最后还是需要一个可控的外壳。
适合它的场景：
·研究、内容生产、方案评审等任务，天然能描述成多个专业角色
·业务方能直接理解“研究员 → 撰稿人 → 审核员”的协作方式
·快速验证一个多 Agent 分工假设，比精细控制每一步更重要
风险也来自同一个地方：角色越多，不代表效果越好。每增加一个 Agent，就增加一组 Prompt、上下文、模型调用和故障点。一个普通函数能完成的校验，没必要请一个“质量审核 Agent”再思考一遍。
我的判断：只有当“谁和谁协作”是需求本身时才优先选 CrewAI。不要为了展示多 Agent，先画组织架构，再倒推业务。
Eino：Go 团队终于不用先把系统拆成 Python 边车
如果团队主力是 Go，Eino 是这张地图里最值得单独看的路线。
它不是简单照搬 Python 框架的 API，而是按 Go 的习惯拆成几层：
·Components：ChatModel、Tool、Retriever、ChatTemplate 等组件接口
·Compose：用 Chain / Graph 组合确定性流程，统一处理流式数据
·ADK：提供工具调用、上下文管理、多 Agent、Interrupt / Resume 等 Agent 能力
·Callback：在组件、图和 Agent 的固定切面接日志、Tracing 和指标
这套设计对后端很友好：普通业务流程可以继续写成确定性的 Graph，需要自主决策时再把 Graph 暴露成 Tool 交给 Agent。不是所有东西都塞进一个大 Agent。
适合它的场景：
·现有服务和基础设施主要是 Go
·在意类型约束、并发、流式处理和服务内集成
·希望 Agent 跟业务代码部署在同一个技术栈里
·愿意跟进一个仍在快速演进、尚未到 1.0 的生态
Go 里还有 LangChainGo。它更像 LangChain 的 Go 实现，模型、向量库等组件覆盖不少；但截至核验日，最新 release 是 v0.1.14，发布于 2025 年 10 月。对新的 Agent 编排项目，我会优先评估发布更活跃、同时具备 Compose 和 ADK 路线的 Eino；如果你只是需要某个 LangChain 风格的组件集成，再具体比较 LangChainGo。
我的判断：Go 项目不必为了“AI 生态都在 Python”默认引入一套新运行时。先看 Eino 能不能覆盖需求，再决定是否跨语言。
还有 Google ADK，要不要一起学？
Google ADK 当然在地图上。它在 2026 年已经进入 2.x，核验时 Python 包版本是 2.6.3，同时提供 Agent、图式 Workflow、Task 委派、评估和部署工具。
如果你的模型与基础设施明显偏 Gemini / Google Cloud，它应该进入第一轮候选。但对一个还没绑定云平台的后端初学者，同时铺开 LangGraph、OpenAI Agents SDK、CrewAI、Google ADK 没什么意义——它们的概念大量重叠，先吃透一条路线，迁移时再对照会快得多。
一张选择路径，别从“最火”开始

Agent 框架选择路径
把选择压缩成五个问题：
4.流程能提前写死吗？ 能就先写普通 Workflow，别上 Agent 框架。
5.主项目是 Go 吗？ 是就先评估 Eino，避免无意义地增加 Python 边车。
6.只是想接管工具循环吗？ Python / TypeScript 优先看 OpenAI Agents SDK。
7.需要持久化、暂停恢复、人工审批和复杂分支吗？ 看 LangGraph。
8.多角色协作就是产品核心吗？ 看 CrewAI；Google 技术栈则同步看 ADK。
如果还是拿不准，我建议从抽象最低、能解决当前问题的方案开始。因为从轻量 SDK 升级到图运行时，通常是增加状态和编排；反过来从一个深度绑定的图或角色系统里抽身，迁移成本要高得多。
真正该提前防的，是迁移成本
框架以后大概率会换，业务工具和状态数据最好别跟着陪葬。写第一版时就守住四条边界：
工具保持普通函数。 参数和返回值用清晰 schema，别让业务逻辑只能在某个框架的装饰器里运行。
状态结构自己定义。 会话、任务状态和审批记录放在你能控制的存储里，框架 checkpoint 是运行机制，不该成为唯一数据源。
模型调用留适配层。 “兼容 OpenAI 接口”不等于行为完全一致，工具调用、流式事件和错误结构都可能不同。
Tracing 从第一天就接。 框架帮你隐藏了循环，也会顺手隐藏故障现场。至少要能看到每次模型调用、工具参数、状态变化、耗时和 token。
这四件事，比争论哪个框架多两个功能更值钱。
写在最后
框架选型本质上是在做一笔交易：用控制权换开发速度，用抽象换工程能力。
我的当前选择很明确：
·Python / TypeScript 的简单 Agent，从 OpenAI Agents SDK 这类轻量 SDK 起步
·复杂、长时间、有审批和恢复要求的系统，用 LangGraph 管运行时
·角色协作确实是业务本体，再用 CrewAI
·Go 项目优先评估 Eino，不默认拆 Python 服务
这不是永久答案。Agent 框架还在快速变化，所以真正要学的不是某个 API，而是循环、状态、工具、恢复和可观测性这些不会过时的工程问题。
下一篇预告：同一个订单分析 Agent，用 Python 和 Go 两条路线分别实现。到时候不看宣传页，直接看代码量、类型约束、流式处理和调试体验到底差在哪。
