大家好，我是程序员无隅。
当两个开发任务同时落到一个仓库时，很多人首先想到的是“多建两个分支”。分支确实隔离了提交历史，却没有自动提供两个可以同时工作的文件目录：当前目录里仍然只有一份文件、一份暂存区和一个检出的 HEAD。
这在人工开发时通常只是切分支不方便；到了 Coding Agent 并行执行的场景，它会变成真实的工程风险。一个 Agent 刚修改完接口但还没提交，另一个 Agent 就可能读到这个中间状态，甚至继续覆盖同一批文件。
Git Worktree 的核心价值，是让同一个仓库拥有多个相互独立的修改现场。
1. 从一个真实问题开始：多个任务同时修改代码为什么容易互相污染
假设一个需求需要同时完成两件事：
任务 A 修改服务端接口，把返回字段 name 改成 display_name；

任务 B 修改客户端调用，让它读取新的字段。

如果两个执行者共用同一个工作目录，理想情况是 A 先完成，B 再基于稳定接口修改。但在并行执行中，更常见的是下面这条链路：
A 修改了接口文件，但尚未提交；

B 在同一个目录中读取代码，看到 A 的半成品；

B 修改客户端，同时运行测试；

A 又调整接口定义，覆盖或破坏 B 的假设；

最后一次测试只证明“某个瞬间的目录状态可以运行”，无法证明两项改动分别正确。

这不是传统意义上的 Git 合并冲突。Git 甚至还没有机会介入，因为冲突发生在提交之前：多个执行者正在同时读写同一份工作区状态。
人工协作里，我们可以通过口头约定“你先别动这个文件”降低风险；Agent 不会天然拥有这种同步机制。即使给每个 Agent 分配了不同文件，接口变化、生成文件、格式化工具和测试缓存仍可能让它们互相影响。
所以，开始并行之前需要先回答一个问题：每个任务是否拥有自己的文件系统边界？
2. Worktree 的本质：共享 Git 对象，隔离工作目录、HEAD 和 index
Git 官方对 Worktree 的定义是：一个仓库可以关联多个工作树，从而同时检出多个分支。除了最初的主工作树，还可以创建零个或多个 linked worktree。
Worktree 并不是重新 git clone 一遍仓库。多个工作树共享仓库中的对象库、引用和提交历史，但每个工作树拥有自己的：
工作目录：磁盘上实际可见和可编辑的文件；

HEAD：当前检出的提交或分支；

index：暂存区；

未提交修改与未跟踪文件。

在 linked worktree 根目录中，.git 通常不是一个完整目录，而是一个指向主仓库管理数据的文件。Git 再通过 $GIT_DIR/worktrees/<id> 保存这个工作树的私有状态，通过公共 Git 目录访问共享对象。
因此，Worktree 同时获得了两种能力：
第一，隔离修改现场。 任务 A 的未提交修改不会突然出现在任务 B 的目录中。
第二，复用仓库历史。 创建新工作树不需要重新下载和存储完整的提交对象，通常比再次克隆仓库更快、更节省空间。
这里还有一个重要约束：Git 默认不允许同一个本地分支同时被多个工作树检出。这个限制不是故意增加麻烦，而是在阻止两个目录同时推进同一个分支，避免分支指针和工作区状态失去清晰归属。
3. Worktree 的完整使用链路：创建、开发、提交、合并、清理
一个可靠的 Worktree 流程不是执行一次 add 就结束，而是完整覆盖创建、交付和回收。

开始前，先检查当前仓库已经关联了哪些工作树：
git worktree list从 main 创建一个新分支，并把它检出到相邻目录：
git worktree add -b feature/api ../repo-api main这条命令同时完成两件事：
创建 feature/api 分支；

创建 ../repo-api 工作目录并检出该分支。

进入新目录后，开发过程与普通仓库没有区别：
cd ../repo-api
git status
git add .
git commit -m"feat: update api contract"任务完成后，回到用于集成的工作树。可以合并整个分支：
git switch main
git merge --no-ff feature/api如果 Agent 分支中只有一个明确、可独立集成的提交，也可以只挑选该提交：
git cherry-pick <commit-sha>无论使用哪种方式，最终测试都应该在集成后的工作树中运行。子任务自己的测试只能证明局部修改成立，无法证明多个任务组合后仍然成立。
确认修改已经提交、集成或不再需要后，再移除工作树：
git worktree remove ../repo-api如果有人绕过 Git 直接删除了工作树目录，仓库里可能残留管理信息。这时可以先查看，再清理已经失效的记录：
git worktree list
git worktree prune --dry-run
git worktree prune不要一遇到删除失败就使用 --force。正常情况下，Git 拒绝删除带有未提交修改或未跟踪文件的工作树，正是在保护尚未交付的成果。
对于只想做实验、不准备长期保留分支的任务，可以创建 detached worktree：
git worktree add --detach ../repo-experiment HEAD如果实验结果值得保留，再从其中创建分支并提交即可。
4. Worktree 如何为多个 Coding Agent 提供文件系统隔离
在多 Agent 编程中，可以把主工作树看成集成区，把 linked worktree 看成各个 Agent 的独立施工区。
一条典型链路如下：
主 Agent 分析任务依赖，确认哪些子任务可以并行；

为每个写代码的子任务创建独立分支和 Worktree；

将任务目标、允许修改的路径、接口约定和验证命令一起交给子 Agent；

子 Agent 在自己的 Worktree 中修改、测试并形成提交；

子 Agent 返回提交哈希、测试结果、修改文件和已知风险；

主 Agent依次集成这些提交，并运行最终验证；

结果确认后删除临时 Worktree 和对应任务分支。

任务分配不能只写一句“完成接口修改”。更可靠的任务契约至少应包含：
目标：要得到什么可观察结果；

基线：从哪个提交或分支开始；

路径边界：允许修改哪些文件；

接口约定：输入、输出和依赖不能随意改变的部分；

交付物：提交哈希、变更摘要、测试结果；

验收方式：主 Agent 如何独立验证。

Worktree 让“不要覆盖别人正在修改的文件”从协作约定变成物理隔离。OpenAI 在 Codex App 的介绍中也将内置 Worktree 支持用于多个 Agent 在同一仓库上并行工作，让每个任务在隔离代码副本中推进。
但物理隔离不是最终目的。真正有价值的交付物仍然是可追踪的提交，而不是留在某个临时目录里的文件。 主 Agent 应当通过提交进行集成，避免人工复制文件导致历史、作者和变更边界丢失。
5. 分支占用、未提交修改、依赖缓存和错误清理等常见问题
问题一：创建 Worktree 时提示分支已经被检出。
同一个本地分支默认只能属于一个工作树。应该为新任务创建独立分支，而不是用 --force 让两个工作树争用同一分支：
git worktree add -b task/new-branch ../repo-task main问题二：worktree remove 拒绝删除。
先进入对应目录运行 git status。如果存在修改，确认它们应该提交、备份还是放弃。只有明确知道内容不再需要时，才考虑强制移除。
问题三：删除目录后，worktree list 仍然显示旧记录。
这通常是因为手动删除绕过了 Git 的管理流程。先执行 git worktree prune --dry-run 查看将清理的内容，再执行 git worktree prune。
问题四：代码隔离了，运行环境却仍然互相影响。
Worktree 只管理 Git 工作区，不会自动隔离数据库、端口、容器名、系统环境变量或外部缓存。两个 Agent 如果同时占用 8000 端口，仍然会互相抢占；如果共用一个可写测试数据库，仍然可能污染数据。
依赖目录也需要单独设计。Python 的 .venv、Node.js 的 node_modules 通常不会随着 Worktree 自动共享。可以利用包管理器缓存减少重复下载，但不要为了省空间让多个并发任务共用容易被修改的运行目录。
问题五：把 Worktree 目录随意移动。
Worktree 与主仓库之间保存了路径关联。需要移动时优先使用 git worktree move；如果已经被外部工具移动，可以使用 git worktree repair 修复关联。
此外，Git 官方文档仍提示多工作树与 submodule 的组合支持并不完整。包含复杂子模块的项目应先做小范围验证，再把 Worktree 纳入自动化流程。
6. Worktree 能解决什么、不能解决什么
Worktree 解决的是并行任务的修改现场隔离：
多个分支可以同时检出，不需要反复 stash 和切换；

每个任务拥有独立的 HEAD、暂存区和未提交修改；

主工作目录可以保持干净，用作代码审查和集成；

Agent 的失败实验可以直接丢弃，不影响其他任务；

子任务可以通过提交形成清晰、可回滚的交付边界。

但它不会自动解决下面这些问题：
两个任务最终修改同一段代码时的合并冲突；

上游接口尚未确定，下游却提前实现造成的语义冲突；

数据库、端口、消息队列和外部服务等运行时资源竞争；

任务拆分错误、验收标准缺失和 Agent 之间的信息遗漏；

集成后才出现的跨模块测试失败。

因此，Worktree 不是并行开发的调度器，而是并行开发的隔离底座。 在它之上仍然需要任务依赖分析、路径所有权、提交交付、统一集成和最终验证。
如果只有一个短任务，或者多个步骤严格前后依赖，单工作树顺序完成通常更简单。只有当任务确实能够并行、并且并发覆盖带来的收益高于创建和集成成本时，Worktree 才真正产生价值。
