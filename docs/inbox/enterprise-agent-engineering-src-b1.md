《企业 Agent 工程化手记》第 8 篇。
前面七篇，我把企业 Agent 从 Demo 走到生产要补的工程断点拆了一遍：边界、工具、异常恢复、状态机、人工接管、权限、集成。这一篇是工程断点这条线的收尾，也是最容易在上线前被跳过的一块——可观测性。
先说结论：一个能读写业务数据的 Agent，至少要留下会话归属、步骤状态、工具调用和人工决议四类记录。它们要能用 run_id、task_id、step_id、tool_id 串起来，才能在结果不对、执行卡住或人工接手时还原现场。
最崩溃的不是它错了，是你不知道它为什么错
这半年重构 Office Agent 的 CRM 能力，有一类问题最让我头疼：Agent 当时看起来确实在执行，事后却很难复盘它到底怎么执行的。
不是那种“系统直接挂掉”的问题。
更麻烦的是：用户问了一个 CRM 问题，Agent 也返回了结果，页面上甚至能看到它“正在查询”“正在生成报告”。但如果结果不对，或者中间卡住了，我需要回答几个更具体的问题：
它到底调用了哪个 CRM 工具？

这次工具调用的 ID 是什么？

它传进去的参数是什么？

它拿到了什么返回？

它为什么从“查询客户”走到“生成报告”？

如果中间等待确认，等的是谁确认，确认了什么？

这些问题答不上来，可观测性就不合格。
传统系统出问题，我看日志、看堆栈，基本能还原“代码走了哪条分支、在哪一行挂的”。Agent 不一样，它错的往往不是一行代码，而是一条决策链路。它为什么选了这个工具，为什么把这条数据判断成匹配，为什么在这一步停下又接着往下走，如果当时没记下来，事后我只能猜。
这就是我后来对 Agent 可观测性的基本判断：
要看的不是它最后说了什么，而是它一路怎么走到这个结果。
我翻提交记录时，看到的不是一个功能，而是一条排查链
这篇不是凭感觉写的。我回头翻了 Office Agent 里几次和 CRM Agent 运行链路有关的提交，它们其实连成了一条很清楚的线。
案例线索都来自项目内的真实改动：95fa1fd3 补会话历史和缺失会话回建，3e296e69 统一工具事件并处理调用 ID，8b9079fc 增加步骤 commentary 和进度日志，6f34688a 把运行中和完成后的过程展示到 TaskFlow。另有 2b47c4d5 处理工具消息历史的清洗，避免为了回放而无差别保留原始内容。这里讨论的是工程重构过程，不是一次生产事故复盘。
第一类提交，解决的是“会话历史能不能找回来”。
有一次我们补了会话历史列表的能力，让会话可以按最后消息时间排序，同时在第一句对话进来但 conversation 记录缺失时，自动补建会话，并把 agent、entity_type、entity_id、entity_name 这些场景信息带上。
这件事听起来很后台，很不性感。
但它解决的是一个最基础的问题：当用户说“刚才那个客户分析结果不对”时，我不能只在数据库里看到几条孤立消息。我必须知道这段对话属于哪个 Agent，关联哪个客户，发生在什么时候，最后一次活跃是什么时候。
否则，复盘从第一步就断了。
第二类提交，解决的是“工具调用能不能串起来”。
我们后来把运行事件统一成 envelope，事件里有 run_id、task_id、agent、sequence、timestamp。工具事件也不再只是散乱的文本，而是区分 tool_start、tool_end，并保留 tool_id 和原始工具名。
同一阶段还修了一个细节：如果流式 update 反复推同一个工具调用，前端不能把它当成多个工具重复展示。于是事件归一化里增加了 tool call ID 的去重，测试里也明确断言，同一个 call_1 只能生成一次开始和一次结束。
这不是前端体验问题。
如果工具调用没有稳定 ID，排查时你就无法把“模型说我要查客户”“工具实际查了客户”“工具返回了结果”“模型继续生成报告”这几件事连成同一条链。你看到的是一堆事件，不是一条可复盘的执行过程。
第三类提交，解决的是“执行过程能不能被人看懂”。
后面我们给 TaskFlow 补了 commentary、progressLog、startedAt、completedAt 和 durationMs。也就是说，一个步骤不只是“成功 / 失败 / 执行中”这么粗。
它可以记录：
这个步骤什么时候开始，什么时候结束，跑了多久。

这一步里每个 progress message 是什么，成功还是失败。

模型在这个步骤前后输出过什么 commentary。

步骤结束后，进度日志仍然可以回放，而不是流式结束就丢了。

再往前端补一层，TaskFlow 会默认展开正在执行、等待确认和错误步骤；运行中的步骤会显示实时耗时；进度日志会按 running、success、error 显示不同状态。
这些东西加起来，才从“页面上有个加载中”变成“我知道它卡在哪一步，卡了多久，卡之前做了什么”。
真正的问题不是没日志，而是链路断了
回头看这几次改动，真正补上的不是“更多日志”，而是三段原来容易断掉的链路。
第一段是会话链路：这段对话是谁发起的，属于哪个 Agent，关联哪个客户或商机。
第二段是执行链路：这次 run 下面有哪些 task、step、tool call，事件按什么顺序发生。
第三段是展示链路：执行时发生了什么，完成后还能不能回放，当人接手时能不能看到足够上下文。
这三段任意一段断掉，复盘都会变成猜。
有日志但没有会话归属，你不知道该查哪段对话。
有工具输出但没有 tool_id，你不知道哪个开始对应哪个结束。
有最终回答但没有 progressLog，你不知道它中间有没有卡住、跳过、失败后继续。
所以我现在越来越觉得，Agent 的可观测性不是把日志打得更细，而是让每一次执行都能被重新拼回一条完整链路。

会话、执行步骤、工具调用和回放结果必须通过同一条可追溯链路连接

黑盒不应直接获得生产写权限
站在企业系统开发负责人的角度，我现在对 Agent 上线有一条硬要求：它的决策过程必须是可还原的。
传统系统观测的是“代码走了哪条路”，Agent 要观测的是“它基于哪些已记录的事实做了这个动作”。一个会自己做决定、还能改业务数据的东西，如果无法还原其动作依据，就不应直接获得生产写权限。
出事的时候，你连“它做了什么”都答不上来，更别说追责和修复。
我现在判断一个 Agent 能不能上线，不先问它错没错，先问：
它出问题时，我能不能还原出它当时的完整执行和决策依据？
这个问题必须落到具体事实上。
如果它查了客户，我要知道查的是哪个实体、什么条件、命中了几条、为什么选择其中一条。
如果它改了商机阶段，我要知道修改前是什么阶段，目标阶段是什么，中间有没有通过状态转移校验，失败时有没有停住。
如果它触发人工接管，我要知道触发原因是什么，等待谁确认，确认后恢复的是哪个 task，而不是只看到“用户已确认”四个字。
如果它生成报告，我要知道报告使用了哪些工具返回、哪些结果引用、哪些中间判断，而不是只保留最终文章一样的总结。
这就是 Agent 可观测性和传统日志最大的区别。
传统日志偏向解释系统行为。Agent 可观测性必须解释决策行为。
要记的不是原始思维链，是可审计的决策依据
Agent 的可观测性，不是“加几行 log”，是设计时就要埋的四类记录。这里的决策记录不是保存模型的原始思维链，而是保存可以审计的意图、前置事实、规则命中和动作理由：它足够支持复盘，又不会把不该留存的内部推理和敏感上下文直接写进日志。
决策依据：每一步要做什么、基于哪些事实和规则判断。这是 Agent 特有的，也是最重要的。出问题时，你要能看到动作理由，而不只是结果。

工具调用：它调了哪个工具、传了什么参数、返回了什么。这直接呼应第 2 篇的工具治理。工具调用既要治理，也要留痕。

状态变迁：它在状态机里走了哪条路、当前停在哪个状态。呼应第 4 篇状态机。状态本来就该是显式的、可查的。

人工接管点：在哪一步触发了人工确认、谁批的、批了什么。呼应第 5 篇人工接管。接管动作必须留痕。

你会发现，这四类记录其实是前面几篇的“留痕”要求收在一起。可观测性不是一个新模块，是把工程断点上的关键节点都变成可还原的事实。这件事必须在设计时埋进去，事后补的日志永远缺最关键的那一段。
我会把这四类再说得更工程一点。
一、决策链路：每一步为什么发生
Agent 的每一步都应该能回答一个问题：它为什么这么做？
不是只记录“调用了 search_customers”，而是要记录这次调用来自哪个用户意图、处在哪个 task、命中了什么前置事实或业务规则。
例如用户问“这个客户最近有没有风险”，Agent 可能先查客户基础信息，再查拜访记录，再查商机，再生成判断。最后结论如果不对，我要能看到它到底在哪一步偏了：
是客户识别错了？

是拜访记录没查全？

是商机阶段理解错了？

还是报告生成时把工具返回解释错了？

如果这些动作依据只存在模型上下文里，没有进入运行记录，复盘就只能靠猜。
二、工具调用：每次调用必须可对账
工具调用不能只在聊天正文里显示一句“正在查询客户信息”。
至少要有稳定的 tool_id，原始工具名、展示名、参数摘要、返回状态、错误类型和耗时。必要时还要保存可脱敏的原始结果引用。
这里有一个很容易被低估的点：同一个工具调用在流式更新里可能出现多次。如果没有 tool call ID 去重，页面上看起来像调用了多次；如果去重过度，又可能丢掉真正的后续结果。
所以工具事件要能对账：
tool_start 对得上 tool_end。

同一个 tool_id 不重复开始。

工具结果能回到对应步骤。

网络错误、权限错误、业务校验错误要分开。

这不是为了日志好看，是为了出问题时知道哪一个动作真的发生过。
三、状态变迁：它停在哪一步，要能继续
前面状态机那篇我说过，状态不是日志。
到了可观测性这里，这句话还要再加一层：状态也必须可解释。
我不只需要知道当前步骤是 running、success、error 或 waiting_confirmation，还要知道它为什么进入这个状态。
比如一个 CRM 写操作进入 waiting_confirmation，原因可能完全不同：
动作不可逆，需要业务 owner 确认。

数据范围超过阈值，需要缩小范围。

权限不够，需要转人工处理。

状态转移不合法，需要停在校验层。

如果状态字段只有“等待确认”，人接手时仍然要重新排查。真正有用的状态，应该让人能从确定位置继续处理。
四、人工接管点：谁在什么时候接住了风险
人工接管不是在系统旁边放一个“确认”按钮。
它本身就是可观测性的一部分。
一次接管至少要留下这些事实：
触发接管的规则是什么。

当时展示给人的上下文是什么。

人批准、驳回、缩小范围，还是要求改成草案。

决议是谁做的，什么时候做的。

决议后恢复的是哪个 task、哪个 step、哪个 tool call。

否则，人接管了，但系统不知道人接管了什么。以后复盘时，只能看到一个孤立的确认动作。

执行过程在暂停点交给人工核验，再决定批准或拦截

最小记录契约：先把这四类对象建起来
我不会一开始就做一个很大的日志平台。先把下面四类对象和它们的关联建清楚，已经能覆盖大多数排查和接管场景：
Run：run_id、会话引用、agent、开始时间、最终状态
Step：step_id、run_id、状态、开始/结束时间、动作理由摘要
ToolCall：tool_id、step_id、工具名、参数摘要、结果引用、错误分类
Approval：approval_id、step_id、触发规则、决议、处理人、决议时间

运行、步骤、工具调用和人工决议由同一条记录链关联

其中的参数摘要和结果引用要按数据分级脱敏。凭据、完整个人信息和不该回放的工具原文，不应该为了“可观测”而被扩散保存。真正需要的是可定位、可核验、可授权查看的证据，不是把所有上下文都堆进日志库。
上线前，我会看这几条检查线
如果把上面这些要求压成上线检查，我现在会看六条。
第一，事件有没有统一 envelope。
至少要有 run_id、task_id、agent、sequence、timestamp。没有这些字段，事件就很难排序和重放。
第二，工具调用有没有稳定 ID。
没有 tool_id，就很难把工具开始、工具进度、工具结果、前端展示和后续模型输出串起来。
第三，步骤有没有状态和耗时。
只看到“加载中”是不够的。我要知道它卡在哪一步，卡了多久，是仍在执行、等待确认，还是已经失败。
第四，进度日志能不能在完成后回放。
很多系统只在流式过程中显示进度，结束后就剩最终回答。这对用户体验可能够了，对工程复盘不够。
第五，结果展示和模型上下文要分开。
大结果可以进结果存储或前端展示，不一定全塞回模型上下文。但它必须有引用、有状态、有总数、有展示记录。否则模型省了 token，人丢了证据。
第六，错误要能分类。
网络错误、权限错误、业务校验失败、契约不匹配、人工拒绝，不应该最后都变成“执行失败”。错误分类越粗，恢复动作越容易错。
可观测性要在设计时埋进去
很多团队会把可观测性当成上线后的补救项。
先把 Agent 跑起来，出了问题再加日志。
这在普通系统里已经不理想，在 Agent 里更危险。因为 Agent 最关键的信息往往只在执行当下出现：当时的上下文摘要、选择工具的理由、规则命中、人工确认前展示的材料、工具返回后的解释过程。
这些信息如果当时没保存，事后很难补。
你可以补一行错误日志，但补不回它当时为什么做这个判断。
你可以重跑一次工具，但补不回当时模型看到的上下文。
你可以查数据库最终状态，但补不回中间有多少步成功、哪一步失败、有没有半成功。
所以我现在更愿意把可观测性当成 Agent Harness 的一部分，而不是一个外挂模块。
Harness 不只是调模型、接工具、管状态。它还要负责把执行过程变成可还原的事实：
每个 run 有身份。

每个 task 有上下文。

每个 step 有状态。

每个 tool call 有 ID。

每个 progress 有时间。

每个人工决议有出处。

每个结果展示有引用。

这样 Agent 才不是一个会自己做决定的黑盒，而是一条可以被检查、被暂停、被接管、被恢复的业务执行链。
