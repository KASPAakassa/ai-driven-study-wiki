大模型落地避坑系列 · 第5期
最近几个月接了几个 Agent 项目，发现一个共同问题：团队拿到需求后，上来就开始写代码，先搭一个 Agent，然后给它挂工具，再加 RAG，发现不对又拆了重来。
折腾两三周，代码写了不少，但流程越改越乱。最后回头一看，很多弯路其实在"选模式"这步就能避掉。
Agent 的工作流设计是有套路的。不是每次都要从零开始想，常见的场景就那么几种，对应几种成熟的设计模式。今天把这几种模式拆开讲，每种附上适用场景和踩过的坑。

模式一：线性管道，最简单也最稳
最基础的模式：输入 → LLM处理 → 输出。一步到位，中间不加复杂逻辑。
适合什么场景？用户提问，模型直接回答，不需要调用工具，不需要多步推理。典型的就是 FAQ 问答、文本摘要、翻译这类单轮任务。
实现上就是把 prompt 模板 + 用户输入拼好，调一次模型，返回结果。代码量可能就 20 行。
别觉得简单就看不上。线性管道在生产环境的稳定性秒杀其他所有模式。没有循环就没有死循环的风险，没有多步调用就没有中间状态出错的概率。如果一个场景能用线性管道解决，千万别上更复杂的模式。
我们的做法：新项目头两周，强制只用线性管道跑。跑通了再考虑要不要加复杂度。很多时候跑通之后你会发现，根本不需要更复杂的东西。
模式二：ReAct 循环，Agent 的核心能力
ReAct 就是"推理-行动-观察"的循环。模型先想"我该干什么"，然后调一个工具，看结果，再想"下一步该干什么"，循环往复直到完成任务。
这是 Agent 区别于普通 Chatbot 的关键。你让它帮你查一个数据，它会自己去调 API、查数据库、翻文档，一步一步把答案拼出来。
适合需要多步推理 + 工具调用的场景：数据分析助手、运维排障机器人、多源信息检索。
但 ReAct 循环有个天然问题：不可控。模型可能转了 5 圈还在原地打转，token 烧了一堆没出结果。上线第一天就可能被用户玩崩。
几个实战经验：
循环次数硬限制设 5 次。超过 5 次直接走兜底，返回"暂时无法处理"加转人工。这个数字不是拍脑袋的，我们统计过，正常完成的任务 90% 在 3 次循环以内，超过 5 次的基本都是卡住了。
每一步都记 trace。哪一步调了什么工具、传了什么参数、返回了什么结果，全记下来。线上排查问题的时候，trace 就是你的救命稻草。没接 trace 的 ReAct 上线等于裸奔。
工具描述写人话。别写"该工具用于获取用户信息"，写"当用户提到自己的订单、账户或个人信息时调用此工具"。前者模型不知道什么时候该用，后者它一看就明白。

模式三：管道编排，把复杂任务拆成阶段
当一个任务太复杂，单个 Agent 搞不定的时候，别急着上多 Agent 协作。先试试管道编排。
管道编排的思路：把任务拆成几个阶段，每个阶段用一个专门的 prompt（甚至不同的模型），前一个阶段的输出作为后一个阶段的输入。
举个例子，做一个合同审查助手。拆成三步：第一步提取合同关键条款（用便宜模型），第二步对比标准模板找风险点（用大模型），第三步生成审查报告（用便宜模型做格式化输出）。
为什么不直接一个 prompt 搞定？因为一个大 prompt 让模型又提取又对比又写报告，每个环节都不够深。拆开后每个阶段的 prompt 聚焦一件事，效果提升明显。而且三个小模型的调用成本可能比一个大模型还便宜。
管道编排和多 Agent 协作是两回事：管道是线性流转，没有循环和交互，每个阶段只做自己的事然后交给下一个。简单、可控、好调试。
如果管道编排能解决你的问题，就别碰多 Agent。复杂度差一个量级。
模式四：人机协作，关键时刻让人来
有些场景 Agent 可以自动完成 90%，但最后 10% 需要人来拍板。比如医疗诊断建议、法律合同审批、大额交易风险评估。
这时候用"人机协作"模式：Agent 自动跑到一个决策点，暂停，把结果推给人工审核，人确认后再继续。
这种模式的价值在于：既享受了自动化的效率，又保留了人工兜底的安全性。在合规要求高的场景里，这个模式几乎是唯一选择。
实现上有几个关键点：
暂停-恢复机制要做好。Agent 跑到决策点后把当前状态持久化（存数据库），等人审核完了再加载状态继续跑。中间可能隔几小时甚至几天，状态管理是重点。
给审核人的信息要够用。别把模型的原始输出直接丢给业务人员，他们看不懂。做一层翻译，把"模型置信度 0.72"翻译成"中等可信度，建议关注第3条风险"。
记录每一步的人工决策。不仅是审计需要，这些数据后面可以拿来做模型效果分析，甚至反哺训练数据。
模式可以选，原则不能丢
最小可用原则。永远从最简单的模式开始。能用线性管道就别上 ReAct，能用管道编排就别上多 Agent。每加一层复杂度，调试成本和线上风险都在翻倍。先跑通最小闭环，再根据实际需要加东西。
可观测原则。Agent 的每一步执行都要留痕：调了什么工具、传了什么参数、返回了什么结果、花了多少 token、用了多长时间。没有可观测性的 Agent 上线就是埋雷。我们团队的规矩是：没接 trace 的 Agent 不许上生产。
兜底原则。每一个可能失败的地方都要有 fallback。模型超时了怎么办？工具调不通了怎么办？循环跑超了怎么办？这些问题不在代码里处理好，线上就会变成用户投诉。兜底策略不用花哨，最简单粗暴的"返回预设话术 + 转人工"就够用，但必须有。
