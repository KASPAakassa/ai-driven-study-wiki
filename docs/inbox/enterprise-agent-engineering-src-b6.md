企业 Agent 出错后：该重试、回滚，还是交给人？

企业 Agent 出错后，该重试、回滚，还是交给人

能进生产的 Agent，不是不出错的那个，而是出错后知道该怎么停的那个。

这是《企业 Agent 工程化手记》的第 3 篇。
前两篇我写了 Agent 最容易失控的两个地方：一个是 《Agent任务边界失控》，一个是 《工具太多失控》。
那两篇讲的是怎么不让它走错。
这一篇要写一个更晚、也更危险的时刻：它已经走错了，接下来怎么办。
过去一段时间，我习惯让 Agent 自己扛。报错了，就让它再试一次。结果不对，就让它接着改。我默认这是省事。
直到我翻协作日报。
连续几天，验证补跑、返工修正、重复推进 这几个信号反复出现。
6 月 14 日，验证补跑 11 次，返工修正 52 次，重复推进 13 次。到 6 月 16 日，返工修正 仍有 10 次，基线是 5.0；安装/配置反复 5 次，基线是 1.0。
很多任务不是没做完，而是在"出错—重试—再出错"里打转。
样本说明：这是我个人的 AI 协作日报，不是行业统计；计数按用户消息级标签归类。
这些数字推不出行业结论。
但它们让我看清一件被我当成"省事"的事，其实是把最该由系统决定的问题，丢给了模型当场发挥：
重试、回滚、人工接管，是三种代价完全不同的动作。让 Agent 自己挑，迟早会挑错。

先给结论：
重试，解决的是可以安全重复的瞬时失败。

回滚，解决的是已经产生副作用、但还有可信状态可退的问题。

人工接管，解决的是系统无法安全判断、继续自动处理会扩大风险的问题。

我们对"出错"的直觉是错的
我们天然觉得，出错就等于再来一次。
模型报错，结果不对，让它重试，似乎是最自然的反应。Demo 阶段，这个直觉几乎不会出事。因为那时候任务可重复，动作没有副作用，错了大不了从头来。
问题从动作有了副作用开始。
"再试一次"其实是有前提的。这一步，重复做会不会出新的问题？上一步留下的半成品，要不要先清掉？
出错不是一个动作，而是一个需要先判断的岔路口。
在决定怎么走之前，得先看清自己站在哪种错误面前。
第一种恢复：重试，前提是这一步能安全地重复
重试是最便宜的恢复动作。
但重试不是"再试一次"。
它的准确含义是：在动作可以安全重复时，用有限次数消除瞬时失败。
它只对"可以安全重复"的动作有效：一次只读查询，一次纯计算，一次幂等写入。这些重复多少遍，结果都一样。
一旦动作有副作用，重试就会变味。
发消息、扣费、提交、改状态——这些动作盲目重试，就是重复发送、重复提交、重复扣费。错误没被修复，只是又发生了一次。
更隐蔽的是重试风暴。
Agent 在一长串工具调用里反复试、反复补，看起来一直在推进，其实在制造垃圾。我那几天的日报里，验证补跑、返工修正和安装配置反复不断出现，很多并不是模型不会做，而是它在不该重试的地方一直重试、一直补。
所以重试之前，先回答一个问题：
这一步，重复做会不会出新问题？答不上来，就不该自动重试。

第二种恢复：回滚，前提是你留了后路
如果这一步不能安全重复，下一个选择是退回去。
回滚不是"撤销错误"这么简单。
它的准确含义是：把系统带回一个已经记录过、仍然可信的状态。
回滚的意思，是把系统恢复到出错前的状态。代价比重试高，但比带着脏数据继续往前安全得多。
能不能回滚，取决于两件事。
一是动作本身可不可逆。二是你有没有记录"改之前长什么样"。
很多 Agent 根本回滚不了。
因为它一路往前补，对应日报里反复出现的 重复推进：既没有检查点，也没有留下原始状态。等发现错了，已经退无可退，只能硬着头皮往下走。
这里其实藏着下一篇的引子：
要能回滚，先得有状态。一个动作执行前没留下"原来的样子"，出错时就没有退路。

第三种恢复：人工接管，前提是系统知道自己处理不了
有些错误，不该由 Agent 决定怎么收场。
人工接管不是让人替 Agent 干活。
它的准确含义是：系统确认自己无法安全决策时，把上下文、已执行动作和风险点交回给人。
不可逆的动作，涉及金额或客户数据的动作，判断依据不足的时候——这些场景，正确的恢复不是重试，也不是回滚，而是停下来，把上下文交回给人。
人工接管不是失败，而是设计的一部分。
关键在于停止条件要写清楚：满足什么条件就停、停在哪一步、把什么信息交回给人。
它的反面是"频繁确认"。
如果每一步都要人点一下确认，那不是接管设计得好，而是边界没划清。人在替工具的越界风险持续买单。上一篇里提到的授权确认次数，就是这种信号。
成熟的 Agent 不是什么都自己扛。
它知道哪类错误必须停下来交回给人。停止条件写得清不清楚，决定了人工接管是兜底，还是负担。

三种恢复动作：重试看幂等、回滚看状态、接管看停止条件

为什么这件事在企业 Agent 上更危险
Coding Agent 出错重试，最多是返工、改坏代码、浪费时间。这些还能靠差异检查、测试和代码审查拦下来，成本变高，但通常能回退。
企业 Agent 不是这样。
站在企业系统开发负责人的角度，我不会先问模型能不能修好，而会先问这一步可不可逆、有没有退路、什么时候必须停。
因为企业 Agent 出错重试，可能是把同一封邮件发给客户三次，把一笔操作重复提交，把一个状态改到回不去。
这里我不把它包装成一个真实生产事故。
更准确的说法是：我现在看 CRM Agent 的写操作，会先把它当成一个风险演练，拆成很具体的现场问题。
比如，Agent 要批量更新客户阶段，同时给客户负责人发提醒。第一次调用超时了，但 CRM 里有一部分客户阶段已经改掉，提醒也可能已经发出。这个时候如果它只是再试一次，第二次就不再是"补上失败任务"，而可能是重复改状态、重复发提醒。
这类问题不靠模型临场判断。
它需要在动作开始前就写清楚：哪些客户已经改过，哪些提醒已经发过，下一步只能查状态、补缺口，还是必须停下来让人看一眼。
放到 CRM Agent 上，问题很具体：
写操作大多不可逆：发邮件、改客户状态、提交审批，重试一次，就是真实世界里多发生一次。

没有状态记录就没有回滚：改了字段却没存原值，出错时连"退回去"都做不到。

缺少停止条件，Agent 会一路自我修复，把一个小错误滚成一连串脏数据。

企业 Agent 的风险，不在于会出错。任何系统都会出错。
风险在于出错那一刻，没有人提前规定过：它该重试、该回滚，还是该停。

我现在怎么做：把失败处理写在出错之前
这几天翻日报，我已经在改自己的习惯。
连续几天的复盘里，优化方向都指向同一句：安装、配置、写操作这类请求，必须先写清验证命令和失败退出条件，而不是让 Agent 边做边补。
这句话不只对 Coding 成立，对企业 Agent 同样成立。
具体有五条。
动作分级，先分清这一步是只读、可写，还是不可逆。三类的恢复方式完全不同。
重试前置条件，只有确认能安全重复的动作才允许自动重试，并且设重试上限，避免重试风暴。
回滚后路，可写动作执行前先记录原始状态或留检查点，否则一律当成不可逆来对待。
停止条件，遇到不可逆、涉及金额或客户数据、判断依据不足的情况，就停下来交回给人。
写进计划文件，把验证命令、失败退出条件、恢复策略写在任务开始之前，而不是出错后临时补。
这件事可以用团队来类比。
你不会让一个新人在生产环境出错后自己看着办、自己反复改。
你会先和他约定：什么情况重试，什么情况回滚，什么情况必须停下来叫人。
Agent 也一样。
Agent 的可靠性，不取决于它出不出错，而取决于你有没有在它出错之前，就替它把"怎么收场"想清楚、写下来。

出错那一刻的决策流：能安全重复就重试，可逆就回滚，不可逆就交给人

Agent 工程化的第三课，是设计它怎么失败
第一课是约束任务边界，第二课是约束工具。
第三课，是设计它怎么失败。
这几天的协作日报给我的提醒很直接：验证补跑、返工修正、重复推进这些信号反复出现，不是模型变笨了，而是它在没有恢复策略的情况下，自己摸索着从错误里往外爬，越爬越乱。
真正能进生产的 Agent，不是从不出错的那个，而是出错时知道该重试、该回滚，还是该停下来交给人的那个。
后面我会继续拆这些生产边界：状态管理、上线检查，以及 AI Coding 如何进入企业研发流程。
常见问题
企业 Agent 出错后，应该默认让它自动重试吗？
不应该默认。只有确认这一步可以安全重复（幂等）的动作，才适合自动重试，并且要设重试上限。对发消息、改状态、提交审批这类有副作用的动作，盲目重试等于让错误又发生一次。
重试、回滚、人工接管怎么选？
按动作性质选，不是按优劣排序。能安全重复的，重试最便宜；不能重复但可逆、且记录了原始状态的，回滚；不可逆、涉及金额或客户数据、判断依据不足的，停下来交回给人。三者是代价和适用场景不同，不是谁高谁低。
失败处理应该什么时候设计？
在任务开始之前。把验证命令、失败退出条件和恢复策略写进计划文件，而不是等出错了再让 Agent 临场补。出错后才想怎么收场，往往已经没有退路。
