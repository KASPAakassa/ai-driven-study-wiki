一、用户级 Agent 和企业级 Agent 是两件事
个人用 Agent，装个工具、写几个 prompt 就能跑起来。企业场景完全不一样——多用户、多 agent、多入口、不同权限，问题复杂度是指数级的。
想一个真实场景：你写了一个查数据的 agent，张三能不能用？李四用的时候，查的是他自己的数据还是你的？王五在群里 @ 机器人问了一句，消息怎么路由到正确的 agent？回复之后上下文要不要保留、保留多久？如果王五问的问题需要跨 agent 协作，谁来调度？
这些不是"装什么工具"的问题，是架构问题。这篇文章把核心设计讲清楚——不是教程，是设计思路和背后的为什么。
二、Agent 的四要素
一个 Agent 由四个要素构成：
Agent = LLM（推理引擎）+ 上下文（知）+ 工具（行）+ Harness（工程保障）

LLM 是引擎，上下文是燃料，工具是手脚，Harness 是神经系统——控制怎么思考、怎么执行、怎么不出错。
2.1 LLM：推理引擎
LLM 是 Agent 的大脑，负责理解意图、规划行动、生成结果。选什么模型、用什么参数，直接影响 Agent 的能力天花板。
但 LLM 本身只带推理能力，不携带任何企业知识。一个裸模型面对"查一下昨天的消耗"——它不知道"消耗"在哪个表里，不知道"昨天"对应的分区字段叫什么，更不知道当前用户有没有权限查这张表。这些全部依赖上下文和工具来补全。
所以模型选择固然重要，但更关键的问题是：你给模型喂了什么上下文、给了它什么工具。同样的模型，上下文和工具的配置不同，表现天差地别。
2.2 上下文：企业上下文 vs LLM 有效上下文
上下文是 Agent 的认知来源。这里有一个关键区分，很容易被忽略：
企业上下文是全量的知识资产——元信息、规范文档、血缘图谱、术语词典、PRD，沉淀在知识库、Git 仓库、图数据库里。它是静态的、持续积累的、体量巨大。
LLM 有效上下文是 model context window 里实际存在的内容——system prompt、对话历史、检索到的知识片段、工具调用结果。它是动态的、有长度限制的、随会话变化。
企业上下文不能直接塞给 Agent。直接塞，context window 瞬间就爆了。真正的工作流是这样的：
工具检索从企业上下文里捞出相关子集 → Skill 引导如何组合这些信息 → Harness 负责注入时机和格式 → 形成 LLM 有效上下文

企业上下文是原材料，工具和 Skill 是加工过程，Agent 看到的是成品。这个区分决定了整套体系的架构——你不能靠"写更长的 prompt"解决问题，你得有一套能把知识按需装进 context window 的机制。这也是为什么 RAG 在企业 Agent 里不是可选项、而是必选项。没有 RAG，企业上下文永远到不了 LLM 有效上下文。
2.3 工具：用户级 vs 服务级
工具是 Agent 的执行能力，分两类：检索类（查知识）和操作类（查数据、调接口、产生副作用）。
这里有一个容易踩的坑——工具分类的标准。直觉上大家按技术形态分：CLI 工具 vs MCP 工具。但真正的维度是用户级工具 vs 服务级工具：工具能不能区分用户身份？
CLI 恰好落在用户级——per-user cookie 透传，张三和李四查同一张表，看到的是各自有权限看的数据。权限隔离天然成立。MCP 恰好落在服务级——不传用户身份，只看到调用方。多用户场景下，权限模型直接失效。
这不是协议决定的，是工程选择——CLI 也可以不绑 cookie，MCP 也能透传用户身份。但分类一旦搞错，多用户场景的权限模型就从根上做不对。
工具标准化的正确做法：先在 API 层做统一鉴权、格式标准化、凭证注入，CLI 和 MCP 都变成这层 API 的薄壳。标准化逻辑只写一次，能力集天然对齐。
2.4 Harness：工程保障
Harness 是 Agent 的"运行时操作系统"——它不决定 Agent 能做什么，但决定 Agent 怎么做：用什么模式思考、什么时候调用工具、如何管理记忆、权限边界在哪。
核心机制拆开来看：
思考模式：ReAct（观察-思考-行动循环）、Plan-then-Execute（先规划再执行）、Loop（持续自我迭代）。不同场景适合不同模式——数据分析适合 ReAct，代码生成适合 Plan-then-Execute。

Hooks：关键节点埋点，比如工具调用前做权限校验、执行完做结果校验。出错时能拦截而不是盲目继续。

记忆管理：自动压缩长对话上下文，保留关键信息、丢弃冗余。不然多轮对话后 context window 被历史对话占满，新的关键信息进不来。

权限控制：Harness 层决定 Agent 能调用哪些工具、以什么身份调用、调用频率上限。

Harness 的设计直接影响 Agent 的稳定性和可控性。很多 Agent "跑着跑着就停"或者"无限循环调用工具"，根因都在 Harness 层没有做好边界控制。
2.5 Skill：四要素的打包复用
Skill 是 Agent 体系里最灵活的一层。它把上述四个要素按领域打包——引用领域上下文、搭载专属工具、指定 Harness 模式——形成一个可插拔的能力单元。
加载 Skill 时，Agent 获得领域知识和专属工具；不加载时，用基础能力工作。一套源码可以跨 AI 工具分发。
Skill 和工具的关系：工具是"怎么做"（检索知识、执行操作），Skill 是"什么时候做什么"（策略和节奏）。比如"做数据分析时，先探查元数据，再写 SQL，最后验数"——这个策略本身是 Skill，不依赖具体工具。做成文档格式、人机共读，维护成本低。Skill 本质是知识的一种封装形式，不是代码。
三、三层体系：生产、服务、消费
四个要素解决了"一个 Agent 怎么做"的问题。企业场景还要解决"多个 Agent 怎么组织"。我们把整个体系拆成三层：
消费层 — 多入口接入与路由Web UI独立入口企微机器人命令路由API外部接入公共能力配置驱动 · 协议适配 · 身份注入 · 会话路由服务层 — Agent 运行时（同一套 Agent / Skill 不感知部署形态）本地模式单用户 · 直接编排 LLM + 工具服务化模式多用户 · 配置驱动 · 灰度发布 · 回滚Agent 工厂（配置驱动）从注册中心拉取组件 · 组装实例 · 新增=提交配置Agent 实例：数据查询Agent · 业务分析Agent · 需求管理Agent · ...生产层 — 知识资产与工具底座知识资产：元信息 · 规范 · 血缘 · 术语 · PRD工具底座：标准化 API 层 → CLI 薄壳 / MCP 薄壳
3.1 生产层：知识资产与工具底座
生产层提供 Agent 体系的两类原材料。
知识资产：企业上下文的全量沉淀——元信息、规范文档、血缘图谱、术语词典、PRD。这些资产持续积累、版本化管理，是 Agent 认知能力的"原料库"。资产越完整，Agent 能回答的边界越宽。
工具底座：标准化 API 层 + CLI 薄壳 + MCP 薄壳。核心设计原则：标准化在 API 层做一次。多套异构后端 API 先在这一层统一鉴权、统一格式、注入 per-user 凭证，然后 CLI 命令和 MCP Server 基于同一套 API 暴露出去。否则 CLI 和 MCP 各自维护一套适配逻辑，能力集不重合，维护成本翻倍，标准化逻辑也无法复用。
这两种形态功能上完全等价，真正的分类维度不是 CLI vs MCP，而是用户级工具 vs 服务级工具——工具能不能区分用户，决定了多用户场景下的权限隔离能不能做对。
3.2 服务层：Agent 运行时
服务层是 Agent 的运转车间，分两种部署形态。
本地模式：单用户，Agent + 工具直接在本地运行。启动时确定身份和权限，简单直接。适合个人开发调试。
服务化模式：多用户，Agent 实例在服务端由配置驱动组装。消费层注入用户身份，配置中心提供版本管理、灰度发布、回滚能力。适合团队共享、多消费端接入。
关键设计：同一套 Agent 和 Skill 不感知部署形态，两边都能跑。Agent 实例的组装方式从"手写代码"升级为"配置驱动"——配置文件声明模型、工具引用（从注册中心）、Skill 引用、Harness 模式。Agent 工厂运行时读取配置、拉取组件、注入 system prompt、产出实例。新增一个 agent = 提交一份配置声明，不需要新建项目、复制代码、重新配环境。工具和 Skill 在注册中心独立管理版本，修改一处全局生效。
3.3 消费层：多入口接入与路由
消费层负责把用户请求送到正确的 Agent。三种接入模式：
独立入口：多页面 / 多 Tab，用户显式选择 agent，每个 agent 独立会话。适合专业工具型产品——用户明确知道自己要找哪个 agent。

共享上下文（命令路由）：单一对话框，通过 / 前缀命令显式路由。同一对话框可跨 agent 共享上下文。适合企微机器人场景——一个群聊里既能查数据、也能问业务。

共享上下文（意图路由）：单一对话框，意图识别自动路由。用户不用知道后端有哪些 agent，自然语言描述需求即可。适合长期演进方向。

公共能力层做协议适配（对接 WebSocket / HTTP / 企微回调等不同协议）、身份注入（per-user cookie / OAuth，确保用户身份透传到工具层）、会话管理（多用户多 agent 的上下文持久化与恢复）、意图路由（识别用户意图，分发到对应 agent，共享上下文模式下可跨 agent 传递上下文）。
消费层同样是配置驱动——一份消费配置声明入口类型、路由规则、用户准入、会话策略，消费工厂运行时加载。
3.4 运维层：横跨支撑
运维层横跨三层，提供体系级的基础能力：
注册中心（工具 + Skill）：统一管理定义和版本，agent 按需引用，改一处全局生效。

配置中心：Agent 配置 + 消费配置的版本管理、灰度发布、回滚。

监控告警：任务完成率、工具调用准确率、延迟监控。

评估反馈：端到端完成率、用户反馈回流，驱动配置迭代。

四、关键设计决策
4.1 为什么选 CLI 做工具标准化入口
CLI 方案能同时覆盖人（终端直接敲）和 agent（bash tool），per-user cookie 天然支持多用户权限隔离。单一 Go 二进制，分发简单。但更重要的是：CLI 天然落在"用户级工具"这一侧——每个用户用自己的凭证调用，权限隔离在工具层就解决了，不需要消费层再做一层权限映射。
4.2 为什么权限做在工具层而不是消费层
多后端 API 各自有独立的鉴权体系，消费层统一接管成本太高。工具层做 per-user cookie 透传，利用各后端的原生权限机制，简单有效。消费层可以做粗粒度的能力路由作为补充。
4.3 多 agent 边界怎么划分
同一领域质量审查 → sub-agent 协作（reviewer / checker）

不同业务域 → 独立 agent

不同消费端 → 消费适配器，共用同一套 agent

这些选择共同指向一个原则：先在工具层做用户身份透传，再用配置驱动降低 agent 组装成本，最后在消费层做统一路由。顺序不能反——没有用户级工具就没有真正的多用户隔离，没有配置驱动就谈不上规模化。
五、演进路径
四个阶段，每层独立推进，不互相阻塞：
Phase 1 — Skill 层收敛：各项目分散维护的 Skill 统一治理，版本化分发，可跨 AI 工具使用。

Phase 2 — Agent 层规范化：提取独立的业务 agent，Agent 后端拆分为纯运行时 + 平台基础设施（认证、WebSocket、DB 等独立出来）。

Phase 3 — 工具底座标准化：建立独立的标准化 API 层，CLI 和 MCP 基于它重构为薄壳，能力集完全对齐。

Phase 4 — 消费层统一：多个入口的路由、会话管理统一为一个消费层网关，各入口只做 UI 适配。

企业 Agent 体系本质上是基础设施设计问题。框架会演进，模型会迭代，但"多用户、多 agent、多入口"的架构约束不会变。把这三层想清楚，剩下的只是工程节奏。
