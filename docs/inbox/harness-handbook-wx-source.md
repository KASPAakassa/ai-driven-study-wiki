一篇关于 Agent 工程“行为地图”的新论文，以及它对可演化系统的现实意义

谈论 AI Agent，我们习惯先问：底层是什么模型？上下文多长？基准分数多少？但当 Agent 真正在电脑里读文件、调用工具、保存记忆、处理失败并持续运行时，模型只是“发动机”。把发动机变成可工作的机器，还需要一整套 harness（可译作运行框架、智能体支架或执行外壳）。
2026 年 7 月 14 日提交至 arXiv 的新论文《Harness Handbook: Making Evolving Agent Harnesses Readable, Navigable, and Editable》，把问题推进了一步：当 harness 越来越复杂，我们如何准确找到“某个行为到底由哪些代码共同实现”？
作者把这个前置难题称为 behavior localization（行为定位），并提出 Harness Handbook 与 BGPD 工作流。
先说明证据等级：本文讨论的是论文 v1 和作者公开代码。它刚刚发布，尚无我们能确认的独立复现、同行评议或长期生产验证。下文会明确区分“作者结论”与“我们的判断”。
一、Harness 为什么不再只是“胶水代码”

模型发动机、工具机械臂与记忆抽屉组成的 Agent 工厂
一个现代 Agent 的 harness，通常负责提示词构造、上下文装配、状态管理、工具调用、权限边界、循环控制、错误恢复、子 Agent 协调和外部环境交互。换模型不一定改变系统行为；但改掉一次重试、一次状态清空或一个工具返回值的处理方式，可能立刻改变 Agent 的可靠性。
Agent 的可用能力 = 模型能力 × harness 提供的观察、行动、状态与约束。

这不是论文给出的公式，而是我们的概括。它想强调：harness 不只是连接 API 的胶水，而是可执行、带状态、会持续演化的软件系统。
麻烦在于，需求用“行为语言”表达——例如“任务完成后必须二次确认”；仓库却按文件、类和函数组织。一个行为可能散落在提示模板、主循环、解析器、状态对象和异常分支中。知道“要改什么”，不等于知道“该改哪里”。
二、行为定位：改代码之前，先找到完整的行为

小机器人在代码迷宫中追踪分散的行为实现
论文将 behavior localization 定义为：找出实现某项目标行为的全部代码位置。这里最重要的是“全部”。只找到主路径而漏掉冷门分支，计划看似合理，落地后却会出现行为不一致。
传统关键词搜索擅长找名称，不擅长找语义。调用图能回答“谁调用谁”，却未必回答“哪些节点共同实现任务完成语义”。把整个仓库塞进长上下文，也只是扩大可见范围，不能自动建立行为到实现的映射。
作者结论：行为定位是 harness 演化的核心瓶颈，尤其影响跨文件功能、低频路径和跨模块状态交互。
我们的判断：这一问题并非 Agent 独有，但在 Agent harness 中更尖锐。它高度状态化，控制流常由模型输出、工具结果和环境事件共同决定；同一行为还可能跨越多轮执行。普通“代码地图”记录结构，harness 更需要一张“运行语义地图”。
三、Handbook：三层文档树，加一张状态地图

三层 Handbook 与跨阶段状态寄存器地图
Harness Handbook 的核心表示由两部分组成：L1—L3 文档树，以及互补的状态寄存器视图。
L1：系统级总览。 说明整体运行方式和主要阶段。

L2：阶段级概览。 解释各阶段职责、输入输出与关系。

L3：源代码支撑的细节单元。 落到函数、函数片段或文件，并保存可回到当前代码的 locator。

状态寄存器视图： 记录关键状态由哪个阶段写入、读取、清空或重置。

“寄存器”不是 CPU 寄存器，而是跨阶段共享状态的抽象。比如“连续完成确认次数”可能在结果解析阶段写入，在循环控制阶段读取，在新任务开始时重置。只看目录树，很容易漏掉其中一处；状态视图则沿数据生命周期追踪行为。
它先用静态分析提取程序事实，再借助 LLM 做行为化组织。重要的安全阀是：L3 定位必须回到当前仓库验证；失效条目会被冻结并排除，而不是让旧文档凌驾于源码。代码变化后，系统还会触发局部重同步。
我们的判断：真正有价值的不是“自动生成文档”，而是行为优先、源码可追溯、变更后可同步三项约束的组合。
四、BGPD：不要一上来就把整个仓库倒给 Agent

小机器人从系统地图逐层放大到具体代码
BGPD 全称 Behavior-Guided Progressive Disclosure，行为引导的渐进式披露。其路径可以概括为：
从 L1、L2 判断需求涉及哪些执行阶段；

沿状态寄存器补入共享状态耦合的远端阶段；

选择 L3 条目，取得候选源码位置；

沿调用关系适度扩展；

打开当前仓库，重新验证 locator；

只基于验证后的证据生成编辑计划。

它不是用文档替代代码搜索，而是先用行为地图缩小搜索空间，再让源码作最终裁判。上下文也不是越多越好：先给轮廓，再按任务揭示阶段、状态与实现细节，可以减少噪声。
五、关键数字：可喜，但要看清测了什么

定位更准、规划 token 更少的实验天平
实验使用 Codex 与 Terminus-2 两个开源 harness，每个仓库 30 个修改请求，共 60 个。规划器统一为 DeepSeek-V4-Pro；GPT-5.5、Opus 4.8、DeepSeek-V4-Pro 担任评审。
作者报告：
计划胜率：Codex 28.3%→38.3%；Terminus-2 26.7%→45.6%。

规划 token：Codex 10.2万→8.9万（-12.7%）；Terminus-2 5.8万→5.3万（-8.6%）。

文件/符号粒度的 Recall、Precision、F1 共 24 项全部提高；F1 增益 5.0—18.8 个百分点。

“完全零重合”的 Wrong 指标最多下降 25.9 个百分点。

这些数字支持“定位更准且更省规划 token”的作者主张。但实验直接评估的是行为定位和编辑计划质量，不是修改后代码的端到端正确率，更不是生产环境长期成功率。“弱模型匹配强模型”也只是对参考计划位置的接近程度。
六、别急着下结论：这项工作还缺什么
第一，论文只评编辑计划，不验证补丁与测试。第二，样本只有两个 harness、60 个请求，且 LLM 裁判不是人工金标准。第三，构建与重同步 Handbook 的成本没有完整计入。第四，静态分析难覆盖反射、动态加载、配置驱动流程和外部服务。第五，缺少各组件消融，也缺少与成熟代码索引/RAG 系统的充分对比。
我们核验过作者公开仓库：静态分析流水线可以运行，但完整评测代码并未公开，因此本文不把一次基础运行包装成“复现成功”。此外，仓库目前没有明确 LICENSE，正式集成还需等待作者补充授权。
七、对 Zero 这类 Agent 系统的启示

小机器人拿着行为地图核对真实源码
对 Zero 这类能调工具、管理记忆、委派任务并在真实工作区执行的 Agent 系统，这项研究带来五点实用启示：
把“行为目录”提升为一等资产；

显式追踪任务、授权、后台句柄、记忆写入和验证状态；

让 Agent 先定位影响面，再生成编辑计划；

让文档条目绑定文件、符号、范围或哈希，验证失败即冻结；

进一步把行为条目连接到测试、运行轨迹、权限规则与历史事故。

Harness Handbook 最值得关注的观点不是“再生成一本手册”，而是：当软件开始帮助修改自身时，必须先让“行为如何落到代码”成为显式、可核验的系统资产。
