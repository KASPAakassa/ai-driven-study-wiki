架构师（JiaGouX）
我们都是架构师！
架构未来，你来不来？

研发里，大概都见过这种“假完成”。
Agent 找到一条失败测试，改了几行代码，目标用例也绿了。第二天联调才发现，跨时区订单还没覆盖；接口少了一个兼容字段；发布说明引用的还是旧配置。
它确实修了一个 Bug，却没有把这项工作交到下一个人手里。
这种错位不只发生在代码里。月度分析写完了，工作簿没有更新；架构方案讲得很顺，迁移顺序和回滚条件还没落下来；一份行程看起来很完整，时间冲突、预订状态和预算仍散在聊天记录里。
在读腾讯 WorkBuddy 团队的 WorkBuddy Bench 论文时，最感兴趣的就是这个问题：Agent 的“完成”，到底应该由什么来证明？
《Claude Code 与 Codex 六大组件拆解：Coding Agent 怎么把任务做稳》最后停在“技术修复完成，业务验收待定”。WorkBuddy Bench 往前补了一步：把这种交接时的谨慎，做成可运行、可复现的评测协议。
论文换了一种测法。它把 Agent 放进完整代码仓库、可运行网页、混合办公文件和安全样本中，请求只交代目标与约束，Agent 自己寻找上下文，最后用文件、状态、测试和证据验收。
如果沿着一次交付往下看，链路大致是这样：

Agent 从自然语言请求到完成证据的交付链图 1：请求、现场、运行时、工件和验收要连成同一条链；对话结束只是其中一个时刻。
《从 Prompt 到 Graph：五层 Agent 工程，真正解决的是什么》讨论的是 Agent 怎样运行。WorkBuddy Bench 接着追问：运行结束以后，留下的东西够不够支持“完成”这个结论。Prompt、Context、Harness、Loop、Graph 管运行；WorkBuddy Bench 补的是验收端。
先看完成
“模型给出了答案”“Agent 执行了动作”“任务已经完成”，是三件不同的事。
放到工程现场里，大致能分成四层：
层次
看到了什么
还缺什么
回答
一段解释、方案或代码片段
没有进入真实工作区
动作
改了文件、调用了工具
不确定结果是否完整
交付
留下补丁、网页、报表或 PoC
还要核对状态与约束
完成
交付物可用，相关状态一致，证据可以复核
可以进入交接、发布或下一步

代码写完，只能说明实现动作结束。能不能进入下一阶段，还要看 CI、接口兼容、数据迁移和发布检查。架构评审也差不多：图画得再漂亮，依赖关系、故障域、迁移步骤和回滚条件没有落到可执行安排里，方案仍然难以实施。
Agent 有没有完成，最后还是要看工作区里留下了什么变化。
四个赛道的评分器并不相同，任务骨架却一致：Agent 进入一个有状态的工作区，根据一句自然语言请求产生工件，再由求解期间不可见的验证器检查结果。
题目要像工作
SWE-bench 把真实 GitHub Issue 和代码仓库带进了模型评测。它的经典任务形态是：给出 Issue，让 Agent 修改代码并通过相关测试。
WorkBuddy Bench 又往前走了一段。它不直接复用公开 Issue 的标题和描述，而是从历史 commit、PR、真实 CVE 或业务场景反向还原任务，再改写成同事之间常见的短请求。
Code 任务还会换成开发、算法、产品、QA、运维五种角色来提需求。请求会保留必要目标和限制，同时省略目标文件、根因、参考 diff、字段结构和部分边界条件。
论文里的一个产品分析任务，大意是：结账文案实验结束了，请计算各组转化率和收入，时间隔得太久的购买不要计入当前实验。
真实同事很可能就说到这里。再往下，他通常不会顺手补齐这些细节：
• 数据在哪个目录；

• 展示事件和购买事件怎样关联；

• 多久算“隔得太久”；

• 最终结果写成 CSV、报表还是代码；

• 项目里已有的归因口径放在哪里。

Agent 得从仓库、数据样例和既有实现中把这些信息找回来。
请求可以留白，工作区不能没有线索。 缺少的信息如果既不在请求里，也不在代码、数据、文档或接口中，Agent 只能猜，评测也就失去了稳定依据。
WorkBuddy Bench 所说的“贴近真实使用”，用的是汇总后的任务分类、请求结构和难度分布。原始用户 Prompt、会话和用户数据没有进入公开任务。它借的是任务分布，不是生产会话本身。这样既保留了真实工作的形状，也避开了直接公开用户数据。
现场要能回放
论文花了不少篇幅说明，一项任务怎样装进评测系统。
每项任务按统一目录封装，大致包含：
task/
├── instruction.md   # 自然语言请求
├── task.toml        # 类别、难度、资源与超时
├── environment/     # Docker 与 Agent 可见的工作区
├── tests/           # 任务结束后执行的评测资产
└── gold.patch       # Code 任务可选的诊断参考这个目录看起来简单，实际把几条关键边界固定了下来：
• Agent 从哪个版本、哪些文件和什么状态开始；

• 它能看到什么，哪些评测资产暂时不可见；

• 它可以使用哪些工具、网络和资源；

• 结果必须写到哪里；

• 任务结束后由什么程序或规则验收。

在《吴恩达开源版 WorkBuddy：拆解 OpenWorker 的桌面 Agent 架构》里，Progress、Artifacts 和 Audit 分别回答“做到哪了”“成品在哪”“做过什么”。WorkBuddy Bench 把这些问题写进一个可复跑的任务包：起点、权限、工件位置和验收程序都能重建。

这里的“隐藏测试”，只在 Agent 求解期间不可见。公开发布后，任务目录、环境、测试、评测代码和参考解都会开放。
论文也没有把防污染说成一种永久能力。公开任务迟早可能进入后续训练数据，它给出的边界很窄：通过重新构造请求关闭“搜索题面就能找到答案”的路径，再通过数据集版本更新管理发布后的暴露。
拿来做内部评测时，这个边界很合适。求解阶段需要隐藏的是本轮验收资产和未发布任务，不必把整个评测协议做成黑箱。协议、环境和结果越能复跑，模型升级或 Harness 改动以后，团队越容易知道分数为什么变了。

这些项目测的是不同边界，放在一张“谁更先进”的榜单里，意义不大。
例如，OSWorld 更适合看桌面 GUI、跨应用操作和视觉定位。WorkBuddy Bench 当前的 Office 子集是文本和文件优先，不覆盖 OCR、像素级版式判断或原生桌面 GUI。τ-bench 更关注动态用户交互、业务策略和 API 调用后的数据库状态；WorkBuddy Bench 更关注本地工作区里的多文件交付和可复核结果。
WorkBuddy Bench 的 Code 子集也主要是 Python，结论不能直接外推到所有语言和工程生态。
WorkBuddy Bench 多做的一步，是在同一套任务目录和运行协议下，对四种工件边界分别验收。统一的是任务怎么装、怎么跑；怎么打分，还是得看交付物是什么。

WorkBuddy Bench 四类工作现场与验收边界图 2：四个赛道共享任务封装和运行协议，交付物与验证器按工作性质拆开。
四个现场
Code：找到契约
Code 子集有 80 个任务，覆盖 18 个细分类目，由开发、算法、产品、QA 和运维五种角色提出。Bug 修复只有 10 个，其余任务包括功能与接口、代码工程、测试、算法、产品和数据分析。
任务来源也分成三类：34 个来自真实上游 commit 的开源仓库快照，24 个是 clean-room 重实现，22 个是为特定工作流编写的合成工作区。
每个候选任务进入公开集前，要先跑两次验证。未修改的基线工作区得分不能高于 0.3，避免“什么都不做也能过”；应用诊断用的 gold patch 后必须得到 1.0，确认任务和验证器存在可行解。
早期运行里有两种很典型的零分：Agent 一直修改测试文件直到超时；Agent 在大仓库里迷路，改了无关模块。
日常研发里也常见：卡住的往往不是那几行代码，而是 Agent 没找到负责这段行为的模块，或者没读懂现有接口契约。
论文数据也支持这一点：bug_fix 和 api_contract 的平均分都是 0.47，feature_pipeline 是 0.94，testing 是 0.88。一个实现即使语义大体正确，只要遗漏必需字段、参数形状或输出格式，接口相关检查仍会失败。
Web：留下工件
Web 子集有 70 个任务，要求 Agent 在声明路径下留下可运行前端工件。聊天里说已经完成，输出路径下没有页面，任务仍然失败。
35 个任务从零开始，另外 35 个分布在 Bug 修复、功能扩展、审查分析、测试生成和格式转换中。45 个任务包含交互或状态变化。
论文给了一个手机门店预约页面的例子：用户选择服务和时间，填写联系方式并确认；已满时段不能再选，提交前还要有复核步骤。
页面渲染出来，只过了第一关。剩余名额有没有真的参与状态判断，复核页和最终提交数据是否一致，刷新后状态是否保留，都要运行以后才知道。
评分也跟着拆成三类：规则检查文件、格式和可执行测试；LLM/VLM 判断文本、结构和视觉语义；Agent Judge 实际操作页面，检查流程、状态变化和持久化。
Office：保持一致
Office 子集有 50 个任务，输入和输出可以同时包含 xlsx、csv、PDF、文档、JSON、Markdown 和文件树。
它验收的是最终工作区。文件有没有生成只是起点，表格里的数字、报告里的结论、状态文件和交接材料还要互相一致。
有一种失败很眼熟：Agent 写出了一份看起来合理的分析报告，却没有更新报告所引用的工作簿。人读报告会觉得任务已经做完，下一位同事打开源文件时，看到的仍然是旧数据。
确定性规则负责检查文件、字段结构、数值、跨文件关系、状态变化和副作用；LLM Judge 只读取任务结束后抽取的固定证据，评估规则不容易表达的语义条件。每个任务预先配置两类分数的权重，论文给出的 Rule 权重范围是 0.70 到 0.95。
放回真实交付里，这个分工也挺自然：机器先查格式和确定事实，语义评审补充质量判断，但不能替文件存在性、数据一致性和状态检查改分。
Security：形成证据
Security 子集有 60 个任务，38 个红队、22 个蓝队，覆盖漏洞发现与安全验证、恶意软件分析、安全运营和 Agent 安全。
白盒任务使用 binutils、curl、nginx、vim、jq、fluent-bit 等项目的真实历史 CVE。Agent 要先定位漏洞路径，达到要求后再提交能够在隔离环境中稳定复现问题的 PoC。
流程并不复杂：
发现线索 → 定位原因 → 安全复现 → 留下证据整个 Security 子集不使用 LLM Judge，由确定性程序评分。论文还设置了五层反作弊检查，用来识别硬编码答案、输入重命名、环境篡改、编码依赖和低权重干扰项。
安全工作对“证据”的要求更高。只说“这里可能有漏洞”无法进入修复和响应流程；复现又必须留在受控沙箱里，不能把验证过程变成新的风险。

论文还固定了不少运行条件：高推理强度、200k 上下文窗口、统一的自动压缩阈值，并关闭 WebSearch 和 AskUserQuestion。Claude Opus 4.8 在 cc 的 Code 结果使用了额外的“一次完成、不提问”指令，所以表里保留了星号。
所以，评测记录里最好把这些条件一起留下：
模型 + Harness 版本 + 数据集版本 + 工具权限 + 指令与运行协议
官方仓库里的 Job 也按“模型、Harness、数据集”组合。只记录模型名，会把上下文治理、工具协议、权限和停止条件带来的差异藏起来。
成本也要连着条件看。Code 子集里，DeepSeek-V4-Flash 在 cc 下平均输出约 28.6k token，GPT-5.5 约 8.7k，前者分数低 14.74。不同模型的 tokenizer 并不相同，这组数据适合观察同一实验里的成本轮廓，不适合直接做跨模型的绝对效率结论。

这些任务的专业程度不同，交付结构却很相似。

《Agent 能干活之后，谁来管执行权？》关心动作发生前的授权和治理。WorkBuddy Bench 关心动作结束后的验收：哪些工件、状态和证据，足以把任务标成“完成”。一个管开工前，一个管交付后。

跑一次看看
腾讯官方仓库已经给出复现入口。每项任务运行在 Docker 中，需要 Python 3.12 以上、uv 和 Docker。数据集按赛道放在 Hugging Face，下载脚本会校验并解压。
最小流程如下：
uv sync
cp .env.example .env
./scripts/dataset/fetch-dataset.sh code

cp configs/models/_template.model.yaml configs/models/<provider>/<slug>.yaml
cp configs/jobs/_template.job.yaml configs/jobs/<slug>.yaml

uv run ./scripts/run.sh --job <slug> --dry-run
uv run ./scripts/run.sh --job <slug>模型配置引用后端地址和密钥对应的环境变量。真实凭据留在 .env，并确保它不进入版本库。
Job 配置至少写明三项：
model: provider/slug
harness: codebuddy-code/version
dataset: datasets/wb-bench-code-v1.0/tasks如果只想先跑通一轮，可以从一个赛道和少量任务开始，执行 dry-run，确认数据路径、模型连接、Harness 版本、超时和输出目录，再逐步扩大规模。
结果会保存在 results/。分数只告诉人“这次得了多少”。要解释失败发生在哪里，还得回到补丁、轨迹、测试结果、运行轮次和 token。
报告可以按下面几类问题归档：
• 找错对象：改了无关文件，或者一直在测试文件里打转；

• 契约遗漏：行为大体正确，字段、参数或输出格式不完整；

• 业务口径错：代码能跑，时间窗口、状态或归因关系错了；

• 交付没落地：聊天里说完成，约定路径没有成品；

• 证据不完整：发现了问题，复现、边界或后续交接材料不足。

按这个层次复盘，下一轮该改模型、改 Harness、补工作区信息，还是调整验收规则，就不容易混在一起。
写在最后
一套 Benchmark 覆盖不了所有真实工作。WorkBuddy Bench 自己也给出了边界：Code 主要是 Python，Office 还是文本和文件优先，开放发布会带来后续污染风险，模型裁判也需要持续校准。至于这些因素会怎样影响后续版本，还得看更多复现实验。
修 Bug 证明 Agent 能完成一个局部动作。完成工作还要再往前走：找到正确对象，理解现场约束，留下可使用的工件，让相关状态保持一致，并给下一位接手的人留下可以复核的依据。
对话可以结束，任务是不是完成，还是得回到文件、状态、测试和证据上。
