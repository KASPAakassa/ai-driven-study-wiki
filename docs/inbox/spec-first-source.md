这篇文章不是讲单一技巧，而是给 AI coding 装一套「决策操作系统」。
它要解决的问题很简单：把复杂工程判断拆成若干可复用的思考模型，用来看清因果、回归本质、判断边界、规避陷阱、理解长期效应和人性机制。
放到 spec-first 里，这套系统不是挂在墙上的概念海报，而是一条工程链路：
思维模型 → 更高质量的判断 → 更少被情绪、局部、短期和表象误导 → 更稳定的长期交付收益。

这四组不是随手归类：每一组管一类问题，正好对应后面决策栈的一层——因果与系统看连锁，本质与概率看真假，边界与规律看深浅，长期与人性看远近。
这套分类真正有用的地方，不是帮你背概念，而是把一个 AI coding 判断拆成五步：

关键不是这五步本身，而是它们的顺序：先看系统、再拆本质、然后校边界、最后推长期，任何一步跳过，后面都会替你付账——跳过系统视角，小歧义就放大成事故；跳过证据校准，demo 成功就被当成系统稳定。
先讲个很多人都熟的场景。
两个工程师，用同一个 AI、接同一个需求：给登录加个错误提示。
第一个人三句话甩过去，AI 改得飞快，半小时后他开始救火——错误提示是加上了，但顺手被改的认证逻辑挂了，测试一片红，他盯着 diff 一行行回滚，越改越慌。
第二个人慢了五分钟：先问清楚这算 bug fix 还是行为变更，圈定只动哪个文件，让 AI 给证据、跑测试，然后才合并。当晚他就敢把这个改动推上线。
差别真的是「第二个人 prompt 写得更好」吗？
不是。
第二个人赢在判断质量：他在 AI 动手之前，已经把这件事放进了一套可复用的思考框架里。

做 spec-first 才半年，AI coding harness 也才集中打磨了一个季度，我越来越确信一件事：那些被用来看清因果、判断概率、洞察人性的经典思维模型，换到 AI coding 的场景，几乎就是这套工程闭环里最缺的那层「判断力」。大家都在卷模型、卷 prompt、卷 agent 数量，但真实工程里反复翻车的，从来不是模型不够强，而是判断没跟上：该不该信这次输出、该不该让它继续改、这个改动到底动了多大范围。这些都不是「写更长的 prompt」能解决的，它们是思考框架的问题。
而思考框架，恰恰是人类已经积累了几十年的东西。我把自己反复用到的 16 个模型梳理了一遍，发现它们几乎一一对应 spec-first 设计里的某个硬约束——这篇就把这层对应关系讲透。
没读过前面几篇也不影响：只要先把 spec-first 理解成一层 AI Coding Harness——把不稳定的 AI 推理，放进可重复、可验证的工程闭环。这一篇是番外：不讲 skill，讲在用 AI 写代码时，脑子里到底该跑哪几个模型。
这篇文章不是 16 个概念的百科式解释，而是把它们压缩成一套工程判断清单：什么时候该信、什么时候该拦、什么时候该继续投、什么时候该停。
01 先给结论：这套模型怎么落到 spec-first
把 16 个模型落到 AI coding，不是为了多懂几个名词，而是为了把 spec-first 的工程动作解释清楚：为什么需求要先澄清、为什么计划要锁 scope、为什么证据要分级、为什么经验要沉淀。
我把它整理成一套四层决策栈：遇到一个 AI coding 的判断，从上往下过一遍。
系统层——这件事会不会连锁放大？谁在过度消耗公共资源？（蝴蝶效应、复利效应、创造性破坏、公地悲剧）

本质层——它的底层事实是什么？最简解释是什么？这是概率还是确定？（第一性原理、奥卡姆剃刀、概率思维、回归均值）

边界层——我和 agent 到底懂不懂？关键少数是什么？还值不值得加投入？（能力圈、帕累托法则、边际效用递减、大数定律）

长期层——下一步、再下一步会怎样？我的认知地图和真实系统差在哪？（二阶思维、社会认同、地图不是疆域、临界点效应）

这套栈的价值不在于背概念，而在于：
它把「AI 该不该这么改」从一种直觉，变成一条可以逐层追问的链路。

但也要防止另一种误用：不要拿模型给已经拍板的决定找理由。四层栈的用途是提前暴露风险、校准边界、要求证据，而不是事后把一次冲动包装成“系统思考”。
具体落到 spec-first，它会变成三类工程动作：
动手前：用系统层和本质层把需求说清楚，先判断这是 bug fix、行为变更，还是架构改造；再锁定 scope、non-goals 和验证方式。

执行中：用边界层和本质层里的证据分级约束 agent，不让它越过能力圈，不把 advisory 线索伪装成 primary 事实，也不因为一次 demo 成功就判断系统稳定。

完成后：用长期层校准真实系统，把 review failure、调试教训和可复用模式沉淀下来，让下一次任务不是从零开始。

效果也很具体：需求歧义更早被拦住，AI 幻觉更难伪装成事实，scope creep 更容易暴露，经验能进入下一轮上下文，而不是散落在聊天记录里。

下面我按这套栈逐层走：先深讲每一层里和 AI coding 翻车最相关的模型，最后用一节把跨层的「长期价值与采用」问题收束起来。偏背景性的模型不单独展开，但都在上面的总览表里给了位置——四层是用来归类的地图，深讲顺序服从「哪个最容易让 AI 翻车」。
02 系统层：小歧义会被多代理悄悄放大
AI coding 进入多步骤、多代理协作后，最大的隐患不是某一步明显错了，而是一个很小的偏差被一路放大。
02.1 蝴蝶效应：一个含糊的词，能毁掉整条链路
你在需求里写「优化一下登录」。
这个「优化」就是一只蝴蝶。它含糊，但没人当回事。到了 plan 阶段，模型把它理解成「重构认证模块」；到了 work 阶段，agent 顺手动了 session 逻辑；到了 review，没人记得最初只是想加个错误提示。
一个词的歧义，在多代理传递里被逐级放大成一次返工。
蝴蝶效应教我们的不是「所有小事都要紧张」，而是识别关键链路上的小问题。在 spec-first 里，这对应一个很硬的设计：先做需求澄清，把意图显式化（spec-prd / spec-brainstorm）；再做计划锁边界，写清 scope 和 non-goals（spec-plan）；最后做任务切片，只允许重排执行顺序，不能改 scope（spec-write-tasks）。
这几道关卡看起来像「流程变重了」，但它们要掐断的，正是蝴蝶振翅的传播路径。一个含糊的「优化」，如果在需求阶段就被逼着写清「只加错误提示、不动认证逻辑」，它就永远长不成那场认证模块的事故。越往后纠偏，成本越高——需求阶段改一句话，到了 review 阶段就是整段回滚。

要注意的另一面是：别把这个原则用过头，把每个小 typo 都当成系统级风险来处理。蝴蝶效应的重点是「关键节点」三个字——位于关键链路、关键依赖上的小问题才值得提前拦，无关紧要的小瑕疵过度解读，只会让流程空转。
决策提问：这个含糊的描述，如果一路传下去会被理解成什么？现在纠偏，成本是不是最低？
02.2 公地悲剧：共享上下文是会被污染的公共资源
多人、多 agent 共用一份上下文、一个 memory、一池 skill，这就是一块公地。
每个人都想「我多塞点上下文进去，AI 答得更全」。塞着塞着，上下文里混进了过期文档、生成产物、未验证的 provider 结果——公共资源被过度消耗，最后谁的判断都被污染。
只靠自觉是不够的，公地需要机制。spec-first 的做法是给上下文划产权边界：普通任务默认不读审计产物、运行时镜像这类容易过期或带噪声的材料（比如 .spec-first/audits/**、.claude/**、.codex/**），任务引用也必须指向最小有用片段（context_refs），而不是整库投喂。
这背后还有一个容易被忽略的陷阱：生成镜像是从 source 生成出来的运行时副本。如果你把 .claude/ 里那份过期副本当成真相去读，模型会基于一份「影子真相」做判断——它读的内容看起来很真，其实早就和源头漂移了。所以这里的产权规则不只是「少读点省 token」，而是「别让公共池里的脏数据污染每一次判断」。
共享资源没有规则，就一定会被过度消耗——AI 的上下文也不例外。

决策提问：这里有没有一块「没人负责」的共享资源？个体最优会不会导致整体最差？
03 本质层：先拆到底层事实，再挑最简解释
系统层看的是连锁，本质层看的是——别被表象和复杂叙事带跑。
03.1 第一性原理：从零设计，而不是在旧方案上修补
AI 最擅长的，其实是「在你给的方案上接着改」。这恰恰是陷阱：如果初始方向就基于一堆惯例假设，AI 只会把这个错误越描越细。
第一性原理要求你先拆掉惯例，确认不可再拆的事实，再从底层重新推导。
设计规范框架时，这意味着回到几个底层问题：这次改动的行为契约是什么？怎么验证它对了？状态真相源在哪？这正是需求阶段拆回 WHAT / WHY、计划阶段推导 HOW 时要做的事——它不让你在模糊需求上直接堆代码。
举个最常见的反例：你让 AI「把这个接口改成异步的」。如果不先拆，AI 会默认沿用现有的错误处理、现有的超时假设、现有的调用方契约，在一堆没被确认的惯例上接着改。而第一性原理的问法是：异步之后，调用方还能假设立即拿到结果吗？失败语义变了吗？这些底层事实一旦摊开，方案往往和「在旧代码上改改」完全不同。

当然也有边界：不能把自己的假设误当成第一性事实。「拆到底」是拆到可被验证的事实，不是拆到你拍脑袋认定的那个起点。
决策提问：去掉「大家都这么做」之后，这件事最基本的事实是什么？如果从零设计，我会怎么做？
03.2 奥卡姆剃刀：别让 AI 帮你把问题复杂化
排查一个 bug，AI 经常一上来就给你一套精巧的多因素解释。听起来很高级，但奥卡姆剃刀提醒你：假设最少、结构最简的解释，往往更可靠。
先看简单原因，再看复杂原因；设计方案时减少不必要的角色、流程、抽象层。Harness 本身也守这条——它不堆砌命令和 agent，而是用最少入口覆盖真实需求。
一个真实的调试场景：接口偶发 500，AI 第一反应给你一套「可能是并发竞争 + 连接池耗尽 + 缓存击穿」的复合假设，听起来很专业。但奥卡姆剃刀让你先问：有没有更简单的？翻一眼日志，往往就是某个上游昨天改了返回格式，一个字段变成了 null。复杂解释不是错，而是它把你的注意力从最可能的那个原因上引开了。所以调试流程要先列假设、按概率排序、用证据逐个证伪，而不是一上来就信那个最精巧的故事。
简单不是简陋。但当 AI 给你一个绕了三层的解释时，先问一句：有没有更直接的那个？

决策提问：有没有更简单的解释？这个方案是不是为了显得周全，引入了不必要的复杂度？
04 本质层（续）：AI 的输出是概率，不是真相
这一层单独拎出来，因为它是 AI coding 区别于传统编程最关键的认知差。
04.1 概率思维：好决策也可能有坏结果
传统代码是确定的：同样输入，同样输出。AI 不是。同一个 prompt 跑两次，可能给你两个答案。
所以好的 AI coding 决策，不是追求「这次一定对」，而是在概率意义上提高胜率：关注期望收益，接受「好决策也可能偶尔翻车，坏决策也可能侥幸成功」。这就是为什么 review 和 debug 结论都必须带证据分级，而不是把单次输出当成确定事实。
证据被锁死成四个可信等级：

primary：已确认，由源码、测试、schema 或命令结果支撑

session-local：只在本次会话成立，没被持久确认

advisory：只是线索，比如 provider 给的一个 pointer

stale：已过期，不能再当真

系统还锁了一张「非法组合表」：能力 unavailable 却声称证据 primary 是不允许的——这堵的正是「工具没用上，却假装拿到了确认」这种最常见的 AI 幻觉。
这套分级落到日常，会改变你读 AI 输出的方式。AI 说「这个函数没有别的调用方，可以安全删除」，你的第一反应不该是删，而是问它：这是 primary（真跑了引用查找）还是 advisory（它扫了一眼觉得没有）？同一句话，证据等级不同，你该承担的风险完全不同。把每一个结论都习惯性地贴上等级标签，幻觉就很难再伪装成事实。
决策提问：这个结论是 primary 还是 advisory？如果重复跑 100 次，它还占优吗？
04.2 回归均值：一次 demo 成功不代表系统稳定
AI 给你跑通了一个漂亮的 demo，你很容易高估它的能力。回归均值提醒你：极端表现之后，大概率会回到正常水平。一次超常发挥，可能只是运气。
判断 harness 到底好不好，不能被几个亮眼案例带跑。一次惊艳的生成、一次漂亮的自动修复，都只能说明“这次表现很好”，不能说明“系统已经稳定”。所以优化流程不能接受「优化好一点」这种模糊请求，而要先定义可度量目标和度量命令，跑多组实验、用 gate 或 LLM-as-judge 打分，向更优解收敛。没有指标，就不该急着下结论。
单次 demo 是个例，不是能力画像。别用一次惊艳，给系统定性。

决策提问：这是趋势还是异常波动？我是不是被一次超常发挥带偏了？
05 边界层：知道自己和 agent 到底懂不懂
好判断不是无限自信，而是清楚边界在哪。
05.1 能力圈：通用 agent 不该什么都接
能力圈说的是：只在你真正理解的领域下注。
放到 AI coding，这条同时约束人和 agent。对人：不懂的领域别因为 AI 看起来很能干就盲目放手。对 agent：不该让一个通用 agent 处理所有任务，而要给它明确的职责边界。spec-first 里 workflow、skill、reviewer、script、LLM 各有清楚分工——脚本只准备可复验事实，LLM 才做语义判断，这就是「Scripts prepare, LLM decides」。
为什么要这么分？因为脚本和 LLM 的能力圈正好互补：脚本擅长文件发现、路径解析、git 状态、schema 校验这些可复验的确定性事实，但它不该假装自己是架构师；LLM 擅长需求理解、架构取舍、风险解释这些语义判断，但它不该假装自己跑过了确定性校验。一旦越界——让脚本模拟架构判断，系统变成脆弱的规则引擎；让 LLM 假装跑过校验，系统变成不可验证的幻觉。承认边界，比假装全能更安全。

决策提问：这件事在我（或这个 agent）的理解边界内吗？我知道自己不知道什么吗？
05.2 帕累托、边际效用与大数定律：别平均用力，也别被小样本骗
帕累托法则：80% 的质量提升，往往来自 20% 的关键规范、测试和工作流。所以 plan 和 review 要聚焦高杠杆风险点，而不是平均扫描所有可能。
边际效用递减是它的另一面：继续加 agent 数量、加文档长度、加 persona，新增收益会越来越小，甚至因为协调成本转负。判断「还要不要再加一个任务/一份文档」，本身就是一个该被问出口的决策。
很多团队对 AI coding 的直觉是「越多越好」：更多 agent、更长的规范文档、更细的 persona 分工。但加到某个点之后，多出来的不是能力，是协调成本——三个 agent 要对齐的上下文，比一个 agent 多得多。计划和任务拆分阶段反复要问的，正是这个边际问题：再拆一个任务、再加一段约束，是真带来新增收益，还是只是让治理本身变重？
大数定律则提醒你：判断哪 20% 真正关键，要看足够多的任务样本，不是看一两次“这招好像很灵”。如果只有三个案例，就急着把某条规则写进团队标准，很容易把偶然经验制度化；反过来，如果几十次 review failure 都指向同一个缺口，那它就不再是个人偏好，而是值得固化的关键少数。
最大投入不等于最优投入。找到边际平衡点，比无脑堆量更难，也更值钱。

决策提问：哪 20% 的动作带来了 80% 的结果？继续加投入，新增收益还值得吗？我的样本量够支撑这个判断吗？
06 长期层：推演二阶后果，别迷信认知地图
决策不能只看眼前那一步。
06.1 二阶思维：多问一句「然后呢」
一阶收益常常带来二阶损害。
你给 AI coding 加一条自动化规则，一阶是「省事了」。但二阶呢？开发者会不会因此不再读 diff？agent 会不会学会绕过这条规则？好策略通常不是一阶最爽，而是二阶、三阶仍然稳健。所以需求、计划和团队标准治理里都要推演：规则落地后，开发者行为和下游消费者会怎么变。
这里还藏着一个更隐蔽的二阶效应，叫古德哈特定律：当一个指标变成目标，它就不再是好指标。比如你用「自动生成了多少行代码」衡量 AI 的贡献，二阶后果就是大家开始比谁生成得多——而不是谁解决得好。所以优化时不能把使用量当目标，真正要度量的是工程质量有没有变好，不是 AI 用得勤不勤。

决策提问：这个决定的直接结果是什么？之后会引发什么反应？长期会改变什么激励？
06.2 地图不是疆域：spec 文档不等于真实系统
这是我最想强调的一个。
我们写的 PRD、plan、架构图，都只是现实的简化地图。最危险的事，就是把地图当成疆域——以为文档说什么，系统就真的是什么。
AI 尤其容易掉进这个坑：它读的是文档，答的却像是在描述真实系统。spec-first 的对策是 living contract——把 PRD、plan、review 都当地图，持续用源码、测试、runtime evidence 去校准真实状态。一个典型例子是代码图谱：如果事实文件标着“工作区有未提交改动，只能参考”（例如 graph-facts.json 里的 dirty-advisory），那它就不能被当成确认证据，只能当成下一步查证的线索。
我自己踩过最典型的一次：架构文档里清清楚楚写着某个模块「已经解耦」，AI 也信誓旦旦照着这个前提给方案。结果翻源码发现，解耦只做了一半，还有三处硬依赖没拆。文档是上个季度的地图，疆域早就变了。从那以后我养成一个习惯：凡是 AI 基于文档给的关键结论，落地前必须有一条源码/测试级的证据回扣，否则它就只是一张可能过期的地图。
不要因为沉没成本，就抱着一张错误的地图往前走。让事实有权推翻原计划。

决策提问：我的认知地图和现实差在哪？有哪些事实正在挑战原计划？
07 跨层收束：经验为什么复利，方法为什么被采用
收尾这一节跨越前面几层，回答一个更大的问题：这套工程化投入，凭什么长期划算，又凭什么让别人愿意采用？它牵涉四个模型——复利、临界点、社会认同、创造性破坏。
07.1 复利效应：可沉淀的经验才会指数增长
AI coding 最大的浪费，是每次任务都从零开始。同一个坑，今天踩、下周换会话再踩、过段时间换模型又踩。
复利效应说：微小但持续的积累，长期会形成指数级收益。前提是它得能沉淀。spec-first 把一次 bugfix、一次 review failure 写进 docs/solutions/，让它成为下一次任务的上下文资产。一次解决，多次复用——这才是复利。
关键在于「能不能被下次发现」。聊天记录里的经验等于没有：它不可搜索、不可被后续 workflow 引用，下周就蒸发了。而写进 docs/solutions/ 的结构化文档，会被 spec-plan、spec-code-review 通过 context_refs 按需召回。区别就像「记在脑子里」和「记进团队 wiki」——前者随人走，后者随项目复利。
决策提问：这次经验能不能被下次自动找到？它是聊天里的感想，还是项目里的资产？
07.2 临界点效应：突破前的平台期最容易放弃
规范、工具、测试、memory 累积到一定程度，会发生质变——工程效率突然上一个台阶。但临界点之前是平台期，看不到明显回报，最容易放弃。

识别关键阈值（知识覆盖度、标准覆盖率、readiness 指标），判断你是在合理坚持，还是无效消耗。难点恰恰在于：平台期里「方向错了」和「还没到临界点」长得一模一样，都是「投入了但没回报」。区分它们不能靠硬扛，要靠指标——覆盖度还在涨、readiness 还在逼近阈值，就值得再走一段；指标停滞甚至倒退，才是该转向的信号。
坚持不是盲目硬扛。但在临界点前放弃，等于把前面所有积累清零。

决策提问：我是在接近阈值，还是指标已经停滞？继续坚持的证据是什么？
07.3 社会认同与创造性破坏：采用决策的人性面
再好的工程方法，也不是靠“我觉得对”被采用的。社会认同提醒我们：真实案例、star、使用反馈、团队内的成功复盘，都会影响别人要不要相信这套流程。但这种信任只能建立在真实价值上，伪造背书反而毁信任。
放到 spec-first，最有说服力的不是一句“我们很工程化”，而是一次次具体交付：某个需求因为 scope 先锁住，没有被 AI 扩大成重构；某次 review 把不可验证结论拦住，避免了上线事故；某个调试教训被沉淀后，下次同类任务直接复用。这些才是社会认同的燃料。
创造性破坏讲的是另一面：新方法不是在旧流程旁边加一个装饰，而是真的会替代一部分低效环节。以前靠人肉记忆、聊天记录、临场 review 兜底的地方，会逐渐被结构化需求、证据分级、可检索知识库取代。抗拒变化，往往比变化本身更危险。
当然，破坏的对象应该是低效惯性，不是工程纪律本身。spec-first 要替代的是“让 AI 自由发挥然后人工救火”，不是替代人对产品、架构和风险的最终判断。
这里最容易误用的是把社会认同变成 star 崇拜，把创造性破坏变成“旧东西都该扔”。前者会让你追热闹，后者会让你丢掉成熟流程里真正有价值的纪律。真正该看的，是真实交付有没有变稳、证据有没有变硬、经验有没有能复用。
决策提问：我维护的是价值，还是惯性？我有没有真实信号，而不是自说自话？
08 把模型装进流程：一份 AI coding 决策清单
单个模型只是工具，真正有效的是组合成流程。把四层栈收成一份可以贴在工位上的清单：

这张清单不是 16 个模型的全量映射，而是日常使用时的操作压缩版：把最容易影响 AI coding 判断质量的提问，压成动手前能快速过一遍的 8 个检查点。
本质（第一性原理）：这件事最底层的事实是什么？是 bug fix 还是行为变更？

系统（蝴蝶效应 / 公地悲剧）：哪个小歧义会被放大？哪块共享上下文会被污染？

边界（能力圈 / 帕累托）：我和 agent 真的懂吗？哪 20% 是关键？

证据（概率思维 / 回归均值）：这个结论是 primary 还是 advisory？是趋势还是个例？

投入（边际效用递减）：继续加任务、加文档，还有新增收益吗？

长期（二阶思维）：这么做，然后呢？再然后呢？

校准（地图不是疆域）：我的计划被真实数据验证过吗？

坚持（复利 / 临界点）：这是临界点前的平台期，还是方向错了？

三句最值得内化的话：
不要只看结果，要看系统。
不要只看当下，要看复利和二阶后果。
不要迷信认知地图，要持续用现实校准。

回到开头那两个工程师。第二个人之所以敢交付，不是因为他的 AI 更强，而是因为他在动手前，脑子里跑过了这套栈：先拆本质，再防放大，认清边界，要证据，推演长期，用现实校准。
而 spec-first 这层 Harness 想做的，正是把这套判断从「靠个人经验」变成「项目里可复用的结构」。
模型不会替你做决定。但有了模型，你的每一次决定，都会发生在更好的判断条件里。

如果你正在把 AI coding 从个人技巧变成团队流程，这篇可以当作一张判断清单。
如果你身边也有人天天在被 AI 改崩的代码救火，把这篇转给他——少踩一个坑，也是省一个通宵。
