# 原始资料:Agentic Abstention:当 AI Agent 该学会"停下来"

LLM Agent 最缺的不是完成能力，而是「判断何时继续行动只会浪费算力和用户耐心」的止损判断力——这篇论文用 28,000 个任务证明，开源模型在网购场景中及时止损率可以翻倍。

01 引子：一个粉色枕头引发的Agent困境
1.1 场景：用户说"买粉色客厅枕头"，但店里没有
想象一个AI导购Agent。用户说："帮我买一个粉色客厅枕头，价格在30美元以内。"
Agent开始做它最擅长的事：搜索、筛选、点击、比价。第1轮，它在搜索框里输入"pink living room pillow under $30"；第2轮，它发现结果里没有粉色；第3轮，它尝试"light pink pillow"；第4轮，它改成"pink cushion"；第5轮，它点进一个商品详情，发现其实是桃色；第10轮，它终于停下来，告诉用户："找不到完全符合的商品。"
这是一个真实的问题。论文来自WebShop——一个模拟电商网站环境的数据集。研究者发现，面对同一个不可行的任务，不同Agent的轨迹千差万别：有人第2轮就停下来解释"找不到"，有人搜了4轮才放弃，还有人一直搜满10轮也没停。
问题不在于Agent能不能完成任务。问题在于：Agent不知道什么时候该停止。
1.2 这不是答错题，而是"什么时候该弃权"
传统AI里有一个经典问题叫"LLM Abstention"：模型在回答不了时，能不能说"我不知道"。它通常是一个单轮决策——用户问一句，模型答或不答。
Agentic Abstention把它升级成了多轮决策问题。Agent不再只是"答或不答"，而是要在每一轮之后判断：
我已经有足够信息回答吗？

我再搜一轮会不会更接近答案？

环境是不是已经给出了足够的否定证据？

继续行动的收益，还值不回用户等待的时间和我消耗的token吗？

这就像经验丰富的顾问：他不会在客户说完需求后立刻说"办不到"，也不会在证据已经足够时继续浪费客户的钱。他会在恰当的时机给出判断。
1.3 这篇论文的核心
这篇论文的核心论点是：当任务目标模糊、环境缺资源或前提错误时，可靠的Agent应该像经验丰富的顾问一样，在证据足够时及时停止，而不是继续消耗用户的信任和成本。
作者把这种能力称为Agentic Abstention，并提出了一个不需要微调模型参数、只通过上下文工程就能改进的方法：CONVOLVE。
02 问题：为什么"停下来"比"做出来"更难
2.1 三类让Agent应该停下来的任务
论文把弃权场景拆成了三类。每一类都是真实产品中经常遇到的情况。
类型
含义
典型例子
Request-based Abstention
请求本身就有问题
"推荐一款最贵的、但性价比最高的手机"——主观偏好矛盾
Environment-based Abstention
环境缺少目标或依赖
"买粉色枕头"但店里没有粉色
QA Abstention
检索后仍无法回答，或问题带假前提
"请用Google Scholar证明AI会毁灭人类"——检索不到可靠证据
Request-based的问题，往往在Agent开始行动之前就该识别。但用户不一定能清晰表达，Agent需要在交互过程中慢慢发现。比如用户说"我想要一款拍照好、续航长、又便宜的游戏手机"，这些需求可能本身就难以同时满足。
Environment-based的问题更隐蔽。请求听起来合理，但环境里确实没有答案。Agent如果只盯着"再搜一次可能就有"，就会陷入无限循环。
QA Abstention则是传统领域的延伸。但即使是这里，Agent也面临新的复杂性：它可以先搜索、再判断，而不是一次回答就定生死。
2.2 从单轮判断到多轮决策：问题的本质变了
传统LLM弃权只问一句话："我现在知不知道？" Agent弃权问的是三句话：
我现在知道吗？

我再行动一次会知道吗？

环境已经告诉我"不可能"了吗？

论文用POMDP（部分可观察马尔可夫决策过程）形式化了这个问题。但不用公式我们也能理解：Agent的"信息状态"是不断变化的。每一次搜索、点击、调用工具，都会带来新的观察。好的Agent需要根据累积的信息状态，决定是继续、回答还是放弃。
更麻烦的是，弃权本身也是一种行动。Agent可以选择"继续搜索"，也可以选择"停止并解释原因"。这两种行动都有成本：继续可能浪费资源，停止可能错过本可解的任务。这个权衡没有简单答案。
2.3 28,000个任务说明：当前Agent普遍"刹不住"
论文在三个场景下测试了13个LLM-as-Agent系统：
WebShop（网购）：超过20,000个任务

终端环境（Terminal/代码任务）：数千个任务

QA（HotpotQA等）：数千个任务

核心发现很惊人：最强基线在WebShop上的及时止损率（AbsRec@1）只有26.7%。也就是说，超过70%的情况下，Agent要么放弃得太晚，要么干脆不放弃。
终端任务更差：某些设置下只有21.6%。QA任务好一些，但某些类别也不到50%。
这不是某个模型的bug。这是整个行业的问题：我们训练Agent去完成，却很少训练它们去停止。
03 方法：CONVOLVE，用一本"动态错题本"教Agent止损
3.1 核心思路：不改模型参数，只改上下文
CONVOLVE是一种"Agentic Context Engineering"。它不动模型的权重，而是给Agent附加一个不断学习的经验手册（playbook）。这个playbook里记录的是：什么信号出现时，Agent应该停止。
对很多企业来说，这一点非常关键。微调大模型成本高、数据需求大，还要担心破坏模型原有的能力。而上下文工程只需要维护一本规则手册，成本低、风险小、可解释性强。
3.2 从完整交互轨迹中蒸馏"停止规则"
CONVOLVE分两个阶段运行。
第一阶段：Reflection（反思）
研究者先让Agent运行大量任务，收集完整的交互轨迹。然后，一个反思模型回顾这些轨迹，找出问题所在：
在哪一轮，环境已经告诉Agent"这个任务不可行"？

哪些后续动作是多余的，只是重复之前已经失败的尝试？

如果更早停止，应该用什么理由向用户解释？

第二阶段：Curation（整理）
反思的结果被提炼成结构化的规则，写入playbook。这些规则不是抽象的"不要过度搜索"，而是具体的、可执行的：
如果连续两次搜索返回"无结果"，且第三次搜索只换了同义词，则停止并解释"环境中找不到匹配商品"。

如果终端命令连续返回"command not found"，且用户要求的是特定工具，则停止并解释"环境缺少必要依赖"。

这个过程像老中医整理误诊案例：不是背更多药方，而是把"什么情况下不能用什么药"的经验写成禁忌。
3.3 小模型也能教大模型：规则的可迁移性
论文里最有意思的发现是规则的跨模型迁移。
研究者用Llama-3.3-8B生成停止规则，然后把这些规则放到Llama-3.3-70B的上下文里。结果是：70B的及时止损率从26.7%提升到了55.3%，接近70B自己学习自己的57.4%。
这说明什么？停止规则本身比模型规模更重要。一个8B模型也能总结出有用的规则，而大模型只需要"知道这些规则"就能大幅改进。
这也解释了为什么上下文工程是有效的：它不是在教学生更多知识，而是在给有经验的专家一本操作手册。
04 实验：数据里的反直觉结论
4.1 及时止损率：Agent普遍的阿喀琉斯之踵
论文提出了两个关键指标：
AbsRec@1：在第一次有机会停止时就正确停止的比例，也就是"及时止损率"。
AbsRec@10：在前10轮内某个时刻正确停止的比例，也就是"整体止损率"。
在Web、Terminal、QA三个场景下，AbsRec@1普遍很低，而AbsRec@10明显更高。这说明：
Agent不是不会弃权，而是弃权太晚。

它们通常要多浪费好几轮工具调用，才最终意识到任务不可行。这在真实产品里意味着用户要等待更久、消耗更多token、体验更差。
4.2 模型越大，不一定越会停
Scaling Law在Agentic Abstention上似乎失效了。
论文在Qwen3系列上做了实验：从8B到235B，整体弃权率（AbsRec@10）确实提升了。但及时止损率（Timely Recall）几乎没有变化。
这背后的原因很反直觉：更大的模型反而更"执着"。它们更相信自己的能力，认为"我再搜一次就能找到""我再试一个命令就能解决"。这种过度自信让它们更难及时止损。
这也给行业提了个醒：模型能力的提升，不等于判断力的提升。我们习以为常地认为"模型越大越可靠"，但在"什么时候停"这个问题上，大模型可能反而更差。
4.3 推理与scaffold：一把双刃剑
论文还测试了更多推理（thinking）和不同scaffold设计的影响。
推理的影响：在Web任务上，更多推理确实能提升及时止损率。但代价是整体弃权率下降——也就是说，模型变得更谨慎，但也更容易在该停止的时候不停止。同时，过度推理还会带来过度弃权（over-abstention），在Web可解任务上，Qwen3-235B-Instruct的错误弃权率可达34%。
Scaffold设计的影响：在终端任务上，Codex CLI作为scaffold比另一款 scaffold（Terminus 2）强了一倍。这说明工具接口和交互框架的设计，对Agent的弃权行为影响巨大。同样的模型，放在不同的工具环境里，判断力可能完全不同。
这些实验指向同一个结论：Agentic Abstention不是单纯靠"换个大模型"或"加更多推理"就能解决的问题。它需要系统性的方法设计。
4.4 CONVOLVE的效果：从26.7%到57.4%
在WebShop上，CONVOLVE让Llama-3.3-70B的及时止损率从26.7%提升到57.4%。这意味着，超过一半的不可行任务，Agent在第一次有机会停止时就做出了正确判断。
而且这个提升是在不更新模型参数的情况下实现的。只需要把失败轨迹中蒸馏出的规则加入上下文，Agent的行为就大幅改变。

05 启发：Agent产品化从"能力"走向"判断力"
5.1 对行业的三点直接启示
第一，客服和导购Agent不能只教"推荐"，也要教"拒绝"。
一个只会推荐的Agent，遇到无法满足的需求时会做什么？要么给用户一个错误的推荐，要么无限循环直到用户放弃。真正有用的Agent，应该能识别"用户需求无法被满足"，并及时给出解释和替代方案。
第二，搜索和研究Agent需要"搜索边际收益递减"的停止机制。
很多研究Agent把"多搜几轮"作为卖点。但如果它不知道何时停止，多搜几轮只是增加了用户的等待时间和token成本。好的研究Agent应该能判断：当前检索结果是否已经足够？继续检索还会带来新的信息吗？
第三，RPA和代码Agent的scaffold设计要和模型能力匹配。
同样的模型，在不同的工具接口下表现可能完全不同。如果scaffold设计让模型容易陷入无意义的循环，再大的模型也救不回来。产品工程师需要把"停止"作为工具设计的一等公民。
5.2 CONVOLVE为什么有效：它补的是"经验"而非"参数"
传统微调让模型"背"更多知识。CONVOLVE让模型"看"更多经验。
停止规则是一种隐性经验。资深的客服知道什么时候该说"抱歉没有"，资深的工程师知道什么时候该说"这个环境跑不了"。这些经验很难通过预训练获得，因为它高度依赖具体环境和任务类型。
CONVOLVE的价值在于，它把这些隐性经验显式地写成规则，注入上下文。对企业来说，这意味着：
不需要大规模标注数据；

不需要昂贵的模型微调；

规则可解释、可审计、可更新；

可以用小模型总结规则，大模型执行规则。

这在合规性、成本和可控性上都是优势。
06 总结
Agent的下一个竞争点不是"多能做"，而是"多懂停"。及时止损率目前仍是全行业的短板，大模型也会"钻牛角尖"。用失败轨迹蒸馏规则、注入上下文，是一条低成本、可迁移的改进路径。
