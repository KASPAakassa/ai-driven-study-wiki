企业 Agent 工具治理，工具太多后为什么一定会失控失控不是因为某个工具坏了，而是工具数量本身，就是失控的来源。

这是《企业 Agent 工程化手记》的第 2 篇。
上一篇真正拖慢 Agent 协作的，不是犯错，而是停不下来我写到，Agent 最容易失控的地方，是 任务边界没有被重新声明。
这一篇要往前找一个更隐蔽的源头：工具。
过去一段时间，我一直在给 Agent 加能力。挂 MCP，装 skill，加命令，接业务系统。我默认这是好事，能查的越多、能调的越多，它应该越像一个能干活的助手。
直到我去看协作日报。
一天里，光是工具调用的回传就有 4286 次，授权确认转录 682 次，技能说明被整段灌进上下文 60 次。
样本说明：这是我 2026-06-12 的个人 AI 协作日报，不是行业统计；计数按用户消息级标签归类。

个人 AI 协作日报中的工具噪音指标：tool_io 4286、授权确认 682、skill_dump 60

这些数字不能直接推成行业结论。
但它们让我意识到一件原本被我忽略的事：
工具越多，上下文越脏，注意力越散，越界的机会也越多。工具太多之后，Agent 不是可能失控，而是一定会失控。

我们对工具的直觉是错的
我们天然觉得，能力等于工具数量。
能查的越多，能调的越多，Agent 看起来越万能。Demo 阶段，这个直觉几乎不会出错。因为那时候工具少，任务单一，上下文干净。
问题从工具变多开始。
每一个工具都不是免费的。它要被模型在每一步重新权衡，也可能被错误调用。工具不是加了就有用的能力，而是一份有持续开销的负债。
每多挂一个工具，模型每一步就要多做一次判断，上下文每一轮就要多背一份噪音。
第一类失控：Agent 不知道该用哪个工具
工具一多，第一件事不是变强，而是先要决定用哪个。
几个功能相近的工具同时存在，模型会来回试。本该用 A 的场景挑了 B，然后再补救。挑工具这一步本身，就在消耗推理预算。
我那天的日报里，验证补跑 92 次，返工修正 190 次，都比平时高出一截。
我不能说每一次返工都来自选错工具，但这些信号叠在一起，至少说明链路复杂度已经明显抬高。
挑工具，成了它真正开始干活之前最容易出错的一步。
第二类失控：工具把注意力稀释掉了
这是我现在最在意的一类。
每次工具调用都会回传一段结果。工具越多、调用越频繁，上下文里就塞满了这些回传。那天 4286 次工具回传，意味着真正重要的目标、约束、验收，是泡在一大片工具输出里的。
技能和工具说明也是一样。它们会被整段灌进上下文，占掉大量注意力，却很少被真正用上。那天这种"整段灌入"出现了 60 次。
这不是只有个人体感。MCP 工具说明已经开始被单独研究，比如论文 Model Context Protocol (MCP) Tool Descriptions Are Smelly! 讨论的就是工具描述质量问题。工具说明写得越多、越乱，模型在选择和调用工具时要消化的噪音就越多。
放到手机屏幕上看，我更愿意把这几种噪音写成对照：
大量工具回传：看起来信息很全，实际代价是关键信号被淹没。

技能说明整段灌入：看起来能力很足，实际代价是注意力被无效占用。

授权确认堆积：看起来很可控，实际代价是上下文越来越脏。

多工具并行调用：看起来很强大，实际代价是模型每一步都要重新权衡。

模型的注意力是有限预算。上下文越脏，真正该聚焦的地方反而越看不清。
工具出错还能修。工具一起把上下文塞满，模型连该看哪里都不知道，这才是更难发现的失控。

工具太多带来的三类失控：选择噪音、上下文污染、动作面放大

第三类失控：能做的事越多，越界越容易
前两类是看不清，这一类是做错事。
工具数量直接决定了 Agent 的动作面。只读工具多，最多是噪音。但可写、可发送、可提交的工具一多，越界和不可逆动作的概率就会上升。
那天授权确认转录有 682 次。
确认环节这么频繁，本身就是一个信号：人已经在为工具的越界风险持续买单了。每一次确认，都是在替一个动作面太大的 Agent 兜底。
给 Agent 装一个能改数据、能发消息、能提交审批的工具，等于给它开了一条可能越界的路。工具越多，这样的路就越多。
为什么企业 Agent 工具越多越危险
Coding Agent 工具太多，最多是返工、试错、改坏代码。这些还能靠差异检查、测试和代码审查拦下来，成本变高，但通常能回退。
企业 Agent 不是这样。
一个企业 Agent 一旦同时接入查询、写入、发送、审批和外部系统，它的工具越多，就越意味着它能同时碰客户数据、业务状态和不可逆动作。
工具层正在变成 Agent 生态里越来越大的动作面。论文 How are AI agents used? Evidence from 177,000 MCP tools 用大量 MCP 工具样本观察 Agent 工具使用，这类研究本身就说明一件事：Agent 的风险不只在模型回答，也在它能调用什么工具。
放到 CRM Agent 上，问题很具体：
既能查客户、又能改状态、还能发邮件时，选择噪音会直接变成业务事故。

工具说明、字段字典、权限说明一股脑塞进上下文，"这次只允许查询"这句关键约束反而被淹没。

工具越多，误改、误发、误提交的入口就越多。

多个业务系统的工具并存时，模型容易跨区域、跨权限乱调。

企业 Agent 的风险，不是工具不够用。
而是工具太多、太杂、太强，却没有被治理。
我最近处理过一次 skills 分类
这个问题不是抽象判断。
我最近刚处理过一次本机 skills 分类管理。起因很具体：Codex 出现了 skills context budget 警告。
一开始我以为，是不是某几个 skill 的说明写得太长。后来扫了一遍才发现，问题不在某个 skill，而在默认可见面太大。
当时本机能扫到 63 个 SKILL.md，active preset 里有 23 个 skills，再加上插件注入，Agent 在真正开始做事之前，先要面对一大片可能无关的能力说明。
这和企业 Agent 接很多业务工具是同一个问题：工具库越大，默认暴露面如果不收敛，上下文就会越来越重。
后来的处理不是把工具全删掉，而是按工作模式重新分组。
Default 收敛到 5 个保底能力，只负责最基础的协作和代码库定向。

vibe coding 收敛到 15 个日常工程能力，专门服务编码、调试、测试、评审、BML 和 Dataverse 这类任务。

writing-publishing 单独放写作和发布能力。

visual-design 单独放视觉设计能力。

my-skills 放我自己的 12 个定制 skills。

quarantine 用来隔离低频、重复、暂时不用的能力。

这次治理带来的变化很明确。
做 coding 任务时，Agent 默认看到的是工程相关能力，不再同时背着写作、图像、发布、低频工具。
做写作任务时，我再切到写作 preset。做视觉设计时，再切到视觉设计 preset。
这不是说模型能力突然变强了，而是选择空间变小了，上下文变干净了，工作模式也更清楚了。
我现在更愿意把这件事叫“默认暴露面治理”。
工具库可以很大，但每次任务暴露给 Agent 的工具面必须很小。

默认暴露面治理：从混杂 skills 到按场景分组

我的做法：把工具当作需要治理的资源
经历过这次整理后，我现在不再问"还能给它加什么工具"，而是问"这次任务到底需要哪几个"。
具体有五条。
最小工具集，默认只挂当前任务必须的工具，而不是能挂的全挂。
按任务装载，工具随任务进出，用完就卸，不让上下文长期背着一堆用不上的能力。
工具分级，把工具分成只读、可写、不可逆三级，区别对待。
确认与接管，可写和不可逆的工具，必须配确认或人工接管，不能只靠模型自信。
可观测，把工具回传、技能灌入、授权确认这类噪音指标当成健康信号去盯，而不是等它们堆满了才发现。
这件事可以用团队来类比。
你不会给一个新人开通所有系统的最高权限，再让他"看着办"。
Agent 也一样。工具是权限，不是福利。
Agent 的能力上限，不取决于你挂了多少工具，而取决于你有没有把工具收敛成这次任务真正需要的那几个。
Agent 工程化的第二课，是给它做减法
上一篇我说，Agent 工程化的第一课，是约束任务边界。
这一篇我想说，第二课是约束工具。
这一天的协作日报给我的提醒很直接：工具不是越多越好。4286 次工具回传、682 次确认、60 次技能灌入，叠加起来，不是让 Agent 更能干，而是让它更难聚焦、更容易越界。
后来的 skills 分类管理又补了一层证据：真正有用的不是拥有更多工具，而是把默认暴露面压到当前任务需要的范围内。
真正能进生产的 Agent，不是工具最多的那个，而是工具最干净、最受控的那个。

常见问题
企业 Agent 为什么工具越多越容易失控？
因为工具数量同时放大三件事：模型要先选择工具，上下文会塞进更多工具说明和调用结果，可写、可发送、可审批的动作入口也会变多。工具没有治理时，能力增加的同时，误选、误读和越界的机会也在增加。
MCP 和 skill 太多时，应该先删工具还是先分组？
我会先分组，再决定要不要删。很多工具不是没价值，而是不该默认暴露给所有任务。先把工程、写作、视觉设计、个人定制和低频能力分开，让 Agent 每次只看到当前任务需要的那一组。
什么是 Agent 的默认暴露面治理？
默认暴露面治理，就是控制 Agent 在任务开始时默认能看到什么工具、说明和能力。工具库可以很大，但默认上下文要小。这样做的目标不是削弱 Agent，而是减少选择噪音、上下文污染和越界入口。
