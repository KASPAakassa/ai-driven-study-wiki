真正拖慢 Agent 协作的，不是犯错，而是停不下来从 51 个 AI Coding 会话里，我看到的不是模型能力问题，而是任务边界在多轮执行中被一轮轮放大。

这是《企业 Agent 开发手记》的第 1 篇。
这个系列，记录我在企业 Agent 从 Demo 走向生产环境前，补齐工程边界的实践。
包括权限、工具治理、状态管理、异常恢复、人工接管和上线检查。
我复盘了自己一天里的 51 个 AI Coding 会话，涉及 8 个项目。原本我以为最高频的问题会是模型答错、工具失败，或者代码生成质量不稳定。
结果不是。
最突出的信号是：范围蔓延型 出现了 47 次。
样本说明：这是我某一天的个人 AI 协作日报，不是行业统计；计数按用户消息级标签归类。
为了避免把这句话说虚，我先把当天最关键的数字摊开：
样本底盘：51 个 AI Coding 会话，涉及 8 个项目。

会话结构：主力编码代理 43 个会话，辅助对话代理 8 个会话。

活跃时间：主力编码代理约 331 分钟，辅助对话代理约 51 分钟；

最高频提问质量信号：范围蔓延型 47 次。

返工信号：返工修正 90 次，重复推进 58 次，安装/配置反复 49 次，验证补跑 24 次。

协作噪音：工具调用记录 1083 次，授权确认记录 127 次，纯截图消息 72 次。

这些数字不能直接推成行业结论。
但它们至少说明，在一个真实工程日里，任务边界没有被重新压实，不是偶发感受，而是一个反复出现的协作结构问题。
正因为它来自真实工作流，反而能说明一个很具体的工程问题：
Agent 最容易失控的地方，不是第一步不会做，而是做完一轮之后，下一轮任务边界被放大了。

这件事看起来像 AI Coding 的小问题。站在企业系统开发负责人的角度，我更关心它背后的生产风险：一个 Agent 如果连当前任务边界都守不住，就不应该直接接业务状态。

任务边界在多轮执行中一轮轮变大

主动性在 Demo 里是亮点，在生产里是风险
我们天然喜欢主动的 Agent。
它会规划，会拆任务，会调用工具，会在失败后继续尝试。Demo 阶段，这些能力会让人觉得它真的像一个能干活的助手。
问题也从这里开始。
在真实工程协作里，主动性不只是能力，也是一种风险。Agent 会顺着上下文继续补、继续猜、继续扩大范围。它不是故意越界，而是上下文给了它一个继续推进的惯性。
举个 AI Coding 的例子。你本来只想让它把某条连接线改细一点，它可能顺手整理组件结构、调整布局、改掉相邻样式。每一步看起来都不大，但几轮之后，任务已经不是原来的任务。
企业 Agent 也是一样。
一个 CRM Agent 如果只是生成客户跟进建议，它主动一点可能很好。但如果它顺手改了客户状态、发送了邮件、读取了不该看的区域数据，这就不再是智能，而是越权。
Demo 阶段看的是 Agent 能不能多走一步。生产环境看的是，它知不知道哪一步不能走。
51 个会话里，任务边界失控不是大事故
这次复盘里最值得警惕的，不是某个 Agent 犯了严重错误，而是很多小失控反复出现。
比如，子代理回传了审查结果或执行状态，下一轮任务没有重新压缩目标。一个样式小改，被带出额外结构调整。一个测试失败，被扩成大范围重构。验证在补救问题，但没有充分前置到任务定义阶段。
这些事情单独看都不吓人。真正的问题是它们会叠加。
放到手机屏幕上看，我更愿意把这些现象写成几组对照：
继续派工：看起来很高效，实际风险是没有重新定义边界。

自动补救：看起来很主动，实际风险是验收条件被后置。

多代理并行：看起来很强大，实际风险是上下文噪音变多。

一次多改：看起来很省事，实际风险是回归风险变大。

这些现象和数字能对应起来。
范围蔓延型 47 次，说明边界问题不是偶尔出现一次。
返工修正 90 次和 重复推进 58 次，说明很多任务不是一次完成，而是在多轮补救里来回拉扯。
安装/配置反复 49 次和 验证补跑 24 次，则说明验证经常是在问题暴露后补上，而不是在任务开始前就变成验收边界。
返工是结果，范围蔓延更像上游原因。任务边界没有先收紧，后面才会出现重复推进、补跑验证和来回修正。
这些数字不能被夸大。它们只是用户消息级计数。
但它们提醒我一件事：Agent 不一定是完全失控，它更常见的问题是每次多做一点点。多几轮之后，任务已经偏离了原来的目标。
每一轮开始时，都要重新声明任务边界
Agent 执行任务时，危险的往往不是第一步做错，而是第二步开始时，还带着上一轮的上下文惯性继续跑。
我现在会把每一轮 Agent 任务拆成三个边界：
目标边界，这轮到底只解决什么问题。

范围边界，哪些文件、模块、行为不碰。

验收边界，做到什么才算完成。

每轮派工前重新压实目标、范围和验收边界

以前我也会写这种指令：
继续处理上面的审查意见。
这句话非常自然，也非常危险。
因为“继续”没有告诉 Agent 当前轮次的目标、范围和验收。它只是把上一轮上下文原样交给下一轮。上下文越长，Agent 越容易把噪音当成任务。
更稳的写法是这样：
请只处理当前项目里的类型检查失败；
范围限报错模块与对应测试；
验收为指定测试通过且不改无关文件。
这不是 Prompt 技巧，更像工程管理动作。
你不会把一堆会议纪要直接丢给工程师说“继续推进”。Agent 也一样。回传信息不是任务本身，必须先被压缩成一个可验收请求。
对 Agent 来说，“继续”是一个危险词。每一次继续，都应该重新声明目标、范围和验收。
为什么这件事和企业 Agent 有关
Coding Agent 任务边界失控，通常造成代码返工。企业 Agent 任务边界失控，可能会误查数据、误调工具、误改业务状态。
这是两类问题的本质差异。
写代码时，Agent 多改了一个文件，我们可以通过差异检查、测试和代码审查把它拦下来。成本会变高，但通常还能回退。
业务系统里不是这样。
一个企业 Agent 一旦接入 CRM、OA、ERP、邮件、审批或客户数据，它的每个动作都带着身份、权限、数据范围和业务后果。
所以，企业 Agent 不能只定义“它能做什么”，还必须定义“它当前这一轮被允许做什么”。
比如：
查客户资料时，不能顺手改客户状态。

生成跟进建议时，不能自动发送邮件。

分析商机时，不能越权读取其它区域数据。

工具调用失败时，不能无限重试或换工具乱试。

数据不完整时，不能用猜测补齐业务事实。

这些限制看起来会让 Agent 变慢。
但真实情况相反。没有边界的 Agent 才慢。它会把本来应该停下来的问题继续推进，然后把风险留给人工返工、追查和兜底。
企业 Agent 的风险不是它什么都不会做，而是它做了超出当前授权和上下文的事。
生产级企业 Agent 必须有停止条件
如果一个 Agent 想进入真实业务系统，它必须知道什么时候该停。
停止条件不是为了让 Agent 变笨，而是为了让它能被托付。一个不会停的 Agent，只适合做 Demo，不适合接业务状态。
我现在会优先看三类停止条件。
权限不明确时停，如果 Agent 不知道自己以谁的身份执行，不知道当前用户能看哪些数据、能改哪些字段，它就不能继续。企业系统里，身份不是背景信息，而是执行边界。
数据不完整时停，业务字段缺失时，Agent 不能为了把流程跑完而脑补事实。客户预算、合同状态、审批节点、发票信息、库存数量，这些都不是可以合理猜测的内容。
动作不可逆时停，发邮件、改状态、提交审批、写入外部系统之前，Agent 必须进入确认或人工接管。越接近不可逆动作，越不能只靠模型自信。

生产级 Agent 的三类停止条件

这也是企业 Agent 和普通聊天机器人的分界线。
聊天机器人答错一句话，用户可以追问。企业 Agent 改错一个业务状态，后面可能就是工单、审计、客户投诉和数据修复。
Agent 工程化要做的，不是让模型更主动，而是把主动性装进可控的状态机、权限边界、工具治理和人工接管流程里。
我的做法：每次派工都压成一个可验收请求
我现在会把每次继续派工压成六个要素。
目标：这轮只解决什么问题
上下文：为什么现在要做
范围：只允许碰哪里
约束：哪些事情不能做
验收：怎么证明完成
交付物：最后要给什么
这六项不一定每次都写得很长。但它们要在任务开始前被重新声明，而不是散落在上一轮上下文里。
如果是 AI Coding，我会这样写：
目标：只修复当前测试里的类型错误。
上下文：上一轮实现已经完成，但类型检查提示返回值不匹配。
范围：只允许修改报错模块和对应测试。
约束：不改公共 API，不重命名字段，不做顺手重构。
验收：指定测试通过，类型检查不新增错误。
交付物：说明改动文件、验证命令和剩余风险。
如果是企业 Agent，我会这样写：
目标：只生成客户跟进建议。
上下文：销售需要基于最近一次沟通记录准备下一步动作。
范围：只读取当前客户、当前商机和当前用户有权限访问的互动记录。
约束：不发送邮件，不修改客户状态，不创建任务。
验收：输出建议、依据和缺失信息。
交付物：给销售确认的跟进草案。
这里真正重要的不是格式，而是控制权。
任务被压缩之后，Agent 才知道这一轮的边界在哪里。人也更容易检查它有没有越界。
我在日报里写过一句话：不要直接把上一轮状态回传当成下一轮任务。先抽取一个动作、一个文件或模块范围、一个可运行检查。
这句话放到企业 Agent 里同样成立：不要直接把上一轮对话、工具返回和业务上下文丢给 Agent 继续跑。先把它们压成一个被授权、可验证、可停止的请求。
Agent 协作质量的上限，不只取决于模型能力，也取决于人有没有把任务边界重新压实。
Agent 工程化的第一课，是约束它
Agent 不是越主动越好。
真正能进生产的 Agent，必须知道边界，知道验收，也知道什么时候该停。
这次 51 个 AI Coding 会话给我的提醒很直接：任务边界不是在第一轮定义一次就够了。每一次审查结果回传、每一次工具失败、每一次继续派工，边界都要被重新声明。
否则，Agent 会沿着上下文惯性继续往前走。
它可能每次只多做一点点。但企业系统不怕 Agent 慢一点，怕的是它在错误边界里跑得太快。
