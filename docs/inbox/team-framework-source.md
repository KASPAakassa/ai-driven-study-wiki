# 原始资料:成品代码越来越便宜,为什么团队框架反而更重要

最近半年，团队里多了不少「一句话搞定一个功能」的时刻。想要一个带筛选和分页的列表页，一句话丢给 AI，三十秒后代码就在那里了。想接一个新的第三方服务，描述一下接口文档，封装层直接出来了。
这种感觉很奇妙。代码的生产成本断崖式下降，以前一个下午的活，现在一杯咖啡还没凉就完成了。
但做着做着我发现一个不太对劲的地方。代码变便宜了，系统的维护成本并没有跟着降。 甚至因为代码产出速度变快了，需要治理的东西反而更多了。
这里说的「团队框架」，不是什么新名词——它就是一套结构化的约定，加一层薄技术胶水，铺在通用框架之上。让团队知道「怎么干」，而不是每次重新讨论。这件事以前就重要，AI 时代来了之后，更重要了。
AI 没有记忆，规则必须有
Vibe coding 有一个很容易被忽略的特点，AI 生成的代码是没有上下文记忆的。你这一次让它写一个列表页，它写了。下一次让它加一个编辑功能，它又写了。但这两次之间，你们用了不同的错误处理方式、不同的状态管理模式、甚至不同的 import 路径。AI 不管这些。每一次生成都像一个新来的外包，干活快，但从来不知道之前的人怎么干的。
你不告诉它规则，它就每次都发明新规则。
这才是真正要命的地方。过去团队的问题是「代码写得不够快」。现在的问题是「代码出得太多，但谁在管一致性」。过去你可能担心框架太死板限制了速度，现在你反而需要担心没有框架托底，速度会把代码库冲成一盘散沙。
矛盾就这么反过来了。AI 不负责一致性，一致性得由团队框架来保证。
没有约束，架构就会散架
不只 AI 这样，人也一样。
一个五人团队，没有统一约束的话，每个人都会按自己的偏好做选择。路由怎么组织，有人喜欢按功能分，有人按页面分。状态管理用什么，A 觉得 Pinia 够用，B 想上 Zustand，C 说直接用 Composition API 就行。API 请求怎么封装，fetch 直接写、axios 加拦截器、或者自己包一层——三种写法同时存在，谁也不觉得有问题。
单独看，每一个决策都合理。放到一起呢，项目就变成了五个人各自舒适区的拼盘。新人进来要看五种风格才能搞明白「我们到底怎么写代码」。这就是架构的碎片化——从来没人做过收敛，每个决策单看都对。
这也解释了为什么很多团队对 Nuxt、Next.js 这类大而全的框架又爱又恨。爱的是它们一上来就把所有决策帮你做了，目录结构、打包策略、渲染模式，不用讨论，照着写就行。恨的也是同一件事，决策不是你做的，想改的时候发现它是承重墙。
Google Chrome DevTools 工程师 Jack Franklin 离开 React 之后写过一篇文章，用了一个词叫 Inversion of Control，控制权的反转。用 React 的时候，组件什么时候渲染不是你说了算，是 React 说了算。99% 没事，剩下那 1%，你想伸手调，伸不进去。全栈框架也一样，便利的代价是控制权。
所以这里其实有两个陷阱，不是一个。
左边，被大框架绑死。右边，没有任何约束，架构散成一地。过去很多团队感受到的是左边那个，本能地往右躲，少用框架、多点自由。但自由多了，碎片化就来了。真正需要的，是在两个陷阱之间找到一条自己能控的中间地带。让团队做一次选择，然后把它固定下来——框架不替你选，个人也不各自选。
但过去这件事走不通。方向没错，但成本太高。你得维护路由、渲染、构建、热更新、TypeScript 支持、测试工具链、部署脚本，而且不是一次性投入，是持续投入。大多数业务团队根本养不起。所以很长一段时间里，大多数人的选择就是忍，选一个最不坏的框架，接受它的限制。
现在条件变了。
框架在变轻，AI 需要轻量约束
先说框架这一头。框架本身正在被拆成可拼装的积木。 过去你选 Next.js，选了它的一整套东西，路由、打包、服务器运行时，没法拆开用。现在不一样了。Vite 提供了框架无关的构建层、HMR 和 SSR 原语。Nitro 提供了可独立使用的服务器运行时，Nuxt、SolidStart、AnalogJS 都在用，但你也可以单独拿来跑自己的服务。
Vike，前身是 vite-plugin-ssr，口号更直接：Build Your Own Framework。在你选好的 UI 框架之上，只提供 SSR 和路由这一层薄胶水，其余你自己组装。Vinxi 再进一步，在 Vite 加 Nitro 之上封装了一套可编程的服务器框架层，SolidStart 就建在它上面。SolidStart 的文档里有一句话说得特别直白，「这里的每一块都可以替换成你自己的实现」。
这些工具的共同点是，它们把 Next.js 给拆了。构建、路由、渲染、服务端运行时变成了一块块可以独立选的积木。框架的价值从「打包提供一切」变成了「你自己决定怎么拼」。组织能力这件事，门槛低得多，收益却大得多。你不需要再造一个 Next.js，你只需要定义「我们怎么用 Vite 加我们选的路由加我们的服务器运行时」。
另一头更关键：AI 需要一个结构化的上下文才能帮上正经的忙，而不是添乱。
团队框架就是 AI 的「工作说明书」
你让 AI 给项目加一个新的 API 接口，如果没有任何约束，它可能会怎么做呢。
把鉴权逻辑直接写在接口文件里，因为上次另一个模块就是这么干的。用了一套跟你现有错误码体系完全不搭的返回格式。import 了一个已经在项目中标记为 deprecated 的工具函数。
这不是 AI 的问题。是你没告诉它规则。
而所谓的「团队框架」，在新环境下，很大程度上就是一套给 AI 读的约定。
「接口文件的鉴权通过这个中间件走，不要自己写。」 「错误返回用这个统一函数，不要发明新的。」 「这个目录下的工具函数不要用了，用新的那个替代。」
这些东西写下来，不只是给人看的。结构化之后，它们就是 AI 的工作说明书。AI 在生成代码之前先读一遍团队约定，产出的代码自然就更像你们团队写的，而不是像从 Stack Overflow 上随机挑的答案。
这里有一个挺有意思的反转。过去团队框架最大的成本是维护文档和保证一致性，现在 AI 恰好擅长把约定执行到位。 你只要维护一套干净的规则描述，AI 帮你落地。相当于把维护成本里最繁琐的那部分外包出去了。
不是再造一个 Nuxt，是铺一条路
所以现在的「团队框架」不应该被理解成一个新的全栈框架。它更像是在通用框架之上铺的一层薄约束。
怎么理解这个区别。Nuxt 这类框架像一个精装修公寓，搬进去什么都有，但你想拆一面墙，可能发现拆不动。而这条路，更像把经常走的土路修成柏油路，你知道往哪个方向走最快、哪里有坑、哪里在修。想走别的路，可以，没人拦。但大多数时候，走这条路最省事。
具体来说，这条路可以包括这些东西。
项目模板和模块边界，新项目从哪开始，模块怎么拆，不用每次讨论。 鉴权、权限、日志、监控的标准接入方式，不绑某个框架的插件，团队统一约定。 数据访问和接口约定，API 怎么调、错误怎么返回，有固定的写法。 部署和测试基线，CI 跑什么，CD 怎么配。 可替换的底层适配器，业务代码不直接 import 框架特定 API，而是通过团队自己的薄封装。框架换了，换适配器就行。 AI 可读取的架构说明和操作指令，活文档，不是写好就过期的 Wiki。 少量验证过的默认路径，加上明确的逃生舱，默认怎么做是清楚的，但你也知道怎么绕。
这条路不是取代 Next.js 或 Nuxt。底层依然是 Vite、Webpack、Node.js。中层你可以继续用现有的框架，只不过不直接裸调它的内部 API，而是经过自己的一层薄封装。这层封装定义的是「我们怎么用」，不是「我们用什么」。
Jack Franklin 有一个判断我挺认同的，选择那些可以被轻易替换的依赖。 他用的是 lit-html，一个 3.3kB 的包，功能不花哨，但随时能换。团队框架的这一层也应该是这个属性。不重，不绑死任何东西，存在的唯一理由是减少团队在「怎么做」上的重复决策，同时也让 AI 知道该怎么做。
写在最后
代码越便宜，写好代码的约束反而越重要。这件事听着反直觉，但仔细一想其实很合理。当生产的门槛降到几乎为零，质量的差异就不再是能不能做出来，而是做出来的东西能不能长期待在一起。
但现在两个条件同时变了。框架生态把自己拆成了可拼装的积木，AI 把维护约定的成本打下来了。铺一条自己的路，花少量成本拿到控制权，同时让 AI 能帮上忙而不是添乱，这件事正在从一个理想主义选项，变成一个务实选项。
它不浪漫，也不革命。就是每个团队迟早要面对的一件事。当代码不再稀缺，稀缺的是秩序。
