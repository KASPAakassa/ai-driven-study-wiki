架构师的日常不是在学新名词，而是在几个看似独立的概念之间建立连接。今天这些概念——复杂度治理、技术债、架构演进——在很多Agent项目的设计文档里各占一个section，但它们实际上指向同一个核心问题：怎样让Agent在复杂环境中持续做出正确的决策？
    先拆复杂度治理。Agent系统复杂度增长很快：Prompt版本、工具数量、模型路由、评估集、权限策略都会互相缠绕。复杂度治理要靠模块边界、配置版本化、废弃机制和架构评审。每新增一个工具，都要问是否已有能力可复用；每新增一条特殊规则，都要问三个月后谁维护；每绕过一次标准流程，都要记录技术债。复杂度不会自己消失，它只会换个地方收利息。
    再拆技术债。Agent技术债比传统系统更隐蔽。一个临时Prompt、一段没有评估的路由规则、一个过宽的工具权限，短期都能跑，长期都会变成事故入口。治理技术债要建立债务台账：问题是什么、风险多大、触发条件、还债成本、负责人和截止时间。每个迭代固定留出还债预算，尤其是评估集、日志、权限和错误处理。技术债不是罪，装作没有才是。系统不会忘，你只是暂时没收到报警。
    最后拆架构演进。这三者的关系不是线性的——复杂度治理是基础，没有它后面的都是空中楼阁；技术债是工程化的保障，把复杂度治理的能力可靠地落地；架构演进是质量的最后一道防线，确保整个链路不会在最后一步翻车。Agent架构演进要从可替换性开始设计。模型会换、框架会换、向量库会换、工具协议会升级，如果核心业务逻辑和这些实现绑死，未来每次升级都是拆房重建。演进友好的架构会把接口、配置、状态和执行引擎分层，关键决策有ADR记录，迁移路径有双写或影子验证。架构不是一次画完的图，而是一套允许系统长大的骨架。骨架歪了，长得越快越疼。
