《企业 Agent 工程化手记》第 7 篇。
我长期做企业业务系统，这半年也在持续重构 Office Agent 的 CRM 能力。最近排查一个真实环境的 400 错误时，我们发现：接口能访问，请求也到了对方，但代码里使用的一个字段，在目标系统里根本不存在。
本地类型能编译，测试数据也能对上。真实环境却直接告诉我们：这份契约不存在。
Could not find a property named
'legacy_contract_number'
on type 'contract_entity'.
这是我们真正修过的一次集成偏差。它没有演变成线上生产事故，但足以暴露问题。
它让我越来越确定：
Agent 接进业务系统时，接口调通只是开始。
上一篇讲权限和用户身份，解决的是“能不能进”。这一篇想讲的是：进去之后，怎样避免把事情做坏。
接口通了，真实系统为什么还是不认
代码里使用的合同号字段看起来很合理。命名规范、调用方式、测试数据，都能对得上。
但真实环境的元数据里，这个字段不存在。真正可用的是另一个历史命名的字段。
同一轮排查还发现，有的记录读取把行 ID 当成了备选键，也就是另一个业务唯一标识。但目标表根本没有定义这个键。
如果只看代码，很容易继续猜字段名、改参数、再试一次。
我们没有继续猜，而是直接检查真实环境的元数据，确认实体、字段和键，再修正中央字段映射与记录读取方式。
主键回答“这条记录是谁”，备选键回答“哪个业务字段能唯一定位它”。目标表没有定义备选键时，换一个方法名解决不了问题，因为调用语义本身就是错的。
修完这一处后，我们又用只读检查扫描了相邻的表、字段和键，避免下一个接口因同类偏差再次失败。
这次排查把存量系统集成里的一个问题摆到了台面上：
接口文档和本地类型都不是最后真相，运行环境才是。
接口可以访问，只代表技术通道存在。它不代表字段、键、返回结构和业务语义已经对齐。
Agent 会把接口偏差放大成业务风险
普通程序遇到接口错误，通常会报错、记录日志，等人处理。
Agent 不一定停在这里。它可能重试、换工具，或者根据不完整的返回继续推进。一次接口偏差，就可能被放大成整条业务链路的不确定性。
我们还处理过另一类相似问题：流式连接一直收到保活消息，页面也一直显示加载中，但没有正文、工具进度或完成事件。
连接没有断，不代表任务还在推进。本地类型能编译，也不代表真实环境存在那个字段。
两类问题都混淆了技术信号和业务事实。
Agent 需要的除了可调用的 API，还包括一份能约束结果、失败和副作用的业务契约。

技术信号与业务事实之间仍需要验证边界

真实集成必须处理的四个现实
我现在更愿意把 Agent 集成理解成：系统要给 Agent 一份可执行的业务契约。
这份契约至少要处理四个现实。

可执行业务契约周围的四项集成保障

一、幂等：失败以后，能不能安全地再来一次
在一条真实的收款回调链路里，外部系统可能因为没有收到响应，把同一笔收款再次推送。
系统收到回调后，第一步不是直接写入，而是用稳定的幂等键查找已有付款。记录已经存在，就返回原付款 ID，不再重复创建。
但“先查再写”还不够。两个回调可能同时查到记录不存在，所以幂等字段还必须由存储层保证唯一。第二次写入发生冲突后，应回读原记录，而不是继续触发后续动作。
因为付款创建之后，还会更新待收余额、创建跟进任务或发布事件。重复一次，错误就会沿整条副作用链放大。
还有一个更隐蔽的问题：第一次调用可能已经写入付款，却在更新余额前中断。重试如果只看到记录存在便直接返回，就会留下未完成的中间状态。
更完整的方案，是保存处理状态和检查点；跨系统事件还可以通过 outbox 持久化后再发送。这里说的是下一层可靠性设计，不代表当前链路已经全部实现。

幂等键、检查点、outbox 和完成状态组成的恢复链路

二、半成功：报错时，业务可能已经完成了一部分
Office Agent 的工单批量导入会同时处理新建和更新，每一行还要先去 CRM 匹配对应项目。
真实情况可能是：前几行已经成功，某一行却因为同名项目匹配到多个结果而失败。
把整批标记为成功，会隐藏失败；标记为完全失败，又会让人误以为前面的写入没有发生。
所以这条链路会保留已经成功的行，继续处理后续数据，并记录新建数、更新数、失败数、失败行号和原因。只要成功与失败同时存在，批次状态就是 partial_failed。
前提是每一行业务上相对独立。如果后一行依赖前一行，或者整批必须共同满足一个约束，就不能继续处理后再汇总失败，而要使用整批事务、预检或补偿流程。
半成功必须成为可保存、可查询、可继续处理的业务状态。
三、契约校验：不要让 Agent 对着旧文档猜现场
存量系统的契约会漂移。字段会改名，环境会不同，错误可能藏在成功响应里，文档也可能落后于实现。
契约校验至少要发生在两个时间点。
接入前：用真实环境的元数据或探测接口，确认实体、字段、键、权限和返回结构，不把本地类型当成现场真相。
运行时：不只检查状态码，还要校验必要字段、业务状态和影响对象。结果不满足契约时，停在集成层，不要交给模型自由解释。
四、超时与降级：没等到结果，不等于可以猜结果
外部系统会慢、会挂，也会出现“连接还在，业务没走”的中间状态。
因此，一个统一超时并不够。至少要区分：
连接超时：通道没有建立。

业务超时：通道存在，但规定时间内没有真实进展。

整体超时：任务超出了用户愿意等待的边界。

可安全重试的动作，按上限重试。无法确认是否已经产生副作用的，先查询状态。涉及不可逆操作的，暂停并交给人。依赖系统整体不可用时，降级为只读建议或明确失败。
超时以后怎么处理，取决于业务，而不只是网络状态。
给 Agent 工具补一份“集成契约”
给 Agent 增加一个工具时，我不会先问“提示词怎么写”。
作为企业系统开发负责人，我会先确认：这个动作会不会半成功，重试会不会重复产生副作用，返回结果能不能信，失败后由谁收场。
具体来说，我会先填完下面这份最小契约：
动作性质：这是只读查询，还是会改数据、发通知、提交审批？

成功定义：除了 HTTP 200，哪些必要字段、业务状态和影响对象必须同时出现？

重复语义：同一个任务再执行一次，是得到同一结果，还是再次产生副作用？

中间状态：任意一步失败后，哪些动作已经完成，哪些可以继续或补偿？

真相来源：字段、键和返回结构，以元数据、服务定义还是真实探测为准？

失败出口：校验失败或超时后，是重试、查状态、回滚、暂停、转人工，还是降级为只读？

一个接口地址，只回答“怎么调用”。集成契约回答的是：调用之后发生了什么，失败时又该怎么收场。

这份契约不需要一开始就很重。
只读查询可能只需要返回校验和超时上限。修改客户状态、提交审批或发送通知的动作，则必须补齐幂等、状态、补偿、审计和人工接管。
风险不同，集成成本也应该不同。但无论轻重，都不能只留下一个接口地址和一段提示词。
集成层，是 Agent 和真实世界之间的责任边界
Demo 关注模型会不会调用工具。
生产更关心调用之后发生了什么：邮件有没有重复发送，记录改到了哪个状态，一次超时是没有执行，还是已经执行但没有返回。
这些问题不能交给模型自己理解。
模型可以提出意图，但不能重新定义外部系统的事务、契约和失败语义。集成层要做的，是把不可靠的现实变成 Agent 可以安全执行的边界。
所以，我判断一个 Agent 是否已经接稳业务系统，会继续看四件事：
副作用能不能控制。

中间状态能不能恢复。

返回结果能不能校验。

超时之后有没有明确去向。

这四件事缺得越多，它就越像一个 Demo。
