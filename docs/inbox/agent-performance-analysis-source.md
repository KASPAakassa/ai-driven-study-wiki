架构师的日常不是在学新名词，而是在几个看似独立的概念之间建立连接。今天这些概念——性能剖析、延迟归因、trace——在很多Agent项目的设计文档里各占一个section，但它们实际上指向同一个核心问题：怎样让Agent在复杂环境中持续做出正确的决策？
    先拆性能剖析。Agent性能剖析要从端到端trace开始，而不是先怀疑模型慢。一次请求可能包含路由、检索、rerank、LLM、工具调用、格式校验和通知投递。每段都要有span、耗时、状态和关键参数摘要。剖析时看P95/P99，不要被平均值骗了；看调用次数，不要只看单次耗时；看失败重试，不要只看成功路径。性能问题最喜欢躲在'偶尔慢一下'里，像蟑螂，开灯才跑出来。
    再拆延迟归因。延迟归因的目标是把'系统慢'拆成可行动的原因。模型首包慢、检索候选过多、工具API超时、队列堆积、日志同步写入，解决方案完全不同。归因需要统一trace ID贯穿所有组件，并记录每段的开始结束时间。没有归因就优化，通常会把最便宜的地方优化十遍，真正的瓶颈纹丝不动。架构师要让每次慢请求都能回答：慢在哪一段、为什么慢、下次怎么避免。
    最后拆trace。这三者的关系不是线性的——性能剖析是基础，没有它后面的都是空中楼阁；延迟归因是工程化的保障，把性能剖析的能力可靠地落地；trace是质量的最后一道防线，确保整个链路不会在最后一步翻车。分布式追踪（Distributed Tracing）是理解Agent端到端执行路径的核心工具。一个Agent请求可能涉及：前端→API网关→Agent引擎→LLM推理→工具调用A→数据库查询→工具调用B→外部API→结果聚合→返回用户。这条链上的任何一环都可能慢或出错。架构师需要：在请求入口生成trace ID并贯穿所有下游调用；每个span记录父span ID、操作名称、开始/结束时间、状态码、关键参数hash；所有span发送到统一的后端（Jaeger/Tempo）。有了完整的trace，你可以回答任何问题：为什么这个请求慢了？它在等什么？哪一步超时了？
设计练习：假设你要为一个代码审查Agent需要检查PR中的安全漏洞设计一个生产级Agent。写出以下四份文档：1) 系统边界定义——Agent做什么、明确不做什么（不要写'需要时再扩展'这种暧昧表述）；2) 异常场景矩阵——至少3个可能的失败场景，每个配具体的恢复策略和用户感知描述（恢复期间用户看到什么）；3) 成本预算——单次任务各环节的延迟和花费预估；4) 上线监控方案——最需要关注的3个P0指标和对应的告警阈值。
