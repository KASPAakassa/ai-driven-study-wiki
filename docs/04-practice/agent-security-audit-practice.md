# Agent 安全审计实战:从海量噪音中捞出真风险(阿里云 AgentLoop)

> **一句话摘要**:Coding Agent 的执行链(仓库/上下文/工具/授权/数据)让安全审计从"看日志"变成"回放行为链"。本文以阿里云 AgentLoop 为样本,拆解 Agent 审计的完整落地链路:事实底座 → 规则命中(低保真)→ 语义判定(高保真)→ 证据定位 → 实体反查,并给出可复用的方法论。
>
> **来源**:微信公众号《Agent 审计:从海量噪音中捞出真风险》(余韬,迅飞),https://mp.weixin.qq.com/s/Pa7FpJhdcLYj7U3Sn1JIjA

## 概念:为什么 Agent 需要专门的审计

!!! warning "安全面的扩大"
    Coding Agent 的能力越强,它接触到的工作空间就越不再只是编辑器,而是 **代码仓库、模型上下文、工具调用、外部授权和企业内部数据共同组成的一条执行链路**。安全系统要判断:当一次任务里同时出现模型输入、模型回复、工具调用、工具结果和应用上下文时,**哪一条风险真的该进入高危队列**。

**真实安全事件背景**:

| 事件 | 风险 |
| --- | --- |
| openai/codex#2847 | `.env`、`.pem`、`.aws/`、`.ssh/` 等敏感路径应更确定地被排除 |
| BeyondTrust 披露 | Codex branch name command injection,风险含 GitHub User Access Token 暴露 |
| DARKNAVY / 安全内参 | 未授权执行、恶意仓库、本地开发环境暴露等预警 |

**Agent 审计的目标不是"风吹草动就告警",而是让真正进入高危队列的风险更准**:

!!! tip "什么是"准""
    准不等于少报,也不等于放过不确定风险。准的意思是:**单点命中要能回到上下文里被解释;风险事件要能说明它越过了哪条边界、影响了哪些对象、证据在哪里、下一步该怎么处置。**

## 原理 1:完整事实底座是一切的前提

准确判断的前提,不是先写更激进的规则,而是先有**足够完整的行为事实**:

- 把不同 Coding Agent 和 Agent 应用里的**会话、轮次、模型请求、模型回复、工具调用、工具结果**统一采集;
- 没有稳定的事实底座,检测规则再敏感,也只能在局部片段上猜——**这是 Agent 审计区别于普通日志告警的地方**。

!!! warning "凭证泄漏是跨字段流转的"
    一次凭证泄漏不一定只发生在某一行文本里:凭证可能先出现在**工具结果**,再被拼进下一轮**模型输入**;也可能由**模型回复**生成,随后进入任务结果、工单评论或下游日志。只看单个字段,容易把局部可疑当成高危;只看最终结果,又看不见它是怎么来的。

**结论:审计要处理的不是一组孤立日志,而是一条能回放的行为链**——先看全,再判断准。

## 原理 2:审计链路——从低保真信号到高保真事件

```
行为事实统一采集
  → 规则在局部事实上命中(低保真信号)
  → 上下文语义判定(证据充分、边界清楚的提升为高保真风险事件)
  → 落到可定位、可治理的对象上
```

- **低保真信号不是没用**:模型输入出现疑似 AK、模型回复出现疑似 AK、工具参数出现敏感片段,都值得记录——问题在于,**如果每次命中都直接变高危,安全同学看到的是一堆"可能有问题"的红点,而不是真正可处置的风险**;
- **高保真事件要多走一步**:以阿里云凭证为例,单独看到 `LTA...` 片段只是"疑似 AK 泄漏";如果**同一个凭证出现在模型输出和外部上传目标中**,性质就变了——从"疑似泄漏"升级为"具体凭证在 Agent 行为链里被确认暴露";
- **上下文语义判定不是为了把告警做少,而是为了让高危队列更可信**:低保真信号可以多、事实可以尽量全,但真正推到高危位置的事件必须能解释**为什么值得优先处理**。

## 实战拆解:AgentLoop 审计的五个落地能力

### ① 概览页:先知道今天该看什么

安全运营不缺列表,缺的是**优先级**。如果所有风险按时间倒排,反复泄漏的 AK、刚扩散到多个应用的凭证、一次孤立的低置信命中会被混在同一张表里。AgentLoop 概览页把风险从**时间列表提升成工作队列**:

- **影响面最大风险**:指向"数据泄漏:密钥/阿里云凭证",显示已影响 6 个应用;
- **恶化最快风险**:指向"密钥/认证头"的增长。

### ② 数据泄漏页:判断泄露越过了哪条边界

同样是阿里云凭证,位置不同、风险边界不同、处置动作不同:

- **提交到模型 38 次** → 凭证进入了模型输入上下文 → 检查上下文拼接;
- **模型回复泄漏 43 次** → 凭证已到输出侧 → 可能继续进入聊天窗口/任务结果/下游日志 → 检查输出过滤、日志落盘,或先轮换凭证。

!!! tip "边界决定处置"
    单独看"命中 AK"只能知道有敏感片段;放到"模型输入/模型回复"这些边界里,才知道该检查上下文拼接、输出过滤、日志落盘,还是先轮换已经暴露到输出侧的凭证。

### ③ 风险明细:从一类风险下钻到具体凭证

- 先按 **"风险类型 + 应用"聚类**:哪个应用里的哪类风险更集中(如 `loongsuite-pilot-qoder` 下 3 个具体风险、19 条事件、4 个会话);
- 再聚合**具体泄漏的凭证值**(掩码 `LTA...`):**同一个 AK 反复暴露(指向轮换 + 追来源)vs 多个 AK 分散暴露(指向上下文拼接/输出过滤/使用方式的系统性问题)**。

### ④ 风险详情页:一键定位证据,而不是只给一段原文

风险详情展示:应用、严重性、发现 ID、证据摘要、命中字段、关联事件;右侧会话视图**直接跳到风险事件并把模型输出中的 AK 高亮**——把低保真命中背后的原始证据拉回上下文,**让"命中"变成可复核的事件**,而不是让安全同学从整段 prompt/response/tool result 里肉眼搜索。

### ⑤ 实体调查页:用一个 AK 反查影响面

安全调查很多时候不是从会话开始,而是**从对象开始**:Secret、PII、应用、主机/容器、用户、来源 IP、Tool 都可作为调查入口。例如某个 `LTA...` 凭证关联了模型输入暴露 + 模型输出暴露,进入关系图可看到它关联的应用、工具、主机/容器、用户、来源 IP:

- 只影响一个会话和应用 → 处置可聚焦;
- 同一 AK 关联多个应用/主机/用户/工具 → 扩大排查范围,检查凭证来源、使用方式和上下文处理策略。

**实体视角提供的是更接近治理动作的入口,而不只是更多图表。**

## 代码 / 实现:审计链路的最小示意

原文为平台实践,无代码。下面用纯 Python 演示"规则命中 → 语义判定 → 高保真提升"的核心逻辑:

```python
# 模拟一次 Agent 任务的行为链(简化字段)
EVENT = {
    "session": "s-1001",
    "tool_result":  {"content": "AK: LTA5x9... (从外部 API 拉取)", "source": "aws_cli"},
    "model_input":  {"content": "继续处理,使用凭证 LTA5x9... 上传到 oss://bucket/x"},
    "model_output": {"content": "已将数据上传到 https://bucket.oss.aliyuncs.com/x"},
    "external_upload": True,
}

SENSITIVE_PATTERN = "LTA"  # 简化:阿里云 AK 前缀

def low_fidelity_signals(event):
    """规则层:局部字段命中 → 低保真信号"""
    hits = []
    for field in ("tool_result", "model_input", "model_output"):
        if SENSITIVE_PATTERN in event[field]["content"]:
            hits.append(f"字段[{field}]命中疑似 AK")
    return hits

def promote_to_high_fidelity(event, hits):
    """语义判定:同凭证跨字段流转且到达输出侧 → 提升高保真"""
    crossed = len(hits) >= 2                       # 凭证在链上流转
    exposed = event["model_output"] and event["external_upload"]
    if crossed and exposed:
        return "高危:具体凭证在行为链中被确认暴露(输入→输出→外部上传),需立即轮换"
    if crossed:
        return "中危:凭证在链内流转,检查拼接与过滤"
    return "低保真:疑似片段,继续观察"

signals = low_fidelity_signals(EVENT)
print("低保真信号:", signals)
print("判定结果:", promote_to_high_fidelity(EVENT, signals))
# 输出:低保真信号 3 条(工具结果/模型输入/模型输出都命中)
#      判定结果:高危——单点命中升级为可处置的确认暴露
```

**运行结果**:工具结果、模型输入两个字段命中"疑似 AK"(低保真信号),语义判定把它提升为**高保真确认暴露**——同一个凭证在链上流转(工具结果 → 模型输入),且到达外部上传目标。这就是"先看全、再判断准"的代码化表达。

## 实践 / 应用:落地 checklist 与心得

**可复用的方法论**:

1. **先建事实底座**:统一采集会话/模型输入输出/工具调用与结果——没有全量事实,规则再强也是盲猜;
2. **分层信号**:低保真信号保留全(不丢不确定风险),高保真事件从严(必须可解释边界、对象、证据、处置);
3. **边界决定处置**:同一个风险,落在"模型输入"还是"模型回复"边界,处置动作完全不同;
4. **聚合优于罗列**:按"风险类型+应用"→"具体凭证"两级下钻,区分"同一对象反复出问题"vs"系统性分散问题";
5. **证据可复核**:高危事件必须能一键回到原始上下文(命中字段/值/会话/位置);
6. **对象驱动调查**:支持从 Secret/PII/应用/主机/用户反查影响面,让治理动作落地;
7. **接受边界**:准确 ≠ 没有漏报,规则一次写不完——先把"采集 → 命中 → 判定 → 定位"链路跑通,再持续迭代。

**安全启示**:Agent 审计是 [生产级 Agent 9 层架构](../03-agents/ai-infra-layering.md) 中**安全治理横切能力**与 [AI Friendly 架构](../06-enterprise/ai-friendly-architecture/ai-friendly-backend.md) **权限/审计原则**的落地实现——"单点命中可解释、越界可定位、对象可治理"。

## 总结

- **安全面扩大**:Agent 的执行链(仓库/上下文/工具/授权/数据)让审计从"看日志"变成"回放行为链";
- **事实底座先行**:统一采集六类行为事实,凭证泄漏是跨字段流转的,只看单字段会误判;
- **审计链路**:规则命中(低保真)→ 语义判定(高保真)→ 对象化治理;
- **五层落地能力**:概览(优先级)、泄漏边界(处置方向)、聚类下钻(个体 vs 系统问题)、证据定位(可复核)、实体反查(治理入口);
- **心法**:**让每一条高危告警都有上下文、有证据、有影响面**——从噪音中捞出真风险,靠的不是把声音调小。
